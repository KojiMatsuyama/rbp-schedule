## 0. IF とは — 膜（感覚・運動の対）

IF 層は単なるポートの列挙でなく、**感覚・運動の対（アフォーダンス）**である
（[TS概念.md §7](TS概念.md)）。

- **感覚（入力）**: 物理界の実働状態を HUMOS に取り入れる（物理界 → HUMOS）。
- **運動（出力）**: HUMOS の作動指示を物理界へ届ける（HUMOS → 物理界）。

**IF 契約（IF contract）** — 各ポートは次の宣言として成立する:

> 物理世界が、**種別 K** のトークンを、**プレース P** へ、**制約 C** 以内で返すこと。

宣言しなければ作動は**漏れ**（出はするが戻らない）で、系は閉じない
（[TS概念.md §7](TS概念.md)）。宣言・アダプタ・コードは全て記号界の産物なので、
膜は**記号界の構成要素**である（[真界哲学_HUMOS設計.md §3.5](真界哲学_HUMOS設計.md)）。

> **膜（membrane）で開き、スコープ（境界）で閉じる。**
> 外界に対して閉じていて、部屋と装置のあいだ（膜）に対して開いている
> （[TS概念.md §3](TS概念.md)）。

### 0.1 作動・実働・IF の因果鎖（2026-09-10 精緻化）

「作動」は T の内部構成ではない。T の内部構成は｛認知→評価→決定→投射｝であり、
作動は T の**外部**に位置する。作動・実働・IF は**因果鎖の役割**として区別される。

```
投射（内容生成、T 内部）→ 作動（起動）──IF──▶ 実働（実行）
   「何を」                「起動」            「実行」
```

- **投射** = 実働の内容をテンプレートから生成（「何を」）。T の内部構成。
- **作動** = 生成した内容を作用させて因果鎖を**起動**（「起動」）。T の外部。
- **実働** = 起動された因果鎖で作業が**実行**される（「実行」）。T の外部。

**区別の軸は「主体（誰が）」でも「領域（記号界/物理界）」でもなく、因果鎖での役割
（起動 vs 実行）**。これは真界（記号界＋物理界の統一された因果系）レベルの概念であり、
どの領域でも同じ区別が成立する。

#### 実働の二種

実働は「物理界の行為」に限定されない。実働は**二種**ある:

| 種 | 例 | 領域 |
|---|---|---|
| **記符号的実働** | 在庫管理アプリが在庫確認・STN が判断を実行 | 記号界 |
| **物理的実働** | 人が倉庫を確認・スプリンクラーが散水 | 物理界 |

実働の**種類**（記符号的/物理的）は、IF 膜の解像度（HUMOS が物理界をどこまで
記号化しているか）で決まる。記号化されていれば実働は記符号的側へ移動する
（在庫確認: 人→アプリ）。

#### STN は作動まで、実働はしない

STN（記号界）の役割は**作動（起動）まで**。判断（決定）だけでは実働ではない。
実働は常に下流の主体（人・機械・アプリ）が担う。

```
T 内部（記号界・STN）:  認知 → 評価 → 決定(判断) → 投射(内容生成)
                                              ↓
作動（起動）:  STN の最後の行為。IF を通過
                                              ↓
実働（実行）:  下流の主体（人 / 機械 / アプリ）
```

#### IF は作動と実働の接続点（双方向）

IF は作動と実働を**接続する**（直交ではなく）。作動が IF を跨いで実働に届く。

```
入方向:  本圃（ドメインオブジェクト）──スケジュール──▶ 要求(作動)──IF──▶ STN（起動）
出方向:  STN──投射(内容)──▶ 作動(起動)──IF──▶ 実働（人 / 機械 / アプリ）
```

- **入方向**: HUMOS のドメインオブジェクト（本圃）が、スケジュールで要求（作動）を
  生成し、IF を跨いで STN を起動する。STN 側の API が IF の接続点。
- **出方向**: STN が投射（内容）を作り、作動（起動）で IF を跨いで実働に届ける。

#### 膜の 3 種（2026-09-14 帰還膜を追加）

IF（膜）は方向・起点で 3 種に分かれる（[真界_事業主体設計.md §5](真界_事業主体設計.md)）:

| 膜 | 方向 | 起点 → 着地 | 意味 |
|---|---|---|---|
| **要求膜** | 入方向 | **事業主体** → 要求プレース（P_rx_req 等） | 主体が要求を発射（膜弧の起点=主体） |
| **帰還膜** | 帰還 | **外部主体（組織）** → 判定プレース（P_external_wait 等） | 外部の判定結果が帰還（検鏡: 那賀連合会→分化あり/なし） |
| **作動膜** | 出方向 | STN（投射）→ 実働（従業員等） | 主体が作動を実行 |

> **帰還膜は「主体→プレース」でなく「外部組織→判定プレース」**。要求膜・作動膜が
> 事業主体を起点にのぼるのに対し、帰還膜は**外部の主体（判定組織）**から判定結果を
> 帰還させる。機構は §2.4（帰還経路）の `record_return`（①状態記録→②STN再開）。
> 検鏡の確定（status=confirmed / judge_result 付与）で、判定組織の state を
> `entity_attribute`（attr_key=`judge_result_{id}`）に記録し、帰還膜を跨ぐ。

#### 再帰的因果鎖

実働が下流に委譲する場合、新しい作動が IF をまた跨ぐ:

```
投射₁ → 作動₁ → IF → 実働₁
                              ↓（実働₁が委譲する場合）
                        作動₂ → IF → 実働₂ → …
```

作動/実働は主体の性質ではなく**因果鎖の関係**。どの主体もどの位置でも、
両役割を兼ねられる。

> **要約**: 作動＝IF を跨ぐ起動、実働＝IF の向こう側での実行。実働は記符号的/物理的
> の二種。STN は作動まで、実働はしない。IF は作動と実働の接続点（双方向）。
> チャネル（実働の所在）の解決は §8 を参照。

## 1. ポートの棚卸し（境界を跨ぐ全イベント）

**閉包**（[TS概念.md §3.2](TS概念.md)）:

> 境界を跨ぐ可能性のあるすべてのイベントに、ポートがなければならない。

閉包の本当に難しい所は**制御不能入力**だ（[TS概念.md §3.2](TS概念.md)）:
誰もチェックしなかったのに「あの薬剤、実は切れてた」・機械が勝手に壊れた・
突然の病害発生。これらは制御しなかったのに跨ぐ入力で、**ポートを持たないと
閉包違反**になる。ポートの棚卸しは「制御できる出」だけでなく
「制御できない入」を列挙する。後者が漏れると閉包は嘘になる。

**スコープ＝ポートの集合**（[TS概念.md §4](TS概念.md)）— 境界は物理的な線でなく、
「ポートとして扱う」ことを決めたイベントの集合。ポートが決まると IF 契約が決まり、
IF 契約が決まると状態空間が決まる。だからポートの棚卸しは**最も高価な設計決定**。

### 1.1 現行ネット（`jobnet.py` NET）の物理界接触点

現行ネット（薬剤選定 STN）の P/T を突合せて、境界を跨ぐ全イベントを列挙する。

| # | ポート | 種 | 制御 | トークン種別 K | プレース P | 制約 C | 現在の配線 |
|---|---|---|---|---|---|---|---|
| **P1** | Slack送信（処方） | 運動 | 制御 | 処方メッセージ | `P_external_wait`（`external_wait_token`） | `sent ∈ {true,false}` | ✅ `T_rx_exec` → `sos.slack.send_message` → `write_sos("slack_send")` |
| **P2** | Slack送信（在庫結果） | 運動 | 制御 | 在庫結果メッセージ | 終端（post なし） | `sent ∈ {true,false}` | ✅ `T_inventory_exec` → `sos.slack.send_message` → `write_sos` |
| **P3** | 在庫結果の帰還 | 感覚 | 制御 | 在庫状態（薬剤別 あり/なし＋数量） | `P_inventory`（`inventory_token`） | 処方薬剤の全件について在庫状態 | ❌ **同期・内部**（`rx_exec_node` が `place_token`、`inventory_node` が DB 照会）。物理オペレータ不在 |
| **P4** | 圃場・病害虫観測 | 感覚 | 制御 | `field_type` / `pest_matrix` | `P_field` / `P_pest` | DB が正（diseases / pesticides） | ✅ DB seed（`run()` 入口・`_TOKEN_KEYS`） |
| **P5** | ユーザメッセージ | 感覚 | 制御 | `messages`（ユーザ入力） | `P_input` | — | ✅ `run()` 入口 |
| **P6** | 機械の故障 | 感覚 | **非制御** | 故障イベント | （未定義） | — | ❌ 未モデル |
| **P7** | 突然の病害 | 感覚 | **非制御** | 病害イベント | （未定義） | — | ❌ 未モデル |
| **P8** | 天候 | 感覚 | **非制御** | 天候イベント | （未定義） | — | ❌ 未モデル |

**読み取り**:
- **運動（P1・P2）は配線済み** — Slack 送信が事実上の出口。`write_sos` で作動ログを残す。
- **感覚（P3・P4・P5）は「同期・内部」でしか閉じていない** — P3（在庫結果の帰還）が
  本題。物理オペレータ（人・倉庫）が還ってきておらず、ネットが DB を照会して
  自己完結している。P4・P5 は DB seed / run() 入口で制御入力として成立しているが、
  **IF 契約として宣言されていない**（関数呼び出しに留まる）。
- **非制御入力（P6・P7・P8）は未モデル** — 閉包違反の温床。ポートとして列挙していない。

> **P3 が石5 の核心。** 現行の在庫リフレックス（石3）は「Slack がプロセス内で即完了し、
> ネットが DB を照会して自己完結する」ため**見かけ上**閉じる。だが物理界の実働
> （人が倉庫を覗く・機械が壊れる）が還ってきていない。P3 を物理オペレータから
> `place_external_token` で還す配線が、石5 の本丸である。

## 2. 配線パターン（どのポートでどう閉じるか）

「相互開き」が抽象でなく、**どのポートでどう閉じるか**を 3 パターンで書く。

### 2.1 同期クローズ（現行・石3）

```
T_rx_exec（作動:Slack送信処方）
  ├─ sos.slack.send_message ──▶ Slack（物理界）      [運動 P1]
  ├─ humos.write_sos("slack_send")                    [作動ログ]
  └─ humos.place_token("inventory_token", 処方JSON)   [同期・内部 — P3 を内部で置く]
        │
        ▼（run_net ループ先頭がライブマーキング再読で発見）
T_inventory（在庫チェック）
  └─ inventory_node が stb.db inventory テーブルを照会  [DB 自己完結 — 物理オペレータ不在]
        │
        ▼
T_inventory_exec（作動:Slack送信在庫結果）
  └─ sos.slack.send_message ──▶ Slack（物理界）      [運動 P2]
```

- **性質**: ネットが全段を同期で完遂する。Slack がプロセス内で即完了し、
  在庫は DB 照会で自己完結するため、一連で走り固定点に到達する。
- **問題**: 「在庫結果の帰還（P3）」が物理オペレータ（人・倉庫）ではなく、
  ネット内部の handler が同期で置いている。物理界の時間（人が倉庫を覗く）を
  認知していない。これは監査 G2（接地が同期チャット経路に限定）の正体。
- **成立条件**: Slack が同期で完了し、在庫 DB が正確である、という前提に依存する。
  非同期化（人的確認・コールバック）すると、このクローズは閉じない。

### 2.2 非同期クローズ（石5 の目標）

```
T_rx_exec（作動:Slack送信処方）
  ├─ sos.slack.send_message ──▶ Slack（物理界）      [運動 P1]
  ├─ humos.write_sos("slack_send")                    [作動ログ]
  └─ post: P_external_wait（external_wait_token）     [「Slack送信完了を待っている」]
        │
        ▼（enabled な T がなくなる → 固定点 = 停止）
   ┌─────────────────────────────────────────────┐
   │  物理界の時間（人が倉庫を覗く・機械が動く）   │  ← ネットは停止し、ここを待つ
   └─────────────────────────────────────────────┘
        │
        ▼（物理オペレータが在庫を確認）
   IF 感覚ポート P3
  humos.place_external_token("inventory_token", 在庫状態,
                             event={"source":"physical_operator", ...})
        │
        ▼（run_net が再開 — 外部イベントでトークンが落ちれば再評価で発火）
T_inventory（在庫チェック）──▶ T_inventory_exec（作動:Slack送信在庫結果）
```

- **性質**: ネットは `P_external_wait` で**停止**（固定点）。物理オペレータが
  在庫を確認し、IF 感覚ポート P3 経由で `place_external_token` がトークンを置けば
  **再開**（再評価で `T_inventory` が発火）。
- **停止・再開は別機構でなく、マーキング駆動ループの帰結**
  （[真界哲学_HUMOS設計.md §5](真界哲学_HUMOS設計.md)）。外部イベントがトークンを
  置けば再開する。
- **接地**: 物理界の実働（人・倉庫）が `physical_operator` として `write_log` に載り、
  SSS が認知する（§5 参照）。物理界の時間（人が倉庫を覗く・機械が壊れる）が認知される。
- **前提**: ネットを**持続させる主体**（イベント駆動ループ or 非同期再開）が必要
  （監査 G3）。同期バッチのままでは `P_external_wait` を非同期で待つ主体がいない。

> **同期 → 非同期の切り替えは、P3 の配線を変えるだけ。**
> `rx_exec_node` が `place_token`（同期・内部）で置いている在庫トークンを、
> 物理オペレータが `place_external_token`（非同期・外部）で置くようにする。
> ネット構造（P/T/弧）は変えない。`place_external_token` は既に存在する
> （[humos_os/humos.py:305](../.venv/lib/python3.10/site-packages/humos_os/humos.py#L305)）が
> **呼び出し元 0 件**（監査 G1）。石5 はこの関数を P3 の配線で実際に呼ぶこと。

### 2.3 非制御入力クローズ（閉包）

```
機械の故障 / 突然の病害 / 天候不良        [物理界 — 制御しなかったのに跨ぐ入力]
        │
        ▼
   IF 感覚ポート P6 / P7 / P8
  humos.place_external_token(<イベントトークン>, <ペイロード>,
                             event={"source":"uncontrolled", ...})
        │
        ▼
   HUMOS（マーキング変化）──▶ STN（発火 / 審議へのエスカレーション）
```

- **性質**: 制御しなかったのに境界を跨ぐ入力。IF 感覚ポートとして列挙し、
  `place_external_token` で HUMOS に還す。
- **閉包**: ポートを持たないと閉包違反（[TS概念.md §3.2](TS概念.md)）。
  「マトリックス化検知＝閉包違反検知」— ポートを持たずに跨ぐイベントは、単なる
  バグでなく「系がマトリックス化し始めた兆候」（[TS概念.md §9](TS概念.md)）。
- **帰先**: 非制御入力の多くは**審議**（例外の帰還）にエスカレートする
  （[TS概念.md §5](TS概念.md)）。常態（在手・天気 OK・散布完了）は反射で再開し、
  例外（欠品・天不良・突然の病害）だけ審議に回る。

### 2.4 帰還経路（実働完了 → 記録 → ドメインエンティティオブジェクト）

§2.2 は帰還を**在庫結果（P3）に限定**して扱っていた。ここを一般化する。
物理界の実働（人・機械・アプリ）が**終われば**、その**実行記録・状態記録**が
HUMOS の**ドメインエンティティオブジェクト**に戻る。これが系の帰還側であり、
「相互開き」が閉じる最後の一段である。

```
実働（人 / 機械 / アプリ）が完了
        │
        ├─ 人が記録（手動）          例: 圃場巡回点検「完了」を UI で押す
        └─ 機械が自ら記録（自動）    例: 在庫アプリが在庫状態を書き戻す
        │
        ▼
  帰還 API（IF 運動ポートの帰還側）
   ├─ ① 状態記録 → ドメインエンティティオブジェクト
   │     entity.set_attribute(domain_id, entity_id, object_id,
   │                          attr_key, value, attr_kind="state", source=...)
   │     = 圃場（entity stb/field/2）の「現在状態」を更新（SSS の認知対象）
   └─ ② STN 再開 → マーキング変化
         humos.place_external_token(token_key, payload,
                                    event={"source":"physical_operator", ...})
         → stn.resume_net（持続させる主体）が後続 T を発火
        │
        ▼
  ドメインの現在状態が変わる ──▶ 次回の要求トリガーになる（入方向 §2.2 の起点）
```

- **①（状態記録）が帰還の本体**: 実行記録・状態記録は必ず**ドメインエンティティ
  オブジェクト**（`entity_attribute`・`attr_kind=state`）に落ちる。これが
  **SSS が認知するドメインの現在状態**であり、次の要求（入方向）のトリガーにも
  なる。系はここで**ドメインレベルで閉じる**。
- **②（STN 再開）は①の帰結**: 状態記録がマーキングに変化すれば
  `resume_net` が後続 T を発火する（§2.2 の在庫帰還は②のみの特殊ケース）。
  ①と②は別機構でなく、**マーキング駆動ループの帰結**（不変条件5）。
- **記録主体は人でも機械でもよい**: 機械がネットにつながっていれば機械自身が
  記録する（記符号的実働の帰還）。そうでなければ人が記録する（物理的実働の帰還）。
  どちらでも①（entity_attribute）・②（place_external_token）は同一 API。
- **同期・非同期を問わない**: §2.1（同期）でも §2.2（非同期）でも、実働が
  終われば帰還は①②で閉じる。同期なら handler が①②を同期で呼び、非同期なら
  物理オペータが後から①②を呼ぶ。

> **要約**: 帰還は「在庫」でなく**実行記録・状態記録がドメインエンティティ
> オブジェクトに戻る**こと。①状態記録（entity_attribute・state）が本体、
> ②STN 再開（place_external_token→resume_net）は帰結。これで入方向（§2.2）
> と出方向（§0.1）と帰還（§2.4）が揃い、系はドメインレベルで閉じる。

## 3. IF 契約の宣言（ポートごとの契約）

各ポートは IF 契約として宣言する。宣言は記号界の産物（宣言・アダプタ・コード）。

### 3.1 契約の形式

```
IF 契約 #N: <ポート名>
  種      : 感覚 | 運動
  制御    : 制御 | 非制御
  種別 K  : <トークンの種別（彩色）>
  プレース P: <どのプレースに返すか>
  制約 C  : <返す条件・形式>
  アダプタ: <物理基盤に合わせる差し替え層>
```

### 3.2 現行ネットの IF 契約（宣言すべきもの）

| 契約 | 種 | 制御 | 種別 K | プレース P | 制約 C | アダプタ |
|---|---|---|---|---|---|---|
| **IF#1** Slack送信（処方） | 運動 | 制御 | 処方メッセージ | `P_external_wait` | `sent∈{true,false}` | `sos.slack.send_message`（Slack Webhook） |
| **IF#2** Slack送信（在庫結果） | 運動 | 制御 | 在庫結果メッセージ | 終端 | `sent∈{true,false}` | `sos.slack.send_message` |
| **IF#3** 在庫結果の帰還 | 感覚 | 制御 | 在庫状態（薬剤別） | `P_inventory` | 処方薬剤の全件 | **人手・倉庫**（現行=DB 照会の同期スタブ） |
| **IF#4** 圃場・病害虫観測 | 感覚 | 制御 | `field_type`/`pest_matrix` | `P_field`/`P_pest` | DB が正 | diseases / pesticides DB |
| **IF#5** ユーザメッセージ | 感覚 | 制御 | `messages` | `P_input` | — | `run()` 入口（チャット） |
| **IF#6** 機械の故障 | 感覚 | 非制御 | 故障イベント | （未定義） | — | （未モデル） |
| **IF#7** 突然の病害 | 感覚 | 非制御 | 病害イベント | （未定義） | — | （未モデル） |
| **IF#8** 天候 | 感覚 | 非制御 | 天候イベント | （未定義） | — | （未モデル） |

> **IF#3 のアダプタは「人手・倉庫」に差し替え可能**（[TS概念.md §10](TS概念.md)）。
> 第一のリフレックス（石3）は「人手・倉庫」の同期スタブ（DB 照会）で成立している。
> 石5 はこのアダプタを「人手・倉庫の実オペレータ」に差し替える（同期 → 非同期）。
> 物理基盤（Slack・人・機械）は差し替わる**基盤（substrate）**であり、
> 不変のコア（ネット構造＋HUMOS マーキング）は変わらない
> （[TS概念.md §9](TS概念.md) 帰結 1）。

### 3.3 IF 契約のスタブがテストの接缝

**IF 契約のスタブがテストの接缝**（[TS概念.md §9](TS概念.md) 帰結 2）— 記号ネットは
境界を跨がなければ完全には検証できない（接地のないネットは SimNet で終わる）。

- 各 IF 契約は**スタブ**（テストダブル）として独立に検証できる。
- IF#3 のスタブ＝現行の DB 照会（同期）。本番＝人手・倉庫（非同期）。
  両方が同じ IF 契約（K/P/C）を満たせば、ネット構造は変えずに差し替えられる。
- 検証: IF#3 のスタブで「在庫あり」→ `T_inventory` 発火 → 「在庫なし」→
  審議へエスカレーション、を単体で確認する。

## 4. 増分原則（IF 契約を一つずつ）

**作るのは IF 契約を一つずつ**（[TS概念.md §9](TS概念.md) 帰結 3）— HUMOS は実際に
契約から生まれるマーキングだけを持つように育つ。存在しない IF 向けの記号世界を
先に作らない。

### 4.1 増分の順序

| 波 | 内容 | 根拠 |
|---|---|---|
| **0（完了）** | **閉じて動く一回の反射** — 在庫リフレックス（石3）。同期クローズで P1/P2（運動）・P3（同期感覚）が閉じる | [TS概念.md §9](TS概念.md) 帰結 4「最初の石は閉じて動く一回の反射」 |
| **1** | **P3 を非同期に** — 在庫結果の帰還を物理オペレータ（人・倉庫）から `place_external_token` で還す。`P_external_wait` で停止・外部イベントで再開 | 監査 G1・G2・G3 の解消。石5 の本丸 |
| **2** | **P4・P5 を IF 契約として宣言** — DB seed / run() 入口を「関数呼び出し」から「IF 契約の宣言」に昇格（K/P/C を明示） | 閉包の明文化。宣言しなければ漏れ |
| **3** | **非制御入力（P6・P7・P8）をポートとして列挙** — 実際にそのイベントが起きるたびにポートを追加（ポートの棚卸しを漸増的に） | 閉包（[TS概念.md §3.2](TS概念.md)）。後者が漏れると閉包は嘘になる |

### 4.2 増分の制約

- **存在しない IF 向けの記号世界を先に作らない** — P6/P7/P8 のプレースは、
  実際にそのイベントを認知する T がネットに置かれるまで作らない。
  非制御入力の帰先（審議 T）が先（監査 G10）。
- **アダプタの差し替えでネット構造は変えない** — 物理基盤（Slack・人・機械）が
  変わっても、K/P/C が同じならネット構造（P/T/弧）と VM（発火ループ）は不変。
- **同期スタブから非同期本番への切り替えは、配線を変えるだけ** — ネット構造は
  変えない。`place_token`（同期）→ `place_external_token`（非同期）の差し替え。

## 5. 物理界＝オペレータ（接地）

**接地**（[真界哲学_HUMOS設計.md §3.6](真界哲学_HUMOS設計.md)）— 物理界は「入力ポート」
でなく、**空間状態を変えるオペレータ**として SSS に認知される。未接地の系は
真界（TrueWorld）ではない。

- **認知スコープ**（[TS概念.md §6.3](TS概念.md)）— SSS の認知スコープは STN に留まらず、
  物理界の**人・機械・ロボット・業務アプリ・物**（物理界の実働＝オペレータ）も対象。
  HUMOS は「誰が空間状態を変えたか」を、STN のトランジションだけでなく、
  物理界の実働（オペレータ）として認識する。
- **書き込み** — 物理界の実働は `write_log` の `operator_kind` に
  `physical_operator` として載る（[TS概念.md §6.1](TS概念.md)）。
  現行: `write_sos` の `operator_kind` は `"sos"` のみ。`physical_operator` としての
  書き込みは存在しない（監査 G2）。
- **メタ認知**（[TS概念.md §6.7](TS概念.md)）— 系が自資源状態（在庫など）を空間状態の
  一部として認識すること。**倉庫＝内**が定まった（[TS概念.md §10](TS概念.md)）—
  在庫は外部の物でなく、系の実働が依存し消費する物理的基盤＝身体の状態。
  在庫の全変化（逓減・補充・破損・棚卸し）をポートで捕らえる。

> **IF（膜）と接地（オペレータ）は表裏。** IF が「どのポートで閉じるか」（§2）を
> 決め、接地が「そのポートを跨いだものを誰（オペレータ）として認知するか」（§5）を
> 決める。P3 を非同期に配線し（§2.2）、物理オペレータとして `write_log` に載せる
> （§5）ことで、在庫リフレックスは「見かけ上の閉じ」から「真の接地」に昇格する。

## 6. 不変条件との整合

石5 は不変条件（[真界哲学_HUMOS設計.md §6](真界哲学_HUMOS設計.md)）を満たす形で組む。

| 不変条件 | IF での具体 |
|---|---|
| **3. 物理界との接触点は HUMOS に一点に集約** | 全ポート（P1〜P8）は `humos.place_external_token` / `write_sos` / `write_log` 経由で HUMOS に還る。別経路で物理界を触るコードは閉包違反（監査 G4 の cron バイパスが違反例） |
| **4. 物理界の全状態変化に IF ポート** | ポートの棚卸し（§1）で制御入力＋非制御入力の全イベントを列挙。非制御入力（P6/P7/P8）もポートとして列挙 |
| **2. STN は IF・SOS を直接 import しない** | ネットは IF を import しない。`place_external_token` がマーキングを変え、`run_net` がライブマーキングを再読して発火する（間接的開き）。IF は HUMOS の外側、ネットは HUMOS の内側 |
| **5. マーキング ≡ M0 からのリプレイ** | `place_external_token` は firing 行も記録（`transition_id="E:<token_key>"`）ため、外部イベントもリプレイで復元される（[humos_os/humos.py:305](../.venv/lib/python3.10/site-packages/humos_os/humos.py#L305)） |

**間接的開き**（[真界哲学_HUMOS設計.md §4](真界哲学_HUMOS設計.md)）— STN は直接に
物理界を触らず、必ず HUMOS を介す。IF は HUMOS の外側（物理界側）に座り、
ネットは HUMOS の内側（記号界側）に座る。両者は HUMOS のマーキングとイベントで
だけ接する。これが純粋さ（検証可能性）と接地を両立させる。

## 7. 完成の判定（石5 の出口）

[真界_実装状況.md §5](真界_実装状況.md) の石5 の出口:

> 物理界の全状態変化に IF ポートがあり、別経路で物理界を触るコードがない（閉包）。

具体的には:

1. **ポート完備** — ポートの棚卸し（§1）の全イベント（P1〜P8）に IF 契約があり、
   非制御入力（P6/P7/P8）もポートとして列挙されている。
2. **P3 が非同期** — 在庫結果の帰還が物理オペレータ（人・倉庫）から
   `place_external_token` で還る。`P_external_wait` で停止・外部イベントで再開する。
3. **接地** — 物理界の実働が `physical_operator` として `write_log` に載り、
   SSS が認知する。
4. **閉包** — 別経路で物理界を触るコードがない（全接触点が HUMOS に一点集約）。
   cron バイパス（監査 G4）が解消され、全経路がネット経由。
5. **リプレイ整合** — 外部イベント（`E:<token_key>`）を含む全マーキングが
   M0 からのリプレイで復元される（`replay_ok=True`）。

## 8. チャネル解決（実働の所在をどう決めるか）

作動が IF を跨ぐとき、実働は**どの主体（チャネル）**で実行されるか。
この解決は**自動（データ駆動）**であり、人が設計するのは「ルーティングのルール」
ではなく「事実の記号化（データ）」である。

### 8.1 自動解決の原理

判断を駆動するのは「ルール」ではなく**記号化された事実（データ）**。

```
IF ライブラリが読む事実（記号化されたデータ）:
  圃場A → 在庫アプリ: 導入済み / 未導入
  圃場A → 担当者: 山田

解決:
  導入済み → 在庫アプリ API アダプタ → 記符号的実働
  未導入   → Slack アダプタ（山田に）→ 物理的実働
```

「圃場A の在庫確認は Slack で」というケースごとの分岐ロジックは書かない。
事実が変われば（アプリ導入）自動で追従する。

### 8.2 責務の分離（オブジェクト vs IF ライブラリ）

- **オブジェクト（投射的機能）**: 要求の内容生成（「何を」）＋ トークン発行。
  チャネルを知らない（Slack/アプリ API は機構、ドメインではない）。
- **IF ライブラリ（作動＝膜の通過）**: チャネルを解決し、アダプタで届ける。
  記符号的実働・物理的実働の両方をアダプタで吸収。

```python
# オブジェクト（投射的機能のみ）
requirement = self.generate_requirement()      # 「何を」：圃場A の在庫確認
stn.place_token(self.create_token(requirement))
if_library.deliver(requirement)                # チャネルは言わない

# IF ライブラリ（作動＝膜の通過）
class IF:
    def deliver(self, req):
        adapter = self.resolve(req)            # 記号化事実から解決
        adapter.send(req)
```

### 8.3 アダプタの自己記述

アダプタは**自分で「何を処理できるか」「どこで使えるか」を宣言**する。
IF ライブラリは「この要求を処理できるアダプタはどれか」を**宣言からマッチング**する。

```python
class AppAPIAdapter:
    serves = "inventory_check"          # 何を処理できるか（自己記述）
    def available_at(self, field):
        return field.inventory_app.deployed   # どこで使えるか（事実を読む）

class SlackAdapter:
    serves = "inventory_check"
    def available_at(self, field):
        return True                     # 常に使える（フォールバック）
```

### 8.4 自動 vs 手動

| | 自動（宣言マッチング） | 手動（ルーティングテーブル） |
|---|---|---|
| 人がやること | アダプタ実装時に `serves` / `available_at` を書く（1回） | 圃場×要求タイプごとに「どこへ」を登録（都度） |
| 変更時 | 事実が変われば自動追従 | 人がテーブルを更新 |

**どちらでも設計は成立する**。自動の方が保守しやすい（事実が変われば自動追従）。
手動でも可（人が明示的に制御）。

### 8.5 上書き（例外処理）

デフォルトは自動解決。ドメインの意思で「必ず人に通知」等の特殊ケースは、
要求に**任意のチャネル上書き属性**を持たせて対応する（コアには含めず、
必要になったら拡張）。

### 8.6 性能・保守性

- **性能**: IF 配送はネットワーク I/O（ミリ秒〜秒、I/O bound）。分離のコストは
  関数呼び出し1回＋アダプタ解決（ナノ秒〜マイクロ秒）で無視できる。むしろ
  トークン配置（高速・同期）と IF 配送（低速・非同期）の分離で、STN 発火ループを
  高速に保ち、I/O をバックグラウンド/キューに回せる。
- **保守性**: 機構（Slack/メール/アプリ API）の重複排除、モック容易。
- **結論**: 保守性・性能の両面で問題ない。**分離する**。

### 8.7 現行コードへの接地（2026-09-10）

チャネル解決（②）は**出方向**の設計だが、**入方向（要求の STN への到達）と
記号化事実（解決の根拠）が前提**。現行コードで確認した実態:

| 要素 | 現行 | ②との関係 |
|---|---|---|
| 出方向（STN→実働） | `sos/slack.py` 単一チャネル・ハードコード（チャネル選択なし） | ②が解決する対象（今は Slack の1本線） |
| 入方向（本圃→要求→STN） | **未実装**。`humos_os.humos.place_external_token` が足場（呼び出し 0 件・監査 G1） | ②がルーティングする「要求」の到着経路。**石5 の領域** |
| 記号化事実 | `entity_attribute`（domain_id/entity_id/object_id/attr_key/attr_value/attr_kind/source）・`workers`＋`assignee_ids`（従業者）・圃場=entity（`stb/field/1`=本圃、`sync_from_domain` で同期） | ②の解決の根拠（データ）。**大半は既存** |

**核心**: ②は独立した機能でなく、**IF の出方向半分の設計**であり、**入方向
（石5）が要求を STN に届けることを前提**にする。記号化事実（entity_attribute）は
解決の根拠のデータとして大半既存。

### 8.8 要求トークンの形（入方向＝石5との接続）

要求は `place_external_token` で STN に届くトークン（入方向 IF）。

```
humos.place_external_token(
    conn, net_id,
    token_key="requirement_token",
    payload={
        "type":   "inventory_check",   # アダプタの serves とマッチする種
        "target": {"domain_id":"stb","entity_id":"field","object_id":"1"},  # 圃場A
        "context": {...}               # 任意の文脈（散布日・薬剤等）
    },
    event={"source":"domain_object", ...}
)
```

- **`type`** = アダプタの `serves` とマッチする要求の種（§8.3）。
- **`target`** = 解決の文脈（どの圃場/対象で解決するか）。entity の 5-level ID（`world_id ⊃ subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id`。実装は現行 4-level・world_id 追加は v1.5.0 次フェーズ）。
- **`context`** = 任意の文脈。

**②の実装は石5（入方向）にゲートされる** — 要求が STN に届く
（`place_external_token` が呼ばれる）まで、ルーティングする対象が存在しない。

### 8.9 記号化事実のスキーマ（解決の根拠）

解決の根拠は `entity_attribute`（既存）に載せる**記号化された事実**。

```
entity_attribute（既存スキーマ）:
  domain_id, entity_id, object_id, attr_key, attr_value, attr_kind, source

チャネル解決に必要な事実（attr_kind=state）の例:
  (stb, field, 1, "inventory_app", "deployed",     "state", "manual")
  (stb, field, 1, "inventory_app", "not_deployed", "state", "manual")

担当者（既存・attr_kind=requirement と同型）:
  workers（id, name, ...）＋ spray_schedule.assignee_ids = "[1,3]"（従業者ID配列）
```

- **`attr_kind=state`** = 能力事実（導入済み/未導入）。解決の分岐を駆動。
- **`attr_kind=requirement`** = 要求情報（担当者等）。要求ナレッジ
  （[真界_オブジェクト接地設計.md §2.5](真界_オブジェクト接地設計.md)）。
- **圃場 = entity**（`stb/field/1`=本圃、`sync_from_domain` で fields DB から同期）— 解決の `target`。
- **人がやること** = これらの事実を登録（「圃場Aに在庫アプリを導入した」→
  `set_attribute(..., "inventory_app", "deployed")`）。**ルーティングルールではなく
  事実の記号化**（§8.1）。

### 8.10 解決アルゴリズム（接地版）

```
def resolve(requirement):
    candidates = [a for a in adapters
                  if requirement.type in a.serves
                  and a.available_at(requirement.target)]
    if not candidates:
        return fallback(requirement)   # Slack → 担当者（物理的実働）
    return max(candidates, key=priority)  # 記符号的 > 物理的（または明示優先度）

# アダプタの available_at が記号化事実を読む
class AppAPIAdapter:
    serves = {"inventory_check"}
    def available_at(self, target):
        return entity.get_attribute(target, "inventory_app") == "deployed"

class SlackAdapter:
    serves = {"inventory_check"}
    def available_at(self, target):
        return True   # 常に使える（フォールバック・物理的実働）
```

- **解決 = マッチング**（serves ∩ available_at）。手書きの分岐テーブルではない。
- **available_at が entity_attribute を読む** = 記号化事実から自動。
- **優先度**: 記符号的実働（アプリ）> 物理的実働（人）。または要求に明示優先度。
- **フォールバック**: 候補なし → Slack → 担当者（assignee_ids）。

### 8.11 実装フェーズ（依存関係）

| フェーズ | 内容 | 依存 | 状態 |
|---|---|---|---|
| **①** | アダプタ抽象化＋IFファサード（挙動不変リファクタ） | 土台 | ✅ 実装済み（`sos/adapter.py`・`sos/membrane.py`） |
| **A** | 記号化事実のスキーマ（entity_attribute に能力事実を登録・`set_attribute` 経由） | 独立（石5に依存しない） | ✅ 実装済み（`capability.py`） |
| **石5** | 入方向（要求の STN への到達） | 前提 | ✅ 機構実装済み（`place_external_token`→`resume_net`） |
| **B** | 要求トークンの形（`place_external_token` の payload 契約） | **石5（入方向）** | ⚠️ 機構は石5 で成立（payload={type,target,context}）。**P_requirement プレースの固定 STN への追加は未着手**（UI 構造変更・方針要確認） |
| **C** | アダプタの自己記述（serves / available_at / **requires**） | A | ✅ 実装済み（`BaseAdapter.requires`＋`AppAPIAdapter` 具体例） |
| **D** | 解決アルゴリズム（resolve + 優先度 + フォールバック） | A・B・C | ✅ 統合済み（`membrane._resolve`/`deliver` が `conn` を受け取ると `capability.resolve_channel` に委譲） |

- **②（自動チャネル解決）の機構は実装済み**（①＋A＋C＋D）。`membrane.deliver(req, conn=...)`
  が能力事実（記号化事実）から自動でチャネルを選ぶ。
- **B の残 = P_requirement プレースの固定 STN への追加**（入方向の着地点の可視化）。
  固定 STN ネットの構造変更で UI（stn.html）に現れるため、ネット合成方針とセットで判断。
- **①（§8.6 のアダプタ抽象化＋IFファサード）は A〜D の土台** — 挙動不変リファクタとして先行。

**結論**: ②の機構は実装済み（①→A→石5→C/D）。残は **B の P_requirement プレース**
（固定 STN 構造変更・UI 影響）と**実イベント配線**（ドメインオブジェクトが実際に
`place_external_token`/`deliver` を呼ぶ配線）。

## 9. 用語（本設計で使う）

| 語 | 意味 |
|---|---|
| **膜（IF）** | 感覚・運動の対（アフォーダンス）。ポートの集合 |
| **IF 契約** | 物理世界が種別 K のトークンをプレース P へ制約 C 以内で返すことの宣言 |
| **感覚（入力）** | 物理界 → HUMOS。物理界の実働状態を HUMOS に取り入れる |
| **運動（出力）** | HUMOS → 物理界。作動指示を物理界へ届ける |
| **制御 / 非制御** | 系が投じた出（制御）/ 制御しなかったのに跨ぐ入（非制御） |
| **同期クローズ** | ネットが全段を同期で完遂する閉じ（現行・石3）。物理オペレータ不在 |
| **非同期クローズ** | `P_external_wait` で停止し、物理オペレータが `place_external_token` で還す閉じ（石5 の目標） |
| **接地** | 物理界をオペレータとして SSS に認知。未接地の系は真界（TrueWorld）ではない |
| **閉包** | 境界を跨ぐ全イベントにポートがあること。非制御入力もポート |
| **マトリックス化** | スコープ境界（膜）の破断。ポートを持たずに跨ぐイベント＝閉包違反 |
| **アダプタ** | 物理基盤（Slack・人・機械）に合わせる差し替え層。ネット構造は変えない |
| **作動** | 因果鎖を起動させる側（トリガー・原因）。IF を跨ぐ起動。T の外部 |
| **実働** | 起動されて実行される側（作業・結果）。IF の向こう側での実行。記符号的/物理的の二種 |
| **記符号的実働** | 記号界での実行（アプリが在庫確認・STN が判断を実行） |
| **物理的実働** | 物理界での実行（人が確認・スプリンクラーが散水） |
| **チャネル** | 実働を担う主体（人・機械・アプリ）。チャネル解決は記号化事実から自動 |
| **チャネル解決** | 要求を処理できるアダプタを、記号化事実（導入済み/担当者等）からマッチング。人はルールではなく事実の記号化 |
