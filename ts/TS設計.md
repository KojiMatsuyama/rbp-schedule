# TS 設計書

> 概念（TS とは何か）は [TS概念.md](TS概念.md)。
> ここは**構造**（TS がどう組み上がるか）の設計書。
>
> 核心は一言で —
> **状態遷移ネットは純粋なペトリネットのまま、HUMOS を介して間接的に物理界に開く。**

---

## 0. 設計の核心

TS は、記号界と物理界を統合した閉システムである。

統合の鍵は、状態遷移ネットを直接に物理界へ開くこと**ではない**。

- **状態遷移ネット**（State Transition Net / **STN**、旧称 JOBNET・NAVNET）はペトリネットが原理である。ペトリネットは記号界に閉じた系であり、それ自体は物理界を触れない。これが「記号界に閉」の問題である。
- **HUMOS**は、記号界と物理界の**両界に開いた状態空間**である。この問題を HUMOS が管理する。
- **状態遷移ネットは、HUMOS からイベントを受け取ることで、間接的に物理界に開いたシステムを実現する。**
- **HUMOS**は「IF」を通じて、物理界の実働（人・機械・ロボット・アプリケーション）の状態を取り入れる。
- **HUMOS**は、状態遷移ネットからのイベントを、SOS・IF を通じて、物理界への作動（実働）として行う。

このようにして、TS は記号界と物理界を統合する。

---

## 1. 問題の所在 — 状態遷移ネットは記号界に閉じている

状態遷移ネット（[jobnet.py](../jobnet.py)）はペトリネットである。
プレースとトランジション、トークンの消費と生成 — すべて記号界の内部で完結する。

ペトリネットの原理は美しい。有界性・閉包・内部整合が機械的に検証できる。
だが、その美しさが同時に限界でもある。

**ネットは倉庫を覗けない。散布機械を動かせない。Slack を送れない。**

トークンは記号界のプレース間で流れるだけだ。
「在庫がある」も「散布が完了した」も、ネット自身には見えない。
これが「記号界に閉」の問題である。

---

## 2. 解決 — HUMOS が両界に開いた状態空間

答えは、ネットを物理界へ開くことではない。
**ネットの外に、両界に開いた状態空間を置くこと**である。それが HUMOS だ。

HUMOS は、

- **記号界側** — 状態遷移ネットのマーキング・トレース・書き込みログを保持する（[TS概念.md §6](TS概念.md)）
- **物理界側** — IF を通じて物理界実働の状態を取り入れる

状態遷移ネットは HUMOS のマーキングを読む（`enabled_when`）。
HUMOS は IF を通じて物理界の状態を受け取り、状態遷移ネットへイベントとして届ける。

**状態遷移ネットは HUMOS の中を流れるトークンを見る。物理界は HUMOS の外にある。両者を接合するのは HUMOS だけだ。**

---

## 3. 間接的開き — 設計の中心

> **状態遷移ネットは直接に物理界を触らない。必ず HUMOS を介す。**

これが設計の中心である。

- 状態遷移ネットは IF も SOS も直接 import しない。読む・書くのは HUMOS のマーキングとイベントだけ。
- 物理界との接触点は HUMOS に一点に集約される。
- 結果として、状態遷移ネットは純粋なペトリネットのまま（検証可能性を保持し）、HUMOS を介して物理界に接地する。

直接に開くと、ネットの純粋さが失われる（検証不能になる）。
間接的に開くと、純粋さは保たれ、接地も得られる。
**間接性が、閉包と接地を両立させる。**

---

## 4. 二つの流

### 4.1 入力流（感覚）— 物理界 → 記号界

```
物理界実働（人・機械・ロボット・アプリ）
        │  状態変化
        ▼
     IF（膜・感覚）
        │  状態を取り入れる
        ▼
   HUMOS（状態空間）
        │  イベントとして届ける（要求トークンを置く）
        ▼
   状態遷移ネット（要求プレースに要求トークンを置く → マーキング駆動で発火）
```

**入力は必ずプレースに接続される（トランジションには直接接続しない）。**
入力流（感覚）が STN に届く先は、対象トランジションの**一つ前のプレース**（要求プレース）
であり、そこに**要求トークン**を置く。トランジションは要求を**読む**側で、
要求の**着地点**ではない。要求がプレース（マーキング）に置かれることで、
マーキング駆動発火ループ（石2）が「要求＋他条件が揃ったら発火」を自然に判定する
（不変条件 5「マーキング ≡ M0 からのリプレイ」）。
詳細は [真界_オブジェクト接地設計.md §4.1](真界_オブジェクト接地設計.md)。

例：人が倉庫で在庫を確認 → IF が「在庫あり」の状態を取り込む → HUMOS がマーキングを更新 → 在庫待ちプレースにトークンが落ちる → 発火が再開する。

### 4.2 出力流（作動）— 記号界 → 物理界

```
   状態遷移ネット（トランジション発火）
        │  イベント
        ▼
   HUMOS（状態空間）
        │  作動を指示
        ▼
     SOS（作動の運動器）
        │  操作
        ▼
     IF（膜・運動）
        │  実働
        ▼
物理界実働（人・機械・ロボット・アプリ）
        │  実働完了（例：Slack送信した）
        ▼
     IF（膜・感覚）
        │  完了状態
        ▼
   HUMOS（状態空間）← 作動完了ログを記録
        │  状態判断
        ▼
   イベント（次トークン生成）
        ▼
   状態遷移ネット（次トランジション自動発火）
```

例：状態遷移ネットが処方決定 → イベント → HUMOS → SOS（Slack 送信ライブラリ）→ IF → Slack に処方メッセージを送る。
送信完了は IF を通じて HUMOS に戻り、HUMOS が状態判断して在庫チェックトランジションを前進させる（§4.3）。

### 4.3 SOS 作動の完了が状態である

SOS の作動（Slack 送信など）は実働だ。
その**完了**（Slack 送信した）は、単なる副作用でなく、**HUMOS の状態**である。

- SOS 作動の完了ログは HUMOS に記録される
- HUMOS はその状態から状態判断する
- HUMOS はネットを前進させるイベント（次トークン）を発生させる

ネットは「Slack が送信された」ことを直接知らない。
HUMOS が知っている（ログを記録したから）。
HUMOS がネットに伝える（イベントでトークンを置く）。
ネットはトークンを見て発火する。

これが間接的開きの具体であり、能動ゲートの具体である。

例：Slack 送信完了 → HUMOS が記録 → HUMOS が状態判断 → 選定済みトークンを在庫チェック前のプレースに置く → 在庫チェックトランジションが自動発火。
`enabled_when` は「上流が発火したか」でなく「今このプレースに選定済みトークンがあるか」を読む（[TS概念.md §6](TS概念.md)）。HUMOS がトークンを置けば条件が満たされ、発火する。

## 5. 構成要素の責務

| 要素 | 責務 | 触れる世界 |
|---|---|---|
| **状態遷移ネット** | ペトリネット構造・発火判定（enabled_when）・トポロジカル実行 | 記号界のみ（HUMOS を介して間接的に物理界） |
| **HUMOS** | 両界に開いた状態空間。マーキング・トレース・書き込みログ。イベントの集約点。空間状態システム（状態認識・予測・通知） | 記号界 ＋ 物理界（IF 経由） |
| **IF** | 膜。HUMOS が物理界を触る機構。感覚（物理界→HUMOS）・運動（HUMOS→物理界）。ポートの集合 | 物理界（HUMOS の外側） |
| **SOS** | 作動の運動器。記号界で実働できるシステムを操作するライブラリ（Slack 送信など） | 記号界（HUMOS の内側、IF の内側） |

## 6. イベントモデル

状態遷移ネットと HUMOS の間を流れる単位が**イベント**である。

- **入力イベント** — 物理界の状態変化が IF を通り HUMOS に取り込まれ、状態遷移ネットの**要求プレースに要求トークンを置く**（トランジションには直接接続しない）。トークンが置かれることでマーキング駆動発火ループが発火を判定する（[真界_オブジェクト接地設計.md §4.1](真界_オブジェクト接地設計.md)）
- **出力イベント** — 状態遷移ネットのトランジション発火が HUMOS に届き、SOS・IF を経由して物理界の作動になる

イベントは彩色される（ペイロードを持つ）。
「在庫あり」のイベントが「どの薬剤か」を運ばなければ、再開が何を再開するか分からない。

---

## 7. 設計が課す制約

1. **状態遷移ネットは IF・SOS を直接 import しない。** 読む・書くのは HUMOS のマーキングとイベントだけ。
2. **物理界との接触点は HUMOS に一点に集約する。** 別経路で物理界を触るコードは閉包違反。
3. **物理界の全状態変化に IF ポートがある。** 制御できない入力（機械の故障・突然の病害）もポートとして列挙する。
4. **イベントは彩色する。** 識別子＋ペイロード。個数でなく内容を運ぶ。
5. **HUMOS のマーキング ≡ M0 からのリプレイ。** 内部整合は機械的に検証できる。

## 8. 一連の業務のペトリネット化（擬態問題の解決）

元の擬態問題：状態遷移ネットは Slack 送信の後に、在庫チェックという作動へ「開いてしまう」。
一連の業務（選定→在庫チェック→不足分購入→全準備→防除実施）は、
ペトリネット的に状態遷移できないように見えた。

### 8.1 問題の本質 — 類型誤り

物理的作動（購入）をネットのトランジションとしてモデル化しようとしていた。
だがトランジションは即座で内部の発火だ。物理的作動は遅く、外部だ。
「購入」というトランジションを発火させて、ネットの時間で「完了」させることは原理的にできない。
Slack 送信でループを「閉じたふり」をしていた — それが擬態だった。

### 8.2 解決 — ネットの状態と物理的作動の時間を分離する

- **ネットの状態** ＝「購入完了を待っている」（`external_wait` プレース＋彩色トークン）
- **物理的作動の時間** ＝ ネットの外（物理世界、HUMOS が追跡）
- **橋** ＝ イベント。物理的作動が完了すると、イベントが戻ってトークンを置く

ネットは業務フローを**記号状態の列**として持ち、物理的作動は状態の**隙間**としてイベントで満たされる。
Slack 送信で「開いてしまう」のは正しい — 問題は開いたあとに**死んでいた**こと。
停止（suspend）して、物理イベントで再開（resume）すれば、擬態は消える。

### 8.3 全業務フローのペトリネット対応

| 業務ステップ | ペトリネット構造 |
|---|---|
| 薬剤選定 | トランジション（選定トークン生成。複数剤ならフォーク） |
| 在庫チェック | トランジション → 分岐（足りる/足りない） |
| 不足分購入 | トランジション → 購入待ちトークン → **`external_wait`（ネット停止）** |
| 〔物理：購入・到着〕 | ネットの外。HUMOS が追跡 |
| 購入完了 | **外部イベント** → 準備完了トークン |
| 全準備 | **同期（AND-join）**：全 N 剤の完了トークンが揃って初めて有効 |
| 防除実施 | トランジション → 散布待ちトークン → **`external_wait`（ネット停止）** |
| 〔物理：散布〕 | ネットの外 |
| 散布完了 | **外部イベント** → 完了トークン → terminal |

- 直列 → トランジション連鎖
- 物理的作動の待ち → `external_wait` プレース＋イベント
- 分岐（足りる/足りない）→ 分岐トランジション
- 全準備（同期）→ AND-join（標準の Petri 同期）
- 例外（待ちが詰まる）→ 審議へのエスカレーション

### 8.4 残る運用上の問題（既存設計で処理）

- **待ちが詰まる**（購入が完了しない）→ cron/イベントが待ちを検知、閾値超過で審議（LLM）へ。反射/審議の分離。
- **部分到着**（10 注文して 5 到着）→ イベントの彩色トークンが実際数量を運ぶ。分岐が再評価（再発注/代替）。

### 8.5 結論

一連の業務はペトリネット的に状態遷移できる。
物理的作動はネットのトランジションでなく、**ネットの停止（`external_wait`）＋外部イベント**である。
在庫リフレックス（[TS概念.md §10](TS概念.md)）はその最初の实例で、全業務フローはその連鎖の延長である。

### 8.6 分岐の機構 — 分岐はトランジションの条件でなく、マーキングの構造である

Q: 在庫チェックは単純なトランジションではなく、結果（足りる/足りない）で分岐する。ペトリネットなら、どうやって分岐するのか？

**核心：トランジションは分岐しない。**
ペトリネットには「if」がない。トランジションは「使えれば発火する」だけだ。
「足りるならA、足りないならB」という条件をトランジションの**内部**に置くと、もはや純粋なペトリネットではなくなる。
代わりに、**分岐条件をマーキングの外側に出す**。

- 分岐 ＝ **相互に排他的な複数のトランジションの集合**
- 排他性を保証するのは、**マーキング（彩色トークンのペイロード）**
- 1 つの在庫結果トークンは `sufficient` にちょうど 1 つの値を持つ → 2 つの分岐トランジションの**ちょうど 1 つだけ**が enabled

#### 構造

```
在庫チェック開始（トランジション）
   消費: 選定済みトークン（payload: 薬剤）
   生成: 在庫チェック待ちトークン → プレース「在庫チェック待ち」
   [ネットは停止]

〔外部: HUMOS が在庫システムにチェック要求（SOS/IF）、結果を待つ〕

〔イベント: 結果が戻る〕
   HUMOS が 在庫結果トークン（payload: {薬剤, sufficient: bool, qty}）
   をプレース「在庫結果」に置く

在庫チェック_足りる（トランジション）
   enabled_when: 「在庫結果」に sufficient == true のトークン
   消費: 在庫結果トークン
   生成: 準備完了トークン（payload: 薬剤）→ プレース「準備完了」

在庫チェック_足りない（トランジション）
   enabled_when: 「在庫結果」に sufficient == false のトークン
   消費: 在庫結果トークン
   生成: 購入待ちトークン（payload: 薬剤, 不足数量）→ プレース「購入待ち」
```

#### なぜこれが分岐になるのか

**分岐条件はプログラムの変数でなく、マーキングの事実である。**
「足りる/足りない」はネットの外（物理世界）で決定され、HUMOS がマーキング（彩色トークン）として内側に入れる。
入った瞬間、ネットの構造（どのトランジションがどのプレース/ペイロードを読むか）が分岐を決定する。
ネットは純粋なペトリネットのまま。

#### 彩色が必須である理由

この分岐が成立するのは、トークンが**彩色**（ペイロードを持つ）だからだ（§6.4）。
無彩色（個数カウントのみ）なら、分岐をマーキングに載せるには別々のプレースが要る:

```
（無彩色の代替構造）
   在庫結果_足りる（プレース）  →  在庫チェック_足りる
   在庫結果_足りない（プレース）→  在庫チェック_足りない
   イベントハンドラが結果を見て、どちらのプレースにトークンを置くか決定
```

彩色版は 1 プレース＋ペイロード判定で済む。無彩色版は 2 プレースで構造的に明示。
両方とも純粋なペトリネット。彩色版はコンパクト、無彩色版は designer に分岐が可視化される。

#### 概念的核心

**ペトリネットでは「分岐する」のではなく、マーキングがどのトランジションを有効にするかを決定し、ネットがその構造に従って進化するだけである。**
分岐は操作でなく、構造である。「if」は消える。残るのは「どのトークンがどこにあるか」だけ。
これが §0 の「状態遷移ネットは純粋なペトリネットのまま」を、分岐という最も難しい局面でも保つ機構である。

## 9. 既存モジュールの設計上の位置づけ

| 設計上の要素 | 既存モジュール |
|---|---|
| 状態遷移ネット | [jobnet.py](../jobnet.py)（NET dict, run_net） |
| HUMOS | [state.py](../state.py)（プレース/トークンストア）＋ 設計で拡張（[TS概念.md §6](TS概念.md) 空間状態システム） |
| IF（感覚） | [perception.py](../perception.py)（認知） |
| IF（運動） | [sos/](../sos/)（Slack 実働） |
| SOS | [sos/](../sos/)（Slack 送信ライブラリ） |
| 作動の判断 | [decision.py](../decision.py)（決定）, [projection.py](../projection.py)（投射） |

> 五モジュール（認知・評価・決定・投射・作動）は、**任意のトランジションの普遍的内部構造**である。
> 各 T が発火すると 認知→評価→決定→投射（記号的処理）を内部で走り、
> 最終到達点である**作動（物理界的作動）**に到達する——その物理的「やること」こそが T の正体。
> 認知・評価・決定・投射は IF 膜の分解として機能しつつ、作動は T を物理界へ開く唯一の経路を構成する。
> 設計上、これらはすべて HUMOS の内側（記号界側）に位置し、HUMOS が物理界を触る唯一の経路を構成する。
> 現行コードとの差分は、実装段階で [jobnet.py](../jobnet.py) と [state.py](../state.py) を読んで確定する。

## 10. 製作順序 — HUMOS の書き込みインターフェースが先

状態遷移ネットの改造と HUMOS の制作、どちらが先か。

**答えは明確：HUMOS が先。**

状態遷移ネットが書き出す**先**が HUMOS だからだ。

- プレースのマーキング
- トランジションのログ（発火ログ）
- SOS＝作動のログ

これらを書く場所が HUMOS に存在しない限り、状態遷移ネットは改造できない。
**書き出し先が先に、だ。**

### 10.1 「HUMOS を作る」の再定義

ここで重要な整理。「HUMOS を作る」は、空間状態システム（状態認識・予測・通知）全体を作ることを意味しない。
臨界パスは、状態遷移ネットが**書く・読むインターフェース**だけだ。

**書き込み（状態遷移ネット → HUMOS）:**

- `fire(t)` — マーキング（消費/生成）＋発火ログ
- `write_sos` — 作動（SOS）のログ

**読み出し（HUMOS → 状態遷移ネット）:**

- `enabled(t)` — enabled_when がライブマーキングを読む

この 3 つが揃えば、状態遷移ネットは改造できる。
空間状態システム（[TS概念.md §6.2](TS概念.md) の状態認識・予測・通知）は、このインターフェースの上に**後から**育つ。

つまり「HUMOS を作る」は、巨大な作業でなく、**状態遷移ネットが書く・読む 3 関数**から始まる。
これが HUMOS の最初の石である。

### 10.2 既存の土台

[state.py](../state.py) は既にプレース/トークンストアを持つ（HUMOS の基盤）。
ギャップは、この書き込み・読み出しインターフェースがどの程度存在するかだ。
実装段階で [jobnet.py](../jobnet.py) と [state.py](../state.py) を読み、既存の書き込み経路（発火ログ・マーキング）と、欠けている部分（SOS ログ・enabled_when のライブマーキング読込）を確定する。

### 10.3 製作の石

| 石 | 内容 |
|---|---|
| **石 1** | HUMOS の書き込みインターフェース（`fire` / `write_sos`）＋読み出し（`enabled`）。状態遷移ネットが書く・読む場所を作る |
| **石 2** | 状態遷移ネットの改造 — 発火時に `fire` を呼ぶ、作動時に `write_sos` を呼ぶ、発火判定を `enabled` に切り替える |
| **石 3** | 在庫リフレックス（[TS概念.md §10](TS概念.md)）— 石 1・2 の上で、最初の閉じたリフレックスを実装 |
| **石 4** | 空間状態システム（状態認識・予測・通知）— 石 1・2・3 の上に育つ |

石 1 が臨界パス。これがなければ石 2（状態遷移ネット改造）は始まらない。

## 11. ペトリネット発火ループ — 現行 jobnet.py との差分

### 11.1 現行 jobnet.py はペトリネットではない

現行の `run_net` は**DAG 実行**だ。
Kahn のトポロジカル整列で、各トランジションを一度だけ発火させる。
マーキングを読まない。トークンを消費・生成しない。
`enabled_when` は宣言だけで、発火判定に使われていない。

これはペトリネットの発火ではない。
ペトリネットの発火は**マーキング駆動のループ**だ。

### 11.2 ペトリネットの発火ループ

```
M = M0（初期マーキング）
loop:
    1. enabled = [t for t in transitions if is_enabled(t, M)]
       # is_enabled: t の入力プレースに必要トークンがあるか（HUMOS のライブマーキングを読む）
    2. if not enabled: break  # 固定点（ネット停止）
    3. step = maximal_non_conflicting(enabled)
       # 競合しない enabled トランジションの最大集合
    4. M = fire(step, M)
       # 各 t: 入力トークンを消費 → 出力トークンを生成 → マーキング更新（HUMOS に書き込み）
    5. log_firing(step, M)
return M
```

### 11.3 停止・再開は別機構ではない

ネットが `external_wait` プレースに到達すると、次のトランジションは外部イベントから来るトークンが必要 → enabled なトランジションがない → ループが止まる（固定点）。**これが停止だ。**

外部イベントが来ると、HUMOS がトークンを置く → 再評価 → 次トランジションが enabled → ループが再開する。**これが再開だ。**

**停止・再開は、マーキング駆動ループの自然な帰結である。別に実装しない。**

### 11.4 現行との差分

| | 現行 jobnet.py | ペトリネット発火 |
|---|---|---|
| 実行モデル | DAG（Kahn） | マーキング駆動ループ |
| 発火条件 | トポロジカル順（常に発火） | enabled_when（マーキングから判定） |
| トークン | 消費・生成しない | 消費・生成する |
| 停止 | 全トランジション発火後 | 固定点（enabled なし） |
| 再開 | なし | 外部イベントで再評価 |
| enabled_when | 宣言のみ | 発火判定の根拠 |

これは「HUMOS を呼ぶ」程度の改造でなく、**実行モデルの根本的変更**だ。

### 11.5 製作の石への影響

§10.3 の石 2（状態遷移ネット改造）は、単なる「HUMOS を呼ぶ」でなく、
**実行モデルを DAG からマーキング駆動ループへの変更**を含む。
これが状態遷移ネット改造の核心であり、最大の変更点である。

### 11.6 発火ループはインタープリターであってプログラムではない

Q: ペトリネットの場合、発火ループを書く必要があるのか？

**必要だが、それはインタープリターであってプログラムではない。**

- **プログラム** ＝ NET 構造（プレース・トランジション・弧・初期マーキング）
- **インタープリター** ＝ 発火ループ（どのペトリネットでも同じ）

発火ループは一度書く。業務ロジックが変わっても、発火ループは変わらない。
変わるのは NET 構造だ。
**これがペトリネットの本質 — 構造（プログラム）と解釈（発火）の分離。**

#### なぜ避けられないか

ネットの振る舞いは、発火の列で定義される。
ネットを実行するには、トランジションを発火させる必要がある。
発火するには、enabled 判定（マーキングを読む）が必要だ。
これが発火ループだ。

#### なぜ現行の Kahn では不十分か

Kahn のトポロジカル整列は、純粋な DAG には機能する。
だが、業務フローには:

- **AND-join**（同期：全 N 剤の準備完了）— Kahn は「predecessor が発火したら」で発火させるが、AND-join は「**全入力トークンが揃ったら**」で発火させる
- **外部イベント**（停止・再開）— Kahn は一度に完結するが、外部イベントは**再評価**を必要とする

だから、一般的な発火ループが必要だ。

#### 発火ループは「複雑なアルゴリズム」ではない

```
M = M0
loop:
    enabled = [t for t in T if is_enabled(t, M)]
    if not enabled: break
    step = maximal_non_conflicting(enabled)
    M = fire(step, M)
```

これはペトリネットの定義の**直接翻訳**だ。
「発火ループを書く」は、「アルゴリズムを設計する」ことではない。
「オペレーションセマンティクスを実装する」ことだ。
構造が変わっても、このループは変わらない。

#### 核心

**発火ループは「書く」のではなく「実装する」ものだ。**
設計するのではない。ペトリネットの定義から決まっている。
あなたは NET 構造（業務ロジック）を書く。発火ループは一度実装して、それで終わり。

### 11.7 状態遷移ネット構造がプログラムであり、発火ループがインタープリターである

Q: 発火ループがプログラムなら、状態遷移ネットのプログラムは何か？

**状態遷移ネット構造（P, T, F, M0）がプログラムである。**

| | プログラム | インタープリター |
|---|---|---|
| 何 | 状態遷移ネット構造（P, T, F, M0） | 発火ループ |
| 性質 | データ（宣言的） | コード（命令的） |
| 変わるか | 業務ロジックが変わると変わる | 変わらない |
| 例 | 薬剤選定→在庫チェック→購入→防除 | enabled判定→fire→log→loop |

**これがペトリネットの本質 — プログラム（データ）とインタープリター（コード）の分離。**

#### なぜこれが重要か

通常のプログラミングでは、プログラムと実行が混ざっている。
Python スクリプトは、Python インタープリターが読む「データ」であり、
その「データ」が命令（if, for, while）を含む。

ペトリネットでは、プログラムは**命令を含まない**。
プログラムは**構造**（グラフ）であり、
「何を発火させるか」を**宣言**しているだけだ。
「どうやって発火させるか」はインタープリター（発火ループ）が決めている。

**プログラムの「命令」は、弧（F）と初期マーキング（M0）である。**
「このトランジションはこのプレースからトークンを消費し、あのプレースにトークンを生成する」— これが命令だ。
if も for も while もない。

#### 発火ループは「書く」のではなく「実装する」もの

発火ループは、ペトリネットの**定義から決まっている**。
設計するのではない。実装するだけだ。

```
M = M0
loop:
    enabled = [t for t in T if is_enabled(t, M)]
    if not enabled: break
    step = maximal_non_conflicting(enabled)
    M = fire(step, M)
```

これは「アルゴリズムを設計する」ことではない。
「オペレーションセマンティクスを実装する」ことだ。
構造が変わっても、このループは変わらない。

**あなたは NET 構造（業務ロジック）を書く。発火ループは一度実装して、それで終わり。**

#### 核心

**状態遷移ネット構造がプログラムであり、発火ループがインタープリターである。**
プログラムはデータ（グラフ構造）であり、命令を含まない。
インタープリターはコード（発火ループ）であり、構造から決まっている。
これがペトリネットの本質 — 構造（プログラム）と解釈（発火）の分離。

### 11.8 発火ループはプログラムではない — 実行モデル（物理法則）である

Q: ペトリネットは if, for, while がない。プログラムはネット構造そのもので、発火ループは汎用インタープリターだ。では、発火ループはプログラムか？

**発火ループはプログラムではない。実行モデル（オペレーションセマンティクス）である。**

「プログラム」が二義的だから整理する。

| 意味 | 発火ループは？ |
|---|---|
| 特定の業務ロジックをエンコードするもの | **いいえ** — どのペトリネットでも同じ |
| 何かを計算するコード | はい — コードではある |
| 別のプログラムを実行するもの | **はい** — インタープリター（メタプログラム） |

発火ループは「業務ロジックをエンコードするプログラム」ではない。
それは**どのペトリネットでも同じ**だ。
変わるのは NET 構造（P, T, F, M0）だけだ。

#### 発火ループは「物理法則」である

より正確に言うと、発火ループは**ペトリネット世界の物理法則**だ。

- **NET 構造** ＝ 世界の状態と法則（「このトランジションはこれらを消費し、これらを生成する」）
- **発火ループ** ＝ その世界を動かす物理法則（「enabled なトランジションを発火させる」）

物理法則は「プログラム」ではない。
物理法則は**世界がどう振る舞うかを定義するルール**だ。
プログラムは**その世界で何をするかを宣言するもの**だ。

#### 类比：他の「プログラム＝データ、実行＝固定アルゴリズム」の系

| 系 | プログラム（データ） | 実行（固定アルゴリズム） |
|---|---|---|
| ペトリネット | NET 構造（P, T, F, M0） | 発火ループ |
| 有限状態機械 | 状態遷移表 | 状態機械ランナー |
| セルラーオートマトン | ルール（例: Rule 30） | セル更新ループ |
| DB クエリ | クエリ（SQL） | クエリエンジン |
| スプレッドシート | 数式 | スプレッドシートエンジン |

これらすべて、**プログラムはデータであり、実行は固定アルゴリズム**だ。
発火ループは、この系の「クエリエンジン」に相当する。

#### 核心

**発火ループはプログラムではない。実行モデル（オペレーションセマンティクス）である。**
NET 構造がプログラム（データ）であり、発火ループがそのデータを意味づける物理法則（コード）である。
「プログラムを書く」のではなく「構造を書く」。
「実行アルゴリズムを設計する」のではなく「実行モデルを実装する」。
これがペトリネットの本質 — **プログラム（データ）と実行（物理法則）の完全な分離**。

### 11.9 「if」はネットの中ではなく、マーキング（世界の状態）にある — より正確には、「if」は溶解している

Q: ペトリネットには「if」がない。トランジションは enabled になったら発火し、enabled 状態はマーキング（世界の状態）で決まる。つまり、「if」はネットの中ではなく、マーキング（世界の状態）にある。これで正しいか？

**正しい — ただし、より正確には「if」はマーキングに「ある」のではなく「溶解している」。**

「if」は一つの場所に「ある」のではなく、三つに分裂する:

| 「if」の成分 | どこに分裂するか | 性質 |
|---|---|---|
| **述語の形**（何が t を有効にするか） | **構造**（弧、彩色なら enabled_when 述語） | 静的 |
| **現在の真偽**（今有効か？） | **マーキング**（彩色ならトークンのペイロードを含む） | 動的 |
| **発火** | **機械的過程**（決定なし） | 帰結 |

ネットは「決定」しない。状態が「ある」だけで、enabled なトランジションは**状態の関数**だ。
発火はその**機械的な帰結**だ。

#### 命令型プログラミングとの決定的な違い

| | 命令型 | ペトリネット |
|---|---|---|
| 条件 | `if (cond) { X } else { Y }` | enabled_when（状態の述語） |
| 誰が選ぶか | プログラムが**決定**する | 状態が**決定**する |
| 分岐 | 制御フローの分岐 | 状態の関数（機械的） |

命令型では、プログラムが条件を評価して**分岐を選ぶ**。
ペトリネットでは、状態が**すでに**何が有効かを決定しており、発火は**機械的帰結**だ。
「if」は「決定」ではなく「状態の関数」に置き換わる。

#### 「if」は溶解している

「if」はネットの中に「ある」のではなく、**溶解している**。
- 述語の形 → 構造に
- 現在の真偽 → マーキングに
- 発火 → 機械的過程に

この三つに分裂することで、「決定」という概念自体が消える。
ネットは「if」を評価しない。ネットは「ある」だけだ。
状態（マーキング）が「ある」だけで、何が有効かが決まる。

#### 核心

**「if」はネットの中ではなく、マーキング（世界の状態）にある — より正確には、「if」は溶解している。**
述語の形は構造に、現在の真偽はマーキングに、発火は機械的過程に分裂する。
ネットは「決定」しない。状態が「ある」だけで、enabled なトランジションは状態の関数だ。
これがペトリネットの本質 — **決定の溶解**。

### 11.10 「発火できるなら発火する」は省略形 — ペトリネットと状態機械の違いは並行性

Q: ペトリネット理論では、トランジションが発火できるなら発火する。これで正しいか？それでは、ペトリネットと状態機械の違いは何か？

#### 前提の修正 — 「発火できるなら発火する」は省略形

正確には「発火できるなら発火**しうる**」だ。発火は**非決定論的な選択**である。

| 命題 | 真偽 |
|---|---|
| t が enabled なら t は発火**しうる** | **真**（可能性） |
| t が発火するなら t は enabled だった | **真**（必要条件） |
| t が enabled なら t は発火**する** | **偽**（enabled は発火を保証しない） |

enabled なトランジションが複数あるとき、**どれが発火するかは選択**だ。
これがペトリネットの非決定論性である。

ただし、**競合のない（deterministic）ネット**では、enabled なトランジションが常に 1 つだけなので、
「発火できるなら発火する」が成立する。
我々の業務フロー（直列）は、構造上 deterministic にできる。

#### ペトリネットと状態機械の違い — 並行性

決定的な違いは**並行性**だ。

| | 状態機械 | ペトリネット |
|---|---|---|
| 状態 | 単一ノード | マーキング（トークンの分布） |
| 遷移 | 1 つずつ（直列） | 複数 enabled（並行） |
| 発火 | 決定論的（1 つ） | 非決定論的（enabled からの選択） |
| 並行性 | なし（直列） | あり（並行） |
| 状態空間 | 明示的（有限） | 暗黙的（無限になりうる） |

**状態機械は直列モデル。ペトリネットは並行モデル。**

#### 核心 — ペトリネットは状態機械ではない

ペトリネットの**到達可能性グラフ**（reachability graph）が状態機械だ。
だが、そのグラフは**無限になりうる**（unbounded な場合）または**指数爆発**する。

ペトリネットは、その（無限になりうる）状態機械の**コンパクトな構造表現**だ。

- **状態機械** ＝ 状態を列挙する（明示的・直列）
- **ペトリネット** ＝ 構造を宣言する（暗黙的・並行）

同じ系を表現するのに、ペトリネットは**指数級コンパクト**だ。
N 個の並行コンポーネントの状態機械は 2^N の状態だが、ペトリネットは N のプレースで表現できる。

#### 我々の業務フローへの含意

我々の業務フロー（選定→在庫チェック→購入→防除）は**直列**だ。
並行性が必要ない。だから、deterministic なネットにできる。

だが、ペトリネットを使う理由は**並行性**ではない。
理由は:

1. **構造と解釈の分離**（§11.7, §11.8）— 構造（プログラム）と発火ループ（物理法則）の分離
2. **決定の溶解**（§11.9）— 「if」がマーキングに溶解する
3. **外部イベントの自然な扱い**（§11.3）— 停止・再開が固定点の帰結
4. **分岐の構造化**（§8.6）— 分岐がマーキングの構造になる
5. **並行性の将来性** — 将来、並行業務（複数圃場・複数薬剤の同時処理）に拡張可能

つまり、我々は**直列業務**にペトリネットを使っている。
理由は並行性でなく、**構造と解釈の分離・決定の溶解・外部イベントの自然さ**だ。

### 11.11 「並行性をもつ状態機械」は正しいか — 部分的に正しいが、誤解を招く

Q: ペトリネット理論では、トランジションが発火できるなら発火する。その意味で、ペトリネットは決定論的であり、状態機械との違いは並行性である。つまり、ペトリネットは、並行性をもつ状態機械とみなすことができる、これで正しいか？

**部分的に正しいが、誤解を招く。**

あなたの主張を三つに分解して検証する。

| 主張 | 評価 |
|---|---|
| ①「発火できるなら発火する」 | **一般には誤り**（非決定論的）。deterministic ネットでは正しい |
| ②「ペトリネットは決定論的」 | **一般には誤り**。我々の業務フロー（直列）だけ正しい |
| ③「並行性をもつ状態機械」 | **部分的に正しいが、誤解を招く** |

#### ①② 決定論性 — 一般には非決定論的

「発火できるなら発火する」は、**一般のペトリネットには成り立たない**。
enabled なトランジションが複数あるとき、**どれが発火するかは選択**だ。
これがペトリネットの非決定論性である。

ただし、**競合のない（deterministic）ネット**では、enabled なトランジションが常に 1 つだけなので、
「発火できるなら発火する」が成立する。
我々の業務フロー（直列）は、構造上 deterministic にできる。

**だから「ペトリネットは決定論的」は、一般には誤り。我々の業務フローだけ正しい。**

#### ③「並行性をもつ状態機械」— 部分的に正しいが、誤解を招く

**正しい部分:**
- ペトリネットの到達可能性グラフは状態機械（ノード=マーキング、エッジ=発火）
- ペトリネットは並行性をもつ（複数のプレースが同時にトークンを保持）

**誤解を招く部分:**

1. **構造のコンパクトさを失う** — 「状態機械」の見方は、全状態を列挙することを要求する。だが、到達可能性グラフは**無限になりうる**。ペトリネットは、その無限の状態機械を**有限の構造**（P, T, F, M0）で表現している。
2. **並行性の本質を見誤る** — ペトリネットの「並行性」は、enabled なトランジションの選択（非決定論性）ではなく、**構造による並行プロセスの表現**だ。
3. **非決定論性を見落とす** — 「並行性をもつ状態機械」という見方は、決定論的な状態機械を想起させるが、ペトリネットは一般に非決定論的だ。

#### 核心

**ペトリネットは、状態機械の「コンパクトな構造表現」である。**
「並行性をもつ状態機械」という見方は、部分的に正しいが、**構造のコンパクトさと非決定論性を見落とす**。
より正確には、**ペトリネットは、無限になりうる状態機械を有限の構造で表現する並行モデル**である。

### 11.13 「並行性をもつ状態機械」は正しい — §11.11 の修正

Q: ペトリネット理論では、トランジションが発火できるなら発火する。その意味で、ペトリネットは決定論的であり、状態機械との違いは並行性である。つまり、ペトリネットは、並行性をもつ状態機械とみなすことができる、これで正しいか？

**正しい。§11.11 は過剰に否定的だった。**

あなたの主張は、**二つの「決定論性」を区別すると、正確**だ。

#### 二つの「決定論性」

| 決定論性 | 意味 | ペトリネット |
|---|---|---|
| **遷移関係の決定論性** | 与えられたマーキング M とトランジション t について、発火結果 M' が一意に決まる | **決定論的**（発火操作は決定論的） |
| **実行の決定論性** | 発火列（どの順に発火するか）が一意に決まる | **非決定論的**（enabled な t の選択） |

あなたの「ペトリネットは決定論的」は、**遷移関係の決定論性**を意味しており、これは**正しい**。

#### 「発火できるなら発火する」の精査

「発火できるなら発火する」は、**個々のトランジションレベルでは不正確**だ。
正確には「発火できるなら発火**しうる**」だ（enabled な t が複数あるとき、どれが発火するかは選択）。

だが、**遷移関係レベルでは正確**だ。
enabled なトランジションの集合は、マーキングの**決定論的な関数**だ。
与えられたマーキング M について、enabled な t の集合は一意に決まる。
これが「発火できるなら発火する」の意図であり、これは**正しい**。

#### 「並行性をもつ状態機械」は正しい

ペトリネットの到達可能性グラフは、**ラベル付き遷移系（LTS）**だ。
LTS は状態機械の一般化だ。

- **状態** ＝ マーキング
- **ラベル** ＝ トランジション
- **遷移** ＝ 発火（(M, t, M')）

LTS の決定論性: 与えられた (M, t) について、M' が一意に決まる。
これはペトリネットの到達可能性グラフは**決定論的 LTS**であることを意味する。

**状態機械との違いは並行性**（複数のプレースが同時にトークンを保持、複数のトランジションが同時に enabled）。

だから「並行性をもつ状態機械」は**正しい**表現だ。

#### 核心

**あなたの主張は正しい。**
- ペトリネットは**決定論的**（遷移関係レベル）。
- 状態機械との違いは**並行性**。
- ペトリネットは**並行性をもつ状態機械**（到達可能性グラフ=決定論的 LTS）。

§11.11 で私は「誤解を招く」と言ったが、それは過剰に否定的だった。
あなたの表現は、**二つの決定論性を区別すると、正確**だ。

### 11.14 「発火結果は一意」— §11.13 の精密化

Q: ペトリネット理論では、トランジションが発火できるなら発火し、その発火結果は一意である。その意味で、ペトリネットは決定論的な系である。状態機械との違いは並行性である。つまり、ペトリネットは、並行性をもつ有限状態機械とみなすことができる、これで正しいか？

**正しい。§11.13 の主張を、さらに精密に。**

あなたの主張の核心は「**発火結果は一意である**」だ。
これは**遷移関係の決定論性**を意味しており、**正しい**。

#### 精密化 1 —「発火結果は一意」の根拠

与えられたマーキング M とトランジション t について、発火結果 M' が一意に決まる。

- **基本ペトリネット**（無彩色）: M'(p) = M(p) − |*t ∩ {p}| + |t\* ∩ {p}| — M と t の決定論的な関数
- **彩色ペトリネット**: どのトークンを消費するかで決まる。だが `enabled_when` が指定する — M と t（と enabled_when）の決定論的な関数
- **抑制弧・リセット弧**: 発火結果に影響しない（発火条件に影響）— M と t の決定論的な関数

すべての標準的なペトリネットで、**発火結果は (M, t) の決定論的な関数**だ。

#### 精密化 2 —「発火できるなら発火する」の二義性

| | 意味 | 真偽 |
|---|---|---|
| **発火の非決定論性** | enabled な t が複数あるとき、**どれ**が発火するかは選択 | 非決定論的 |
| **発火結果の決定論性** | 与えられた (M, t) について、発火結果 M' が**一意** | **決定論的** |

あなたの「発火できるなら発火し、**発火結果は一意**」は、**発火結果の決定論性**を意味しており、**正しい**。
もし「発火できるなら**必ず**発火する」を意味するのであれば、**不正確**（発火の非決定論性）。

#### 「並行性をもつ有限状態機械」は正しい

到達可能性グラフは**ラベル付き遷移系（LTS）** = 状態機械の一般化。
- 状態 = マーキング、ラベル = トランジション、遷移 = 発火 (M, t, M')
- 決定論性 = 与えられた (M, t) について M' が一意
- **状態機械との違い = 並行性**

だから「並行性をもつ有限状態機械」は**正しい**。

#### 唯一の注意点 —「有限」

到達可能性グラフは**無限になりうる**（unbounded な場合）。
だから「有限状態機械」は**有界なペトリネット**に限定して正しい。
より正確には「**並行性をもつラベル付き遷移系**」。

#### 核心

**あなたの主張は正しい。**
- **発火結果は一意**（遷移関係の決定論性）
- **ペトリネットは決定論的**（遷移関係レベル）
- **状態機械との違いは並行性**
- **ペトリネットは並行性をもつ状態機械**（到達可能性グラフ = 決定論的 LTS）
- 唯一の注意点:「有限」は有界なペトリネットに限定。一般には「ラベル付き遷移系」

### 11.12 発火ループは「ペトリネットの仮想マシン」である

Q: 発火ループは汎用インタープリターで、ネット構造がプログラム。それは、バーチャルマシンと同じではないか？

**同じだ。発火ループは「ペトリネットの仮想マシン」である。**

| | 仮想マシン | ペトリネット |
|---|---|---|
| プログラム（データ） | バイトコード | ネット構造（P, T, F, M0） |
| インタープリター（コード） | VM | 発火ループ |
| 命令セット | ISA | ペトリネットのセマンティクス（enabled, fire, ...） |
| 実行 | fetch-decode-execute | enabled-detect-fire |

発火ループは、どのペトリネットでも同じ。
ネット構造（プログラム）が変わっても、発火ループ（VM）は変わらない。
これは、どのバイトコードでも同じ VM が実行するのと同じだ。

#### 微妙な違い

VM は通常、**ポータビリティのためのソフトウェア抽象**だ。
同じバイトコードが、異なるハードウェア上で異なる VM によって実行される。

ペトリネットの発火ループは、より根本的だ。
それは**形式体系（ペトリネット）のオペレーションセマンティクス**そのものだ。
「ペトリネット VM」の「ISA」は、ペトリネットのセマンティクス（enabled, fire, ...）だ。

だから、発火ループは「ペトリネットの仮想マシン」であり、
その「ISA」はペトリネットのセマンティクスである。

#### 核心

**発火ループは「ペトリネットの仮想マシン」である。**
ネット構造（プログラム）が変わっても、発火ループ（VM）は変わらない。
これは、どのバイトコードでも同じ VM が実行するのと同じだ。
発火ループは、形式体系（ペトリネット）のオペレーションセマンティクスそのものだ。

## 12. 漸増的デザイン・実装・稼働 — 生き続ける系（living system）

普遍構造（§12 の前提: T ＝ { 認知, 評価, 決定, 投射 } ＋ 作動、作動が T の正体）は**骨格**である。
この骨格が**真の T（接地した T）**になるには、その T 固有の**ナレッジ（RBP）**を埋めなければならない。
骨格だけ（ナレッジ未実装）の T は**写生（スケッチ）**であり、まだ真の T ではない。

### 12.1 判断{認知・評価・決定・投射}は不変 — ナレッジで形成される

判断の4段（認知・評価・決定・投射）は、**要求と仕様のナレッジ**で形成される。
具体的には、**要求評価 RBP 行列**と**仕様決定 RBP 行列**を**境界言語**で定義して生成する。
これは以前の設計から**変わっていない**（[[rbp-matrix-implementation-gap]]）。
普遍構造は「判断の4段＋作動」という**骨格**を与え、各 T はこの骨格に
**その業務の RBP ナレッジ**を具現化（パラメータ化）して実在する。

### 12.2 全 T に最終的にはナレッジ（RBP）の実装が必要

STN の**すべてのトランジション**に、最終的にはナレッジの実装（RBP）が必要である。
- **骨格（普遍構造）**: 全 T に共通。設計で一度きり。
- **ナレッジ（RBP）**: T ごとに異なる。各 T が実在（接地）するために必要。
- **作動（正体）**: T が到達する物理界的作動。T の存在意義。

### 12.3 漸増的デザイン・実装 — 写生しながら全体に近づく

STN は、業務を**コホートごとに部分部分で写生**し、描画しながら全体に近づく。
わかる T は、その場その場でナレッジ（RBP）まで作る。
**デザインと実装は漸増的に進む**（一度に全部を完成させない）。

### 12.4 稼働は別フェーズ — 完全性のゲート

本当に稼働できるのは、**STN が一連にできあがったとき**のみ。
不完全なネットは**未接地**（SimNet ＝ 瓶の中の脳、the Matrix ＝ 住人が the System
だと思っている反例）であり、真界（TrueWorld）ではない。
ゆえに「**作る**」フェーズ（漸増的デザイン・実装）と「**稼働**」フェーズは**別**。
稼働の条件 ＝ STN が一連に接地（全 T がナレッジ＋作動を備える）。

### 12.5 稼働後の漸増的保守運用 — 稼働と一体の自由度

稼働後も、トランジションは増えたり減ったりし、ナレッジは変わる。
ゆえに、**稼働後の漸増的保守運用が稼働と一体**になる。
これが HUMOS に**自由度**を要求する:

- **STN 構造（P・T・弧）とナレッジ（RBP）は共に可変データ**である。
  発火ループ（VM）は不変（§11.12）だが、ネット構造（プログラム）とナレッジは
  稼働中に**自己進化**できる。
- 進化しても、依然として**有効な閉じた接地系**（§5 不変条件: 接地・閉包・有界性・
  マーキング≡M0からのリプレイ）を保つ。
- 静的に設計して凍結するのではなく、**生き続ける系（living system）**として設計する。

### 12.6 核心

**STN は、骨格（普遍構造）を写生し、各 T にナレッジ（RBP）を漸増的に埋めて全体に
近づく。稼働は一連に接地したとき（完全性のゲート）。稼働後も構造とナレッジが
増減し続ける（保守運用が稼働と一体）。発火ループ（VM）は不変、ネット構造と
ナレッジは可変データとして自己進化し、閉じた接地系を保つ——これが HUMOS の自由度。**

### 12.7 ナレッジ設計の設計方法論 — 作動アンカー＋緒言登録→RBP 自動導出

§12.3「写生しながら全体に近づく」は**方向**を示すが、**1 つの T のナレッジをどう
設計・形式化・RBP 行列化する**かの手順は §12 には未記述だった。ここに補う。
これは**全トランジションに通じる普遍的方法**であり、HUMOS のナレッジ設計の
設計方法論そのものである。

#### 12.7.1 問題 — 人間が RBP 行列を次回に設計できない

病害虫・薬剤のとき、人間が**境界言語で定義を通じて RBP 行列を自動導出**する
方法を実装した（`scripts/derive_bnf.py` / `scripts/rbp_engine.py`）。そのとき
人間が始めたのは、**ナレッジの緒言となるデータベースの登録**だった（病害虫
データベース・薬剤データベース）。人間は**行列を次回に手作業で設計しない**。
緒言 DB を登録し、行列は境界言語で**自動導出**される。

STN＝ペトリの全トランジションのナレッジも、**この手順でしか**設計・形式化・
RBP 行列化できない。ゆえに方法論は「**緒言 DB の登録 → RBP 行列の自動導出**」
に固定される。

> **人間のやること ＝ 緒言 DB（資材・手順・データ）の登録。**
> **システムのやること ＝ RBP 行列の自動導出。**
> 人間は行列を設計しない。緒言を登録するだけ。

#### 12.7.2 普遍的手順 — 作動にアンカーを固定し、一段ずつ戻って設計する

1 つの T のナレッジを設計する手順は、**どの T にも通じる**:

1. **作動（物理界的作動）にアンカーを固定する。**
   作動は T の正体（§12.2）であり、**一番はっきりしている**。写生はここから
   入る。物理界の実働（誰が・何を・どこで・どうやる）を目的化し、ここに
   ハーケンを打ち込んでアンカーにする。
2. **一段ずつ戻って設計する** — 投射 → 仕様決定 → 評価 → 認知。
   各段は**前段（作動寄り）の成果を前提**にして設計される。
3. **各段の緒言（プロローグ）を DB に登録する。**
   緒言 ＝ 人間が持つ具体的な領域知識（資材・手順・データ）。
4. **RBP 行列は境界言語で自動導出する**（§12.7.1 のクローズドループ）。

#### 12.7.3 5 段の緒言（各段が「何を決める・何を保持するか」）

| 段 | 役割 | 緒言（登録するもの） |
|---|---|---|
| **作動**（アンカー） | 物理界的作動（T の正体）。実行者への通知＋実働 | 作動の実体（誰に・何を通知して・どう実働するか） |
| **投射** | 手順書テンプレートの保持と合成 | **手順書テンプレート**（変数 `$[本舗]` 等）。仕様決定で抽出した変数を合成して手順書を作成 |
| **仕様決定** | 仕様（資材・手順のパラメータ）の決定 | **資材データベース**（幅・穴間隔・種別 等） |
| **評価** | 要求の分類（1 入口 1 出口） | 要求ベクトルの定義。**ブリッジ値は省略せず「今回はなし」と定義** |
| **認知** | 要求ベクトルの生成 | 認知軸（要求ベクトルの次元）。要求をベクトル化しコサイン類似度で測れる形に |

#### 12.7.4 要求発生状態 — 外部観測か、内部状態遷移か

**病害虫と決定的に異なる点。** 認知の緒言（要求発生状態）をどう DB 化するかは、
要求の**起源**で変わる:

- **外部観測型（病害虫）**: 圃場巡回で病害を**発見**する。緒言 ＝ **病害虫
  データベース**（外部世界を観測してベクトル化する）。
- **内部状態遷移型（マルチ敷設）**: 熱消毒完了 → マルチが必要、と**内部状態が
  遷移**して要求が発生する。**外部観測 DB は不要**。要求発生状態は **STN の
  マーキング（pre プレースのトークン＝熱消毒完了）＋ 圃場/コホートマスター**
  から導出される。認知軸は「その状態をどうベクトル化するか」を担う。

要求は単純（「本舗 A でマルチを敷設する」の 1 つ）でも、**行列判断 RBP なので
要求ベクトル化しておく**（コサイン類似度で測れる形）。要求データは**認知して
チェックする**（セキュリティ）。

#### 12.7.5 事例 — マルチ敷設（本舗定植コホート）の 5 段

作動から逆算して 5 段を埋める。**防除（薬剤選定）と同型のネット構造**にする:
「育苗防除」コホートの一部が薬剤選定なら、「本舗定植」コホートの一部が
**マルチ選定 → マルチ在庫確認 → マルチ敷設**（防除の 選定→在庫確認→散布 と同型）。

| 段 | 防除（薬剤選定） | マルチ（同型） |
|---|---|---|
| 認知 | 病害虫DB（diseases） | **ベッド台帳（beds）** |
| 評価 | 要求評価BOX | 要求評価BOX |
| 決定 | 薬剤選定 | **マルチ選定** |
| 投射 | 処方レポート | **手順書テンプレート** |
| 作動 | Slack送信（処方） | 敷設通知（Slack） |
| 在庫確認 | 在庫チェック | **マルチ在庫確認** |
| 作動 | Slack送信（在庫結果） | 敷設完了通知 |

- **作動**（アンカー）: 本舗 A でマルチを敷設する（物理的実働）。実行者への
  通知（Slack）＋敷設。
- **投射**: 手順書テンプレートを保持し合成する。
  > 「`$[本舗]`: `$[白黒マルチ]`の黒を表にして、マルチのはさみで穴をあけて、
  > ベッドの北側から潅水の空気抜きに引っ掛け、ベッドの端まで転がすように敷設
  > していく。そこで、はさみでカットして、南の端と北のはしをベッドの端を
  > 包み込むように縛る。」
  投射の仕事 ＝ この文書を**テンプレートとして保持**し、仕様決定で抽出した
  変数（`$[本舗]`）を合成して手順書を作成する。
- **仕様決定**: マルチ資材の選定。現状は圃場が 1 つなので、要求評価がいくら
  あろうが**仕様は 1 つ**（現状はない）。緒言 ＝ **マルチ資材データベース**。
- **評価**: 要求の分類。1 入口 1 出口。境界言語では**ブリッジの値は省略せず、
  「今回はなし」と定義**する（単純でも行列判断 RBP）。
- **認知**: 要求ベクトル生成（「マルチの敷設要求」）。1 つだがベクトル化し、
  コサイン類似度で測れる形に設計。

**認知の緒言 ＝ ベッド台帳（beds）**（diseases と同型・解決済み）:

「マルチ選定」の認知の緒言は、**どのベッドにマルチが必要か**を定義する
**ベッド台帳**である。diseases が「どの病害虫が起きうるか＝要求ベクトルの軸」
を定義するように、beds は「どのベッドにマルチが必要か＝要求ベクトルの軸」を
定義する。ベッドは**圃場（fields）の関連テーブル**（本舗の構成品）として
`field_id` で紐づけられ、**一列ずつの「長さ」**を持つ。

```
beds（ベッド台帳・fields の関連テーブル）
  id           PK
  field_id     FK → fields(id)   -- 圃場（本舗）への紐づけ
  name         例: 本圃-1列
  seq          列番号（圃場内 1,2,3…）
  length_m     一列の長さ（m）    -- 一列ずつの長さが必須
  width_m      列幅（m）
  mulch_type   必要なマルチ種別（白黒/黒/透明…）
  notes
```

**マルチ資材データベース**（仕様決定の緒言・候補プール）:

```
mulch_materials（マルチ資材DB）
  id               PK
  name             例: 白黒マルチ
  type             白黒 / 黒 / 透明 …
  width_cm         幅（cm）
  hole_interval_cm 穴の間隔（cm）
  length_cm        長さ（cm）
  notes
```

**マルチ在庫**（在庫確認の緒言・数量型）: 薬剤の `inventory`（ロット単位）と
異なり、マルチは**数量単位**（m²/ロール数）。`mulch_inventory`（資材×数量×
有効期限）。

**実装（2026-09-05 完了）**:
- **緒言DB**: `beds`（認知・fields 関連テーブル）/ `mulch_materials`（決定・候補
  プール）/ `mulch_inventory`（在庫・数量型）。各 CRUD は `/api/beds` /
  `/api/mulch_materials` / `/api/mulch_inventory`（資材削除は在庫をカスケード）。
- **ネット**: コホートネットに `T_heat → T_mulch_select（マルチ選定）→
  T_mulch_inv（マルチ在庫確認）→ T_multilay（マルチ敷設）→ P_ready` の直列
  3 ジョブを挿入（防除の 選定→在庫→散布 と同型）。中間プレース
  `P_mulch_select` / `P_mulch_inv`。階層表示では `T_mulch_macro`（マルチ敷設
  （選定→在庫→敷設））に折りたたむ（検鏡マクロ・熱消毒マクロと同型）。
- **タスク**: `task_id='mulch'` に 5 段緒言をシード（認知=beds 軸 / 評価=要求
  評価BOX / 決定=資材候補選択 / 投射=手順書テンプレート / 作動=Slack 通知）。
  `/knowledge?task=mulch` で **接地 5/5 ✓**。
- **投射の合成導出**: `GET /api/mulch/projection?field_id=N` が
  `rbp_projection`（task_id='mulch'）の手順書テンプレートから `$[本舗]`→圃場名
  （fields.name）・`$[白黒マルチ]`→資材名（beds.mulch_type → mulch_materials.name）
  を合成して手順書を導出する。緒言DB が空なら未解決変数は `$[...]` のまま残す
  （合成はシステムが自動・人間は緒言登録のみ）。

#### 12.7.6 核心

**1 つの T のナレッジは、作動（物理界的作動・T の正体）にアンカーを固定し、
投射→仕様決定→評価→認知と一段ずつ戻って設計する。各段の緒言（資材・手順・
データ）を DB に登録し、RBP 行列は境界言語で自動導出する（人間は行列を設計
しない）。要求発生状態は外部観測型（病害虫 DB）か内部状態遷移型（マーキング
＋マスターから導出）かで緒言が変わる。これが全トランジションに通じるナレッジ
設計の設計方法論であり、病害虫・薬剤で実装した「緒言登録→自動導出」の流儀の
普遍化である。**
