## 2. 核心的なギャップ（TW が閉じた系になっていない理由）

> 石1・石2・石3 でギャップ 1・2・3 は解消（HUMOS 実在、マーキング駆動発火ループ稼働、
> 在庫リフレックス閉鎖）。残るは SSS（石4）・IF（石5）による両界への開き。

1. ~~**HUMOS が無い**~~ → ✅ **解消（石1）**: `humos.py` がマーキング・発火ログ・SOS作動ログを保持。
2. ~~**能動ゲートになっていない**~~ → ✅ **解消（石2）**: `run_net` がマーキング駆動
   （M0 → enabled_when 判定 → 固定点で停止 → fire → loop）。`enabled_when` が発火判定の根拠に。
   停止・再開は固定点の帰結として機構化（external_wait プレース追加は石3）。
3. ~~**在庫リフレックスが閉じていない**~~ → ✅ **解消（石3）**: Slack送信処方（T_rx_exec）が
   完了すると `sos/slack.py` が `humos.write_sos` で記録し、HUMOS が状態判断して
   `humos.place_token` で在庫プレースに処方トークンを置く。`run_net` のループ先頭が
   ライブマーキングを再読して発見し、在庫チェック（T_inventory）が自動発火する。
   設計 §4.3 の「作動完了が状態である」が**最初の閉じたリフレックス**として実装。
   同期モデルでは一連で走り、非同期化（Slack コールバック/人的確認）しても
   コード変更なしで実際に停止・再開する（§11.3）。

## 3. 実装の順番（石）

設計書 [TS設計.md §10.3](TS設計.md) の石を、現行コードの差分に合わせて具体化する。
**石1 が臨界パス** — これが無いと石2・石3 は始まらない。

### 石 1 — HUMOS の書き込み・読み出しインターフェース（臨界パス）✅ 実装済み（2026-08-29）

`humos.py` を新設し、[state.py](../state.py) の `_tokens_store`（シングルトン）を HUMOS 配下に昇格。
**3 関数だけ**作る。

```
書き込み（STN → HUMOS）
  fire(transition, consumed, generated)   # マーキング更新 ＋ 発火ログ
  write_sos(action, result)               # 作動ログ（Slack送信した etc.）

読み出し（HUMOS → STN）
  enabled(transition) -> bool             # enabled_when をライブマーキングで判定
```

- 既存の `state.py`（プレース/トークンストア）が HUMOS のマーキングストアの**種**。
- この 3 関数が揃えば、石2（STN 改造）が可能になる。
- 空間状態システム（SSS）は**後から育つ**（石4）。

### 石 2 — STN の改造（マーキング駆動発火ループ）✅ 実装済み（2026-08-29）

`jobnet.run_net` を DAG 実行（Kahn トポロジカル＋エッジ DFS）から**マーキング駆動発火ループ**に変更（[TS設計.md §11](TS設計.md)）。

- **M0 構築**: 前段トークン（`store="humos"` の field_type/pest_matrix）を HUMOS から seed ＋
  後段トークン（`store="chatstate"`）を None にクリア（run() のプレースホルダ `vector=[0]*10` を
  「未生成」に戻す → 各 T は入力トークンを生成した直後に初めて enabled）。
- **ループ**: `M = M0 → enabled 判定（enabled_when をライブマーキングで）→ 固定点で停止 →
  maximal non-conflicting step → fire（humos.fire）→ fired 更新 → loop`。
- **分岐**（T_decision → T_projection / T_rx_exec）: 両方が同じ prescription を読むが、
  handler は state を変換しトークンをハード消費しないため競合しない → 同一ステップで両方発火（§8.6）。
  （石3 で T_projection2 は T_rx_exec に置き換え。）
- **冪等**: `fired` 集合で各 T は 1 実行につき 1 回のみ発火（循環ネットでも無限ループしない）。
- **停止・再開は別機構でなく**、マーキング駆動ループの自然な帰結
  （`external_wait` 到達 → enabled なし → 固定点 = 停止、外部イベントでトークン → 再評価 → 再開）。
  external_wait プレースの**追加**は石3。
- `NET["edges"]` は実行トポロジーではなくなった（視覚化・構造検証のみ）。
- 検証: スタブ 13/13・本物 handler 10/10・既存テスト 77/77（test_14 意図分類含む）パス。

### 石 3 — 在庫リフレックス（最初の接地）✅ 実装済み（2026-08-30）

設計 §4.3 のループを閉じた（**最初の閉じたリフレックス**）。

- **フロー**: 処方決定 → **Slack送信処方（T_rx_exec・作動）** → 送信完了が HUMOS の状態に
  → 在庫チェック（T_inventory）自動発火 → Slack送信在庫結果（T_inventory_exec・終端）。
  T_projection2（投射2・在庫トークン生成）は T_rx_exec に置き換え。
- **作動完了が状態である（§4.3）の 3 段**:
  1. 記録 — `sos/slack.py` の `send_message` が `humos.write_sos("slack_send", result)`
  2. 状態判断 — 送信成功か・処方が空でないか（`rx_exec_node`）
  3. 次トークンを置く — `humos.place_token("inventory_token", 処方JSON, "T_rx_exec")`
- **間接的開き**: ネットは inventory_token を handler の返り値では持たない。
  `run_net` のループ先頭が**ライブマーキングを再読**して発見し、T_inventory が発火する。
  `place_token` は発火ログに直接追記せず、ループが handler 発火前後のマーキング差分で
  トリガーしたトランジション（T_rx_exec）の生成トークンとして記録（発火ログ 1 トランジション
  = 1 エントリを維持、リプレイ整合 §7.5）。
- **external_wait プレース**（P_external_wait・store=humos）＋ 彩色トークン
  （`{"sent": true/false}`）で「ネットの状態」と「物理的作動の時間」を分離（§8.2）。
- **ストールトークン防止**: `humos.clear_transient_tokens()` を run_net 開始時に呼び、
  前走の出力トークン（inventory_token 等）をマーキングから消す（2 走目で T_inventory が
  前走の処方で先発火するのを防ぐ）。発火ログ・作動ログも実行単位でクリア。
- **送信失敗**: 在庫トークンを置かない → T_inventory 未発火 → 固定点で停止
  （§8.4「待ちが詰まる→審議へエスカレーション」の足場）。
- **停止・再開**: 同期モデルでは Slack が即完了するため一連で走る。非同期化
  （Slack コールバック/人的確認）してもコード変更なしで実際に停止・再開する（§11.3）。
- **併せて修正**: `humos.replay_marking()` が M0 を `_TOKEN_KEYS` の現在値から開始
  （従来 None で開始し、set_token で置いた前段トークンを復元せず replay_ok が常に False）。
- 検証: スタブ 21/21・本物 handler 12/12・既存テスト 77/77 パス。
  `/api/net`（T_rx_exec・P_external_wait 反映）・`/api/humos`（replay_ok=True）確認。

### 石 4 — 空間状態システム（SSS）

石1〜3 で HUMOS に流れ込む書き込みを、**空間状態として認識・予測・通知**する層。

- 一般システム理論で「系全体の振る舞い」として状態を捉える。
- 認知スコープを STN 外（物理界の実働＝オペレータ）へ拡張。
- メタ認知（自資源状態＝在庫を空間状態の一部として認識）。

### 石 5 — IF（膜・ポート）の明示化

- 物理界との接触点を HUMOS に一点集約する制約（[TS設計.md §7](TS設計.md)）をコードで担保。
- IF 契約（種別 K のトークンをプレース P に制約 C で返す宣言）をポートとして列挙。
- 制御できない入力（機械の故障・突然の病害）もポートとして列挙（閉包）。
