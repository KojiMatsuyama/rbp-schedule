## 0. 方法と結論

**方法** — 設計文書（トップダウン）ではなく、実コードを読み上げ、
各概念が「どう実在するか」を特定し、トップ哲学と突き合わせる。
「設計に書いてあるがコードに無い」「コードにあるが設計の意図と違う」を個所ごとに挙げる。

**結論（一言）** —

> **実装は「ペトリネット構造を持つ一発バッチパイプライン」であり、
> 「持続する閉じた接地系」ではない。**

骨格（STN 構造・発火ループ・RBP・SOS・PLAN・リプレイ整合・能動ゲート・接地ゲート）は
**正しい**。問題は 2 種類に分類できる（§2 の骨子）:

- **真の不整合** — 実装が設計と**矛盾**している（既存コードが設計に反して動く）。
  G4（cron がネットをバイパス）・G5（4 記号段が HUMOS に書き込まない）・
  G6（cron で 4 元素の原子性が壊れる）・G10（審議エスカレーションなし）・
  G11（ネット構造が可変でない）。
- **未実装（石4 SSS・石5 IF）** — 設計が**指定していて、まだ作っていない**もの
  （将来作業）。G1（入力流が閉じていない）・G2（接地が同期限定）・
  G3（停止・再開がバッチ帰結）・G7（SSS 未実装）・G8（IF 未実装）。
  これらは「矛盾」でなく「未到達」で、石4（SSS）・石5（IF）で埋める。

この区別が監査の骨子である。3 つの軸への集中は変わらない:

1. **系が閉じるか否か** — 物理界が記号界へ還る経路（IF 感覚）が未配線
   （G1/G2/G3/G8＝未実装・石5 IF）。
2. **一つのネットか否か** — 実行経路が 2 系統（G4＝真の不整合）。
3. **4 元素が状態空間に痕跡を残すか否か** — 認知・評価・決定・投射は
   HUMOS に書き込まない（G5/G6＝真の不整合）。

## 1. 現実装の全体像（ボトムアップ）

### 1.1 共有 OS コア `humos_os`（pip パッケージ・venv 個別インストール）

ドメイン無依の共有 OS。STB・DC が同一の v1.0.0 を各自の venv に持つ。

| モジュール | 行数 | 実体 |
|---|---|---|
| `schema.py` | 90 | 5 テーブル DDL（place / token / marking / firing / writing） |
| `humos.py` | 451 | 状態空間ストア。`fire` / `write_sos` / `place_token` / `enabled` / `place_external_token` / `write_log` / `replay_marking` / `verify_replay` / `clear_transient` |
| `stn.py` | 180 | 発火ループ `run_net`（マーキング駆動・**バッチ**・固定点まで走りきる） |
| `plan.py` | 373 | PLAN レイヤー（`schedule_def` / `expected_state_at` / 逸脱判定） |

> **`sss.py` も `if.py` も存在しない。**
> 骨子の 5 機構（SSS / STN / RBP / SOS / IF）のうち、OS コアに実在するのは
> **STN（stn.py）と PLAN（plan.py）**、および状態空間ストア（humos.py）だけ。

### 1.2 STB ラッパー

| ファイル | 実体 |
|---|---|
| `humos.py`（331） | `humos_os.humos` への薄シム（net_id="stb"・`_TOKEN_KEYS={field_type, pest_matrix}`） |
| `jobnet.py`（508） | `NET` dict（P 10・T 8）＋ `run_net`（`stn.run_net` へ委譲）＋ `net_to_json` / `net_firing` / `net_runnability` |
| `state.py`（94） | `humos` への純再エクスポート・シム ＋ `state_node` |
| `agentic_chat/nodes.py` | 薄アダプタ（perception / evaluation / decision / projection / rx_exec / inventory） |
| `agentic_chat/__init__.py` | `run()` 入口 → `jobnet.run_net(state)` |
| `sos/slack.py` | `send_message` → `humos.write_sos("slack_send", result)` |
| `server.py` | HTTP（`/api/net`・`/api/operations/*`・`/api/chat`）＋ cron 経路（`_handle_spray_schedule_generate`） |

### 1.3 実行経路は 2 系統（最重要の構造的事実）

同じ業務（処方）が、**ネットを通過する経路**と**ネットをバイパスする経路**の 2 つで走る。

| | チャット経路 | cron 経路（防除暦自動処方） |
|---|---|---|
| 入口 | `POST /api/chat` → `agentic_chat.run`（[server.py:3591](../server.py#L3591)） | `_handle_spray_schedule_generate`（[server.py:5001](../server.py#L5001)） |
| 認知 | `T_perception`（ネットの T） | `_run_perception_check`（perception を**直接**呼びゲート判定） |
| 評価・決定 | `T_evaluation` → `T_decision`（ネットの T） | `api.prescribe(vector)` **1 呼び出しで圧縮**（[rx_prescribe.py:185](../scripts/rx_prescribe.py#L185)） |
| 投射 | `T_projection`（ネットの T） | `projection.build_slack_text`（**直接**呼び） |
| 作動 | `T_rx_exec` → `sos.slack.send_message` | `sos.slack.send_message`（**直接**呼び） |
| 在庫 | `T_inventory` → `T_inventory_exec`（ネットの T） | なし |
| **STN を通過するか** | ✅ 全 T 通過・発火ログ記録 | ❌ **STN をバイパス**（`run_net` を呼ばない） |
| HUMOS への痕跡 | marking ＋ firing（全 T）＋ writing（sos） | marking（set_token）＋ writing（sos）のみ。**firing なし** |

cron 経路は `set_token`（marking 書き込み）と `sos.slack.send_message`（writing 書き込み）
で HUMOS に触るが、`run_net` を呼ばないため **firing ログに一切現れない**。
つまり同じ処方でも、チャット経由なら発火履歴に全 T が残り、cron 経由なら
「2 トークンの投入＋Slack 送信」の痕跡だけが残る。

## 2. 不整合の整理

各項目は **設計の主張 → 現実装 → 不整合 → 重み → 分類** で記す。
重み: **高**＝本質・不変条件に関わる／**中**＝機構の実在に関わる／**低**＝運用・拡張性に関わる。
分類: **真の不整合**＝実装が設計と矛盾／**未実装（石4 SSS・石5 IF）**＝設計が指定し未到達。

### 骨子 — 真の不整合 vs 未実装

| # | 項目 | 重み | 分類 |
|---|---|---|---|
| G1 | 入力流（感覚）が閉じていない | 高 | **未実装（石5 IF）** |
| G2 | 接地が同期チャット経路に限定 | 高 | **未実装（石5 IF）** |
| G3 | 停止・再開が「ループの帰結」でない | 高 | **未実装（石5 IF）** |
| G4 | 実行経路が 2 系統（cron が STN をバイパス） | 高 | **真の不整合** |
| G5 | 4 記号段が HUMOS に書き込まない | 高 | **真の不整合** |
| G6 | cron 経路で 4 元素の原子性が壊れる | 中 | **真の不整合** |
| G7 | SSS（空間状態システム）未実装 | 高 | **未実装（石4 SSS）** |
| G8 | IF（膜・ポート）未実装 | 高 | **未実装（石5 IF）** |
| G9 | 3 柱の片寄り | 中 | 混合（G3 未実装＋G7 未実装） |
| G10 | 審議へのエスカレーション機構なし | 中 | **真の不整合**（既存ネットの拡張） |
| G11 | ネット構造が可変データでない | 低 | **真の不整合**（既存ネットの拡張） |

> **真の不整合**は G4・G5・G6・G10・G11 に絞られる。G4/G5/G6 は「既存コードが
> 設計に反して動いている」（cron がネットをバイパスし、4 元素が書き込まない）。
> G10/G11 は「既存ネットに設計が要求する構造が無い」（審議 T・可変構造）。
> **未実装**は G1/G2/G3/G7/G8 で、石4（SSS）・石5（IF）で埋める将来作業。
> IF の具体（ポート表・配線パターン・増分原則）は石5 の設計書
> [真界_IF設計.md](真界_IF設計.md) に分離した。

### 第 1 群 — 系の閉じ方（本質・二つの流・接地）

#### G1. 入力流（感覚）が閉じていない — 重み: **高** ｜ 分類: **未実装（石5 IF）**

- **設計**: 本質＝「記号界と物理界が**相互に**開かれた状態系」（§1.1）。
  入力流（感覚）＝`物理界 → IF → HUMOS → STN`（§5）。
  物理界の全状態変化に IF ポートがある（不変条件 4）。
- **現実装**: IF 感覚ポートの実体は `humos_os.humos.place_external_token`
  （[humos.py:305](../.venv/lib/python3.10/site-packages/humos_os/humos.py#L305)）のみ。
  **呼び出し元は 0 件**（全ソース grep）。
  物理界から HUMOS へ還るトークンは、どこからも置かれない。
- **問題（未実装）**: 系は**片方向（記号→物理＝Slack 送信）にだけ開いて**いる。
  「相互に開かれた状態系」の**入力側が未実装**。物理界の実働完了が
  記号界へ還る経路が存在しない。設計が指定し、まだ作っていない（石5 IF）。
- **影響**: 「Slack 送信した**のち**」が、同期チャット経路では Slack が
  プロセス内で即完了するため**見かけ上**閉じるが、非同期（人的確認・
  コールバック）では閉じない。本質の「相互開き」が構造的に担保されていない。
- **処方**: 石5 の設計書 [真界_IF設計.md](真界_IF設計.md) §2.2（非同期クローズ）。
  在庫結果の帰還（IF#3）を物理オペレータから `place_external_token` で還す配線。

#### G2. 接地が同期チャット経路に限定 — 重み: **高** ｜ 分類: **未実装（石5 IF）**

- **設計**: 接地＝物理界を「空間状態を変える**オペレータ**」として SSS に認知
  （§3.6）。書き込みスコープに `physical_operator` が含まれる
  （[TS概念.md §6.1](TS概念.md)）。
- **現実装**: `write_sos` の `operator_kind` は `"sos"` のみ。
  `physical_operator` としての書き込みは存在しない。
  在庫リフレックス（石 3）は `rx_exec_node` が `humos.place_token`
  （[nodes.py:281](../agentic_chat/nodes.py#L281)）で在庫トークンを置くが、
  これは**ネット内部の handler が同期で置く**もので、物理界のオペレータが
  外部から還すものではない。
- **問題（未実装）**: 「物理界＝オペレータとして認知」が構造的に無い。
  接地は「Slack が即完了する同期チャット経路」に限定され、
  物理界の時間（人が倉庫を覗く・機械が壊れる）を認知する機構がない。
  設計が指定し、まだ作っていない（石5 IF・接地）。
- **処方**: 石5 の設計書 [真界_IF設計.md](真界_IF設計.md) §5（物理界＝オペレータ）。
  物理界の実働を `physical_operator` として `write_log` に載せ、SSS が認知する。

#### G3. 停止・再開が「ループの帰結」でない — 重み: **高** ｜ 分類: **未実装（石5 IF）**

- **設計**: 停止・再開は**マーキング駆動ループの自然な帰結**であり、
  別機構でなく、`external_wait` 到達で固定点（停止）、外部イベントで再開（§5）。
  「常態は反射で再開し、例外のみ審議にエスカレート」（§1.2）。
- **現実装**: `stn.run_net` は `while True` で**固定点まで一気に走りきる一発バッチ**
  （[stn.py:122](../.venv/lib/python3.10/site-packages/humos_os/stn.py#L122)）。
  ネットを背景で持続させるループ・スレッドは存在しない（`Thread(target` なし）。
  「停止」＝バッチが return する、「再開」＝**新しい** `run_net` 呼び出し
  （新しいチャット or 新しい cron）。
- **問題（未実装）**: 設計の「ループが持続し、外部イベントで再開する」は未実装。
  実在するのは「一発のバッチが、Slack が同期で完了するためたまたま
  リフレックスを完遂する」もの。`P_external_wait` は存在するが、
  **それを非同期で待つ主体がいない**。設計が指定し、まだ作っていない
  （石5 IF・非同期クローズ）。
- **影響**: 非同期化（Slack コールバック・人的確認・天候待ち）すると、
  停止したネットを再開する経路が無い。設計 §11.3 の停止・再開は
  「同期バッチの帰結」としてのみ成立している。
- **処方**: 石5 の設計書 [真界_IF設計.md](真界_IF設計.md) §2.2（非同期クローズ）。
  ネットを**持続させる主体**（イベント駆動ループ or 非同期再開）を置き、
  `P_external_wait` を非同期で待ち、外部イベントで再開。

### 第 2 群 — 一つのネット（不変条件・閉包）

#### G4. 実行経路が 2 系統（cron が STN をバイパス）— 重み: **高** ｜ 分類: **真の不整合**

- **設計**: 「**物理は複数、記号ネットは一つ**」（[TS概念.md §9.1](TS概念.md)）。
  物理界との接触点は HUMOS に**一点に集約**（不変条件 3）。
  別経路で物理界を触るコードは**閉包違反**。
- **現実装**: §1.3 の通り、チャット経路（ネット経由）と cron 経路
  （`rx_prescribe.process_row` が perception / api.prescribe / projection /
  sos.slack を**直接**呼び、[server.py:5028](../server.py#L5028)）が併存。
- **不整合**: 同一業務が 2 つの経路で走り、cron 経路はネットをバイパスして
  物理界（Slack）に触る。**不変条件 3（接触点の一点集約）と閉包に違反**。
  「一つのネット」が構造的に保たれていない。
- **影響**: 発火履歴（firing）に cron 処方が出ない（§1.3）。
  運航管理センターのタイムライン・AI 解読層が cron 由来の業務を
  「ネットの発火」として見られない。同じ処方が 2 種類の痕跡で残る。
- **処方**: cron 経路も**ネット経由**に統一（`run_net` を呼ぶ）。
  評価・決定・投射を T として発火させ、firing に残す。接触点を HUMOS に一点集約。

#### G5. 4 記号段が HUMOS に書き込まない — 重み: **高** ｜ 分類: **真の不整合**

- **設計**: 書き込みスコープに**認知・評価・決定・投射のログ**が含まれる
  （[TS概念.md §6.1](TS概念.md)）。これらは「空間状態の生データ」であり
  SSS の認知対象（`humos_os.humos.write_log` の `operator_kind` に
  perception / evaluation / decision / projection が想定される）。
- **現実装**: `perception.py` / `evaluation.py` / `decision.py` / `projection.py`
  は `humos` を **0 回** import（grep 確認）。4 記号段は HUMOS に**一切書き込まない**。
  HUMOS に書き込むのは**作動（SOS）のみ**（`sos/slack.py` の `write_sos`）。
- **不整合**: 深層の核心（トラスト形成＝認知→評価→決定→投射の 4 元素）が
  **状態空間に痕跡を残さない**。4 元素は「判断エンジン」だが、
  その判断の過程が HUMOS（土壌）に乗らない。
- **影響**: SSS が「4 元素の判断」を空間状態として認識・予測・通知できない
  （G7 と連鎖）。`write_log` 関数は存在するが、4 段から呼ばれていない。
- **処方**: 認知・評価・決定・投射が `humos.write_log`（operator_kind 各段）に
  **判断の痕跡を書く**。4 元素を状態空間に乗せる。既存の `write_log` を使うだけで揃う。

#### G6. cron 経路で 4 元素の原子性が壊れる — 重み: **中** ｜ 分類: **真の不整合**

- **設計**: 4 元素は**原子化**された 4 段（認知→評価→決定→投射）。
  各 T はこの普遍構造を具現化（§3.2）。
- **現実装**: cron 経路は評価＋決定を `api.prescribe(vector)` **1 呼び出し**に
  圧縮（[rx_prescribe.py:185](../scripts/rx_prescribe.py#L185)）。
  評価と決定が別段として分離・記録されない。
- **不整合**: 4 元素の「原子化」が cron 経路で保たれていない。
  チャット経路では 4 T が別々に発火・記録されるが、cron 経路では
  評価・決定が 1 段に融合する。
- **処方**: G4 に従い、cron も 4 段を別 T で発火（`api.prescribe` の
  1 呼び出し圧縮を T 分解に置き換え）。

### 第 3 群 — 機構の実在（SSS・IF）

#### G7. SSS（空間状態システム）未実装 — 重み: **高** ｜ 分類: **未実装（石4 SSS）**

- **設計**: SSS＝HUMOS の本質。書き込みを空間状態として**認識・予測・通知**
  （§3.1）。状態予測はカルマンフィルタ（予定）。
  OS の 3 柱の「**状態**」の柱（§1.4）。
- **現実装**: `humos_os` に SSS モジュールは**無い**。
  `humos.py` は書き込み（firing / writing）を**生データとして記録するストア**に留まる。
  「認識・予測・通知」の層は存在しない。
- **問題（未実装）**: 3 柱のうち「状態」の柱が欠如。書き込みは溜まるが、
  系全体の振る舞いとして認識・予測・通知されない。
  （PLAN は「期待状態」の柱であり、SSS の「実状態の認識・予測」ではない。）
  設計が指定し、まだ作っていない（石4 SSS）。
- **処方**: 書き込み集合を**空間状態として認識・予測・通知**する層（石4）を実装。
  3 柱の「状態」を補う。

#### G8. IF（膜・ポート）未実装 — 重み: **高** ｜ 分類: **未実装（石5 IF）**

- **設計**: IF＝膜。感覚・運動。**IF 契約**（種別 K のトークンをプレース P に
  制約 C で返す宣言）をポートとして列挙（§3.5）。
- **現実装**: IF 層・ポート宣言は**無い**。
  実在するのは `place_external_token`（関数）のみで、**未配線**（G1）。
  「宣言・アダプタ」の形（IF 契約）は存在しない。
- **問題（未実装）**: 膜が「宣言されたポートの集合」ではなく、
  未使用の関数 1 個に留まる。不変条件 4（全状態変化にポート）を満たさない。
  設計が指定し、まだ作っていない（石5 IF）。
- **処方**: IF 契約（種別 K・プレース P・制約 C）を**ポートとして宣言・列挙**
  （石5）。制御不能入力もポート化。具体（ポート表・配線パターン・増分原則）は
  石5 の設計書 [真界_IF設計.md](真界_IF設計.md)。

### 第 4 群 — OS である所以（3 柱）

#### G9. 3 柱の片寄り — 重み: **中** ｜ 分類: 混合（G3 未実装＋G7 未実装）

- **設計**: 不変のエンジンは 3 柱（§1.4）—
  **実行**（発火ループ / VM）・**状態**（SSS）・**運用**（PLAN）。
- **現実装**:
  - **実行**（VM）— 実在（`stn.run_net`）だが**バッチ**（G3）。
  - **状態**（SSS）— **欠如**（G7）。
  - **運用**（PLAN）— **実在**（`plan.py`・`/api/operations/*`・`operations.html`）。
- **問題**: 3 柱のうち 1 柱（PLAN）が堅牢、1 柱（実行）が部分的、
  1 柱（状態）が欠如。「不変の 3 柱」がまだ揃っていない。
- **処方**: G3（実行を持続化・石5 IF）＋ G7（状態＝SSS・石4）で 3 柱を揃える。

### 第 5 群 — 判断の二速度（反射／審議）

#### G10. 審議へのエスカレーション機構なし — 重み: **中** ｜ 分類: **真の不整合**（既存ネットの拡張）

- **設計**: 常態の帰還（在手・天気 OK・散布完了）は**反射**で再開、
  例外の帰還（欠品・天不良・突然の病害）だけ**審議**にエスカレート（§1.2）。
- **現実装**: 在庫チェック（`T_inventory` / `T_inventory_exec`）は
  結果を Slack に送るのみ。**「欠品 → 審議（LLM・代替剤選定）へ分岐」する
  機構が無い**。`enabled_when` の宣言的発火（反射）は実在するが、
  審議へのエスカレーション経路はネットに無い。
- **不整合**: 「反射／審議」の線が**反射側のみ**実装。
  例外を審議（高価な中央経路）に回す分岐が構造的に無い。
- **処方**: 例外（欠品・天不良）を検知し**審議（中央経路）へ分岐**する T を
  ネットに置く。反射／審議の線を完成。IF の非制御入力（P6/P7/P8）の帰先
  （[真界_IF設計.md](真界_IF設計.md) §2.3）。

### 第 6 群 — 漸増的ライフサイクル（living system）

#### G11. ネット構造が可変データでない — 重み: **低** ｜ 分類: **真の不整合**（既存ネットの拡張）

- **設計**: STN 構造（P・T・弧）とナレッジ（RBP）は**共に可変データ**として
  自己進化し、発火ループ（VM）は不変（§7）。
- **現実装**: ナレッジ（RBP）は DB 駆動で可変（`rbp_*` テーブル・`/knowledge`）。
  一方、**ネット構造（P・T・弧）は `jobnet.py` の `NET` dict にハードコード**
  （[jobnet.py:67](../jobnet.py#L67)）。コホートネット（`server._cohort_net`）は
  動的生成されるが、固定 STN はコード内定数。
- **不整合**: 「ネット構造が稼働中に可変データとして自己進化」は未達。
  ナレッジだけが可変で、構造はコード変更を要する。
- **処方**: ネット構造（P・T・弧）を**可変データ**（DB）化し、稼働中の
  自己進化を可能に。

## 4. 改造の指針（不整合 → 揃える方向）

各不整合に対する**揃える方向**の一言。実装指示ではなく、
「哲学に揃えるなら何を揃えるか」の方向づけ。優先度は重みに従う。
分類（§2 骨子）で、**真の不整合**（既存コードの修正）と**未実装**（石4/石5 で新設）を分ける。

| # | 不整合 | 分類 | 揃える方向 |
|---|---|---|---|
| G1 | 入力流が閉じていない | 未実装（石5 IF） | IF 感覚ポート（`place_external_token`）を**物理界の実働完了から実際に呼ぶ**経路を作る（Slack コールバック・人的確認・cron 実績）。相互開きの入力側を実装。 |
| G2 | 接地が同期限定 | 未実装（石5 IF） | 物理界の実働を `physical_operator` として `write_log` に載せ、**外部から還るトークン**を認知する。 |
| G3 | 停止・再開がバッチ帰結 | 未実装（石5 IF） | ネットを**持続させる主体**（イベント駆動ループ or 非同期再開）を置く。`external_wait` を非同期で待ち、外部イベントで再開。 |
| G4 | 実行経路が 2 系統 | **真の不整合** | cron 経路も**ネット経由**に統一（`run_net` を呼ぶ）。評価・決定・投射を T として発火させ、firing に残す。接触点を HUMOS に一点集約。 |
| G5 | 4 記号段が書き込まない | **真の不整合** | 認知・評価・決定・投射が `humos.write_log`（operator_kind 各段）に**判断の痕跡を書く**。4 元素を状態空間に乗せる。 |
| G6 | cron で原子性が壊れる | **真の不整合** | G4 に従い、cron も 4 段を別 T で発火（`api.prescribe` の 1 呼び出し圧縮を T 分解に置き換え）。 |
| G7 | SSS 未実装 | 未実装（石4 SSS） | 書き込み集合を**空間状態として認識・予測・通知**する層（石 4）を実装。3 柱の「状態」を補う。 |
| G8 | IF 未実装 | 未実装（石5 IF） | IF 契約（種別 K・プレース P・制約 C）を**ポートとして宣言・列挙**（石 5）。制御不能入力もポート化。 |
| G9 | 3 柱の片寄り | 混合 | G3（実行を持続化・石5）＋ G7（状態＝SSS・石4）で 3 柱を揃える。 |
| G10 | 審議エスカレーションなし | **真の不整合** | 例外（欠品・天不良）を検知し**審議（中央経路）へ分岐**する T をネットに置く。反射／審議の線を完成。 |
| G11 | ネット構造が可変でない | **真の不整合** | ネット構造（P・T・弧）を**可変データ**（DB）化し、稼働中の自己進化を可能に。 |

### IF の具体（要約）

G1/G2/G3/G8（未実装・石5 IF）の「揃える方向」を、**どのポートでどう閉じるか**で要約する。
詳細（ポート表・配線パターン・増分原則）は石5 の設計書
[真界_IF設計.md](真界_IF設計.md) に分離した。

- **運動（出力）は配線済み** — Slack 送信（処方・在庫結果）が事実上の出口。
  `sos.slack.send_message` → `write_sos` で作動ログを残す（IF#1・IF#2）。
- **感覚（入力）は同期・内部でしか閉じていない** — 在庫結果の帰還（IF#3）が本題。
  現行は `rx_exec_node` が `place_token`（同期・内部）で置き、`inventory_node` が
  DB 照会して自己完結する。**物理オペレータ（人・倉庫）が還ってきていない**。
  石5 はこれを `place_external_token`（非同期・外部）で還す配線に差し替える。
- **非制御入力は未モデル** — 機械の故障・突然の病害・天候（IF#6/7/8）は
  ポートとして列挙していない。閉包違反の温床（[TS概念.md §3.2](TS概念.md)）。
- **同期 → 非同期の切り替えは、IF#3 の配線を変えるだけ** — ネット構造（P/T/弧）は
  変えない。`place_token`（同期）→ `place_external_token`（非同期）の差し替え。
  `place_external_token` は既に存在するが呼び出し元 0 件（G1）。石5 はこの関数を
  IF#3 の配線で実際に呼ぶこと。
- **増分原則** — IF 契約を一つずつ（[TS概念.md §9](TS概念.md)）。波0（完了・石3
  同期クローズ）→ 波1（IF#3 を非同期）→ 波2（IF#4/5 を契約として宣言）→
  波3（非制御入力 IF#6/7/8 をポート化）。

### 優先度の目安

- **第 1 波（真の不整合の解消）** — G4・G5・G6。
  「一つのネット」「4 元素の痕跡」は本質・不変条件に関わる。**既存のコードが設計に
  反して動いている**ので、既存の `run_net` / `write_log` を使うだけで揃えやすく、
  閉包違反と状態空間の痕跡を同時に解消する。
- **第 2 波（未実装の新設）** — G1・G2・G3（石5 IF）・G7（石4 SSS）・G8（石5 IF）。
  第 1 波で HUMOS に溜まった書き込みを前提に、IF（相互開き・接地）と
  SSS（認識・予測・通知）を実装。
- **第 3 波（運用の完成）** — G10（審議エスカレーション）・G11（構造の可変化）。

## 5. 用語（本監査で使う）

| 語 | 意味 |
|---|---|
| **一発バッチ** | `run_net` が固定点まで走りきって return し、持続しない実行モデル |
| **ネット経由 / バイパス** | 認知〜作動を STN の T として発火させるか、モジュールを直接呼ぶか |
| **痕跡** | firing / writing / marking に残る記録。4 元素の判断が HUMOS に残るか |
| **相互開き** | 記号→物理（作動）と物理→記号（感覚）の両方向が開いていること |
| **3 柱** | 実行（VM）・状態（SSS）・運用（PLAN）（[真界哲学_HUMOS設計.md §1.4](真界哲学_HUMOS設計.md)） |
| **真の不整合** | 実装が設計と**矛盾**している（既存コードが設計に反して動く）。G4/G5/G6/G10/G11 |
| **未実装（石4 SSS・石5 IF）** | 設計が**指定していて、まだ作っていない**もの（将来作業）。G1/G2/G3/G7/G8 |
