## 0. 背景 — 作業場問題

育苗圃・本圃で要求を持たせてきた既存設計は、**圃場（場所）が要求の主体**という前提で
成り立っていた。

- 育苗圃 → 防除要求（散布）
- 育苗圃 → 検鏡要求（検鏡）
- 本圃 → 定植要求

しかし、**花芽分化した苗の定植前防除**は、育苗圃でも本圃でもない。**作業場（外）**で
行う。この要求をどこに持たせるか、圃場ベースでは答えが出ない。

「苗に持たせる」案も考えたが、苗は**移動するオブジェクト**（育苗圃→作業場→本圃）。
苗を要求の主体にすると、苗の位置が変わるたびに要求の所在が動く。不安定。

この問題が、要求の主体の再考を迫った。

## 1. 事業主体の定義原理

> **事業主体とは、実働（作動・要求）の発生源であり、実働に直接接続される主体である。**

### 1.1 「経営体」でなく「事業主体」である理由

「経営体」とすると、主体性を**法的・経済的地位**で定義することになる。すると：

- ホールディングス（所有はするが実働しない）が経営体になる
- 実働する子会社がまた別の経営体になる
- 株主・取締役・法人格のレイヤーがモデルに混入する

これらは HUMOS（実働 OS）にとって**ノイズ**だ。OS が知りたいのは「誰が実働を
始めるか」であって、「誰が誰の株を持っているか」ではない。

「事業主体」だと、定義が**実働への接続**に落ちる。法形態は問わない。個人でも、
家族でも、NPO でも、町内会でも、法人でも、**実働を始める主体**なら事業主体。

### 1.2 実働 OS の含意 — 主体は人間でなくてよい

「人と**機械**の実働 OS」である以上、事業主体は**人間である必要も、法人である
必要もない**。

- 人間が営む事業 → 事業主体 = 個人 / 屋号
- 機械が営む業務 → 事業主体 = その機械 / システム
- 人機ハイブリッド → 事業主体 = そのチーム / システム

事業主体は「実働の主体」という**機能**で定義される。これは「経営体」（人間/法人の
概念）には持たない汎用性だ。

### 1.3 普遍性

| 業務 | 事業主体（主語） | 対象 |
|---|---|---|
| いちご栽培 | 三果倉 | 圃場・苗・薬剤 |
| NPO の活動 | NPO 法人 | 支援対象・活動場所 |
| 行政業務 | 和歌山県那賀振興局 | 地域・対象事業 |
| 町内会の清掃 | 町内会 | 清掃区域 |
| 自分の生活 | 自分 | 家・仕事・健康 |

**「誰が」「何を」「どこで」する** — この「誰が」が事業主体。HUMOS が扱うのは、
この「誰が」の状態遷移。

## 2. 本体論 — オブジェクト＋役割＋委任（agent 廃止）

> **2026-09-14 確定**: 「エージェント」概念を廃止する。ドメインエンティティオブジェクトは
> **1種類**で、**役割**と**委任**で差別化する。OOP（オブジェクト指向）の
> 「オブジェクト＋参照＋状態＋導出」にそのまま一致する。

### 2.1 「エージェント」の廃止

[真界哲学_HUMOS設計.md §3.7](真界哲学_HUMOS設計.md) は「育苗責任者エージェント」
「圃場責任者エージェント」を**状態遷移の作動**として定義していた。この "agent" は
3つの意味が混ざっており、それぞれが**既存概念**に吸収される：

| "agent" の意味 | 既存概念 | 処理 |
|---|---|---|
| 化身・代理（実在の記号） | **接地（grounding）** | オブジェクトそのもの |
| 作動の対象（実行者） | **実働（オペレータ）** | オブジェクト＋実行者の役割 |
| 自律アクター（AI agent） | —（該当なし） | 該当しない |

**オッカムのカミソリ**: "agent" は「接地されたオブジェクト」と「実働」の別名にしかならない。
新語として持ち込む必要がない。

### 2.2 なぜ agent 語を使わないか（外への説明）

世の中の「AIエージェント」は、**認知・判断・実行・ループ・身体**を1語に束ねた言葉。
束ねざるを得ないのは、判断が**生成AI（確率的・ブラックボックス）**だから分解できないから。

真界ネットは判断を**決定論的（RBP行列・ルール）**にしている。だから分解できる：
認知／評価・決定／投射／作動（SOS）／マーキング駆動／実働＋接地。

| | 世の中の AI agent | 真界ネット |
|---|---|---|
| 判断（brain） | 生成AI（確率的・ブラックボックス） | **決定論的（RBP）** |
| 実行（hands） | ツール呼び出し | SOS（作動の運動器） |
| ループ | agentic loop | STNマーキング駆動発火 |
| 身体 | 接地 | 実働＋接地 |

**分解できたこと自体が、真界の核心**（確率→決定、意思決定の機械化、トラスト形成）。
防除（農薬散布）のような安全に関わる領域では、ブラックボックスの確率的判断より、
分解・監査可能な決定論的判断が要る。だから「手垢のついたオブジェクト」でやっていく——
**弱さではなく強さ**。

> **判断の補助に生成AIを置く余地**（未決、§13）: RBP だけでは拾えない判断
> （予期しない病害への臨機応応な対応）に生成AIを「判断の補助」として差し込める余地を
> 残すか。残すなら「判断＝決定論＋（補助として）生成」の2層になり、"agent" 語の
> 再導入が議論になる。残さず純粋決定論で通すなら、"agent" 語は完全に不要。

### 2.3 オブジェクトは1種類（役割で差別化）

ドメインエンティティオブジェクトは**1種類**。圃場・薬剤・従業員・組織・場所・主体、
全部「オブジェクト」。差別化するのは**役割**：

| 役割 | 内容 | 例 |
|---|---|---|
| **主体（subject）** | ドメインの根・要求の発生源 | 三果倉 |
| **実行者（operator）** | 作動の対象（実働） | 松山浩士・ロボット散布機 |
| **判定者（judge）** | 帰還膜の発生源 | 那賀いちご生産組合連合会 |
| **被所有（owned-target）** | 主体が所有する対象 | 圃場・薬剤 |

役割はオブジェクトがそのドメインで担うもの。OO で言えば「クラスは1種類、役割はメソッド
（behavior）」。"Agent" クラスを作る必要はない。

### 2.4 接地（grounding）は2面 — 化身＋委任

接地とは、物理界の実在をドメインに化身（オブジェクト）として置くこと。化身を作るだけ
では不十分。物理界の実在は**責任と権限**を持っており、それがオブジェクトに**委任**される。

- **化身（embodiment）**: このオブジェクトは物理実在Xの記号。受動的。**全オブジェクト**が持つ。
- **委任（mandate）**: このオブジェクトは物理実在Xの責任・権限を担う。能動的。
  **実働オブジェクト（人・機械・ロボット・業務アプリ）だけ**が持つ。

圃場・薬剤・場所は化身のみ（委任なし）。松山浩士・那賀組合は化身＋委任。
**「同じオブジェクトでも」**——オブジェクトは1種類に統一されるが、委任が受動的な化身と
能動的な化身を区別する。委任こそが、統一されたオブジェクトを差別化するもの。

### 2.5 委任は3つを生む — 権限・責務・責任

委任（エッジ）は、**権限・責務・責任**の3つを射影する：

| | 委任 | 権限 | 責務 | 責任 |
|---|---|---|---|---|
| 意味 | 誰が誰に渡すか | **していい**こと | **すべき**こと | **答える**こと |
| 向き | 関係（エッジ） | 前向き | 前向き | 後向き |
| 落ちるレイヤー | 関係グラフ | IF/作動のゲート | **PLAN**（期待＋期限） | record_return（帰還・監査） |
| 内容 | 委任者→委任先 | どの作動を起動し、どの判定を受け入れるか | 何を・いつまでに・何の状態に | 誰が答えるか |
| OOP | delegation | permission | obligation / contract | accountability |

- **権限（authority）**＝「何をしていいか」。前向き。作動のゲート。
- **責務（duty）**＝「何をすべきか」。前向き。PLAN（期待状態＋期限）の実体。
- **責任（accountability）**＝「誰が答えるか」。後向き。帰還・監査の記録。

> **「責任」は2つに分かれる**（2026-09-14 確定）:
> - **責務（duty）**＝前向き。「何をすべきか」（期待＋期限）＝ **PLAN**
> - **責任（accountability）**＝後向き。「誰が答えるか」（帰還・監査）＝ **record_return**

### 2.6 会社組織で検証 — 権限は「位置的」

会社組織（会社⊃事業部⊃部⊃課⊃担当、各グループに組織長）で分解すると、
「関係でもあるし属性でもある」が3層に分解して見える：

| 層 | 内容 | 関係 or 属性 | 例 |
|---|---|---|---|
| **① 委任エッジ** | 誰が誰に委任するか | **関係**（辺） | 育苗課 → 松山浩士（委任） |
| **② 権限スコープ** | 何の権限・責任か | **属性**（エッジ or ノード） | 育苗課の責任範囲＝育苗の防除 |
| **③ 実効権限** | 実際に持てる権限 | **導出**（①×②を計算） | 松山浩士の実効権限＝育苗課スコープ |

- **①「誰に」は関係**（エッジ）。
- **②「何を」は属性**（スコープ）。
- **③実効権限は、①と②から導出**（保存しない・計算する）。

**権限は「位置（ポスト）から来る」**。「松山浩士は育苗課の課長」は松山浩士の内在属性で
なく、育苗課と松山浩士の**関係**（異動すれば変わる）。「育苗課の責任範囲は育苗の防除」は
育苗課の**属性**（誰が課長でも同じ）。松山浩士の実効権限は、育苗課のスコープ×彼が課長
である関係で**導出**。

**スコープは2種類**:
- **ノードのスコープ**: ポストの固有権限（課長であること自体）。→ 属性は**委任先ノード**に。
- **エッジのスコープ**: 個別の委任（会社が直接「この一回の散布」を委任）。→ 属性は**エッジ**に。

**グループ（事業部/部/課）も一級オブジェクト**（entity type）。STB は
三果倉（主体）→ 従業員（松山浩士等）の**平坦な1段**で、会社組織（多段階層）の
「段数が1」の特殊ケース。将来 三果倉が事業部を置いたら、段が伸びるだけ。

**OOP対応**:
- 組織階層 ＝ **コンポジショングラフ**（オブジェクトがオブジェクトを参照）
- グループの責任範囲（②）＝ **オブジェクトの状態（属性）**
- 個人の**実効権限（③）＝ 導出プロパティ**（メソッド。保存しない）
- 組織長 ＝ グループの**代表者**（関係: group → person, role=leader）

#### 2.6.1 役割を一級エンティティに（位置的角色・entity_id='role'）

「権限は位置的」（§2.6）の帰結として、**役割（ポスト）を第一級エンティティ**
（`entity_id='role'`）として建模する。役割は「位置」そのもので、人が変わることに
よって存在しない。

```
subject/{id} ──[has_role]──▶ role/{id} ──[holds]──▶ worker/{id}
   事業主体（三果倉）          役割（事業主）          保持者（松山浩士）
```

- **要求の発生源は役割（人物でなく）**。要求トークンは `role`（事業主）・`role_id`・
  `role_holder`（保持者名）を持つ（§5.2）。
- **世代交代 = `holds` エッジの差し替えのみ**。役割ノード（`role/{id}`）は不変。
  松山浩士→松山凌梧へ交代しても、要求の発生源「事業主」は動かない。
- **多段階組織**（店長/部門長/課長）は、`has_role` の先が上位 role/group になるだけ。
  STB は三果倉→事業主→人の**平坦な1段**で、会社組織の「段数が1」の特殊ケース。
- 役割の紐付け（保持者）は HUMOS の **delegation**（`rel='has_role'` / `rel='holds'`）で
  表現する。役割ノードの name/同一性の正はドメインDB の `roles` テーブル。
- **概念的役割（§2.3: 主体/実行者/判定者/被所有）とは別軸**。§2.3 の役割は
  「オブジェクトがドメインで担う差別化」、本節の役割は「人が担う位置（ポスト）」。
  松山浩士は「実行者（概念的）」でありつつ「事業主（位置的角色）の保持者」でもある。

#### 2.6.2 複雑組織構造のエンティティ化（group / project・横断・所属）

§2.6・§2.6.1 は「平坦な1段」（subject→role→worker）で確定した。家族経営の
STB はこれで十分だが、企業が大きくなると組織は**木構造**（事業部⊃部⊃課）に
なり、**組織を横断する組織**（プロジェクト・タスクフォース）や、**各組織に所属
しながらプロジェクトに所属する**構造が現れる。一人が複数の役割に二重・三重に
割り当てられることもある。HUMOS はこれを**ドメインエンティティオブジェクトとして
認識**し、STN への要求イベントと、要求→確認の責務・責任を管理できなければならない。

**本体論は変えない**（オブジェクトは1種類・役割で差別化・委任で接続）。
`delegation` は既に「型付きエッジ」1枚（`rel` で種を区別）なので、複雑組織は
**新エンティティ種＋新 rel の追加**だけで表現できる（スキーマ変更なし）。

**エンティティ種（entity_id）の3分割**:

| 種 | 意味 | 例 | 責務/責任の立場 |
|---|---|---|---|
| **group** | 内部組織ノード（事業部/部/課）。木・横断の単位 | 育苗部・防除課 | 役割の担い手（内部） |
| **project** | 組織を横断するプロジェクト | 「新圃場開拓」タスクフォース | 役割の担い手（内部・横断） |
| **organization** | 外部組織（判定/管理）。帰還の相手 | 那賀いちご生産組合連合会 | 帰還膜の発生源（外部） |

> `organization` は**外部**（判定・管理・帰還の相手）のまま。内部組織（group）と
> 外部組織（organization）を分けることで、「責務の担い手（内部）」と「帰還の相手
> （外部）」が明確に分離する。

**新 rel（delegation の rel はフリーテキスト・スキーマ変更なし）**:

| rel | from → to | 意味 |
|---|---|---|
| **contains** | group → group | 組織階層（木）。事業部⊃部⊃課 |
| **member_of** | group/project → worker | 所属。横断＝同一 worker に複数エッジ |
| **lead** | group → worker | 組織長（代表者・§2.6 の OOP 対応） |

**役割の一般化**: `has_role` は subject→role のみでなく、**group/project→role も
許可**（使用の拡張・スキーマ変更なし）。役割は「位置」なので、主体直下（事業主）
でも部門（課長）でもプロジェクト（PM）でも同じ `role` 種。

- **一人→N役割（二重・三重）**：各役割の `holds` エッジが独立 → **既に互換**
  （`assign_role` は役割単位で「1役割＝1保持者」を保証、人単位は自由）。
- **横断**：同一 worker が複数の group/project の `member_of` を持つだけで表現。
- **木構造**：`contains` の鎖。実効権限はグラフから導出（§2.6 の③・保存しない）。

**解決関数の一般化**: `list_roles` / `role_holder` を「subject から辿る」から
「**任意ノード（subject/group/project）から辿る**」に一般化。要求の発生源は
「どのノードのどの役割か」で特定される（STB は引き続き subject→事業主 の平坦1段）。

### 2.7 実働の定義（再確認）と機械・アプリへの責務

[真界.md §1.5](真界.md) の実働（オペレータ）の正確な定義は：

> **実働（オペレータ）＝ 人・機械・ロボット・業務アプリ・物**

- **SOS は実働ではない**。SOS は記号界の構成要素で**作動の運動器**（§1.4）。
  作動（起動）が SOS を通って IF を跨ぎ、向こう側の**実働**に届く。
- 因果鎖（[真界_IF設計.md §0.1](真界_IF設計.md)）:
  `投射（T内部・内容生成）→ 作動（起動・SOS）──IF──▶ 実働（実行・人/機械/ロボット/業務アプリ/物）`

**責務は機械・アプリに置ける。責任は置けない**：

| | 機械・アプリに置けるか | 理由 |
|---|---|---|
| **責務**（PLAN：期待状態＋期限） | **置ける** | 系（システム）の性質＝作業指示 |
| **責任**（accountability：誰が答えるか） | **置けない** | 道徳的性質＝問責の対象 |

- 責務は「何を・いつまでに・何の状態に」の**作業指示**。系（システム）の性質なので、
  機械・アプリにも置ける。ロボット散布機に「9/25までに育苗圃を散布済み状態に」は
  そのロボットの**作業指示（work order）**。
- 責任は「誰が答えるか」。道徳的性質で、機械には問責できない。責任は必ず**人・組織**で終わる。

**古典原則**: **権限と責務は委任できるが、責任（最終問責）は委任できない。**
- 権限（していい）→ 機械に渡せる（散布を許可）
- 責務（すべき・PLAN）→ 機械に渡せる（作業指示）
- **責任（答える）→ 機械に渡せない。** 委任した人・組織が負う。

```
三果倉（主体）
  └─ 委任 ─▶ 松山浩士（従業員・実働）
               └─ 操作 ─▶ ロボット散布機（実働・道具）
```

- ロボットの**責務**（PLAN）：「9/25までに散布済み状態に」→ 作業指示として置ける。
- ロボットの**責任**（問責）：散布が失敗したら、**ロボットに問わない**。
  松山浩士／三果倉が答える。ロボットは**道具**であり、トラストの相手ではない。

**これが真界ネットの強さ（トラスト形成と直結）**: トラストは道徳的主体（問責できる相手）
との関係。機械・アプリは道具で、トラストの相手にはならない。だから**責任（問責）の鎖は、
必ず人・組織で終わる**。これは制約ではなく強さ——どんなに機械・アプリに実働を委ねても、
「誰が答えるか」は常に人間にたどり着く。問責先が常に人間で確定するから、系は信頼できる。

### 2.8 業務と責務の区別

「防除は責務か？」への答え：**防除は業務。防除＋対象＋期限＋期待状態が責務。**

| | 内容 | 例 |
|---|---|---|
| **業務** | 何を（活動） | 防除 |
| **対象** | 何を対象に | 育苗圃 |
| **期限** | いつまでに | 9/25 |
| **期待状態** | 何の状態に | 防除済み |

「育苗圃 の防除を 9/25 までに防除済み状態にする」——**これが責務**。

落ちるレイヤーが異なる：
- **業務（防除）**＝ STN のマクロ（T_rx_macro：選定→在庫→散布）。**「どうやるか」の構造**。
- **責務**＝ PLAN（schedule_def ＋ expected_state ＋ deadline）。**「いつまでに何の状態にすべきか」の義務**。

```
業務（防除）          = 活動そのもの。STN マクロ
  └─ 責務            = 業務＋対象＋期限＋期待状態。PLAN
       └─ 作動        = 責務を発火させる起動。T の正体
            └─ 実働   = 作動で起動された実行。人/機械
```

### 2.9 STN は純粋のまま（不変条件維持）

- **STN**：マーキングで発火。純粋ペトリネットのまま。
- **権限**：IF/作動のゲート（どの作動を起動するか）。
- **責務**：PLAN（期待状態＋期限）。STN の発火には触れない。
- **責任**：record_return（帰還・監査）。

3つとも STN の外（IF/PLAN/監査）に置く。

### 2.10 役割は「要求→確認」の単一の糸（責務・責任の担い手）

§2.6.1 で役割は「要求の**発生源**」になった。しかしこれだけでは不十分。
要求を出した役割は、その要求が**確認されるまで**、**責務（何を・いつまでに・
何の状態に＝PLAN）**を負い、確認の時点で**責任（誰が答えるか＝帰還・監査）**を
負わなければならない。これは個別トランジションでも、トランジションのグループ
である**コホート**でも同じ。

> **役割 X が「要求を発生 → 責務（期限＋期待状態）を負う → 確認で責任を負う」
> の単一の糸になる。** 発生源と担い手は同じ役割ノード。

| 段階 | 落ちるレイヤー | 役割との接続 |
|---|---|---|
| **要求の発生** | 要求トークン（IF 入方向） | `role` / `role_id` / `role_holder`（§5.2・既存） |
| **責務（PLAN）** | `schedule_def` | **`responsible_role_id`**（何を・いつまでに・何の状態に＝期待状態＋期限） |
| **責任（帰還）** | `record_return` | 確認イベントを**役割保持者**へ解決し状態記録（§13.2） |

**責務を役割に（PLAN 層）**:
- `schedule_def`（業務定義＝責務の正）に **`responsible_role_id`**（NULL 可・
  後方互換＝subject の事業主）を追加。
- **個別トランジションの責務**＝その行の `responsible_role_id`。
- **コホート（トランジション群）の責務**＝同一 `group_id` の行群が同一
  `responsible_role_id`（または `cohorts` テーブルにも `responsible_role_id` を
  追加してコホート単位で）。
- 期限（`deadline_spec`）＋期待状態（`expected_state`）は既に `schedule_def` に
  ある。役割に紐づけば「**期限の責務を役割に割り当て**」が成立する。

**責任を役割保持者に（帰還層）**:
- 確認イベント（検鏡判定確定・定植完了・散布完了）を、そのトランジション/コホートの
  `responsible_role_id` の**保持者**（`entity.role_holder`）へ解決し、
  `record_return` で状態記録する。
- 責任は必ず**人（役割保持者）**で終わる（§2.7 古典原則：権限と責務は委任できるが
  責任は委任できない）。
- 実装には ①連絡先の正（email/Slack user）②人別チャネル解決 ③役割保持者を
  キーにした `record_return` 経路が必要（§13.2）。

**STN の純粋ペトリネット性は維持**（§2.9）：責務は PLAN、責任は帰還、権限は IF。
3つとも STN の外。役割は STN の発火には触れず、PLAN/帰還/IF の「誰が」を特定する。

## 3. 5層の階層（カーディナリティ 1:N : 1:N）

```
真界 (world)           どの世界（閉じた系）  stb       ← 最上位・デプロイ/インスタンス
   │ 1:N
事業主体 (subject)     誰が・実働の主体   三果倉      ← 接地の根・OS のユーザー（world をまたぐ）
   │ 1:N
事業ドメイン (domain)   何の事業          いちご農園
   │ 1:N
事業 (business)         何を              いちご栽培      ← STN のスコープ
   │ 1:N
対象 (objects)          何を・どこを
   ├─ field        育苗圃, 本圃            （主体が所有）
   ├─ worker       松山浩士, 志保, 凌梧          （主体が雇用・実行者）
   ├─ organization 那賀いちご生産組合連合会(判定)
   │               和歌山県那賀振興局(管理)
   └─ location     JA紀の里地域本部ふるさとセンター
```

> **2026-09-15**: 最上位に **world（真界・閉じた系）** を導入。subject は world をまたぐ
> グローバルな行為者（三果倉が stb と dc の両方を営む）。world は ID 段（§4）でもある。

### 3.1 従属関係の確定

**世界（world）が先、主体は世界をまたぐ行為者、ドメインは主体の活動、事業は STN がモデル化する対象。**

- **world（真界）は閉じた系（デプロイ/インスタンス）**。STB=三果倉のいちご世界、
  DC=三果倉の発電機世界（別々の world）。
- **主体（subject）は world をまたぐ**（三果倉が栽培をやめても、三果倉は残る。
  stb と dc の両方の world を営む）。subject は**行為者**であり、world は**系**。
- ドメインは主体の「活動」であり、容器ではない。
- 主体が接地の点（grounding point）。圃場も苗も、主体が所有・操作する対象。

### 3.2 現行 domain_id の位置

現行の `domain_id="stb"` は、実は**事業（栽培）**のレベル。
「事業ドメイン（いちご農園）」は栽培・体験・販売を束ねる**上位**。

つまり現行の domain_id は、4層階層より**1つ下**に座っている。
本設計では、domain_id を**事業ドメイン**に引き上げ、事業（栽培）は STN のスコープ
（net_id）として扱う。

### 3.3 対象の所属

圃場・薬剤・従業員は**事業ドメイン**に属する（事業に属さない）。
理由は、圃場も従業員も複数の事業で共有されるから：

- 育苗圃 は栽培（育苗）でも体験（いちご狩り）でも使われる
- 松山浩士 は栽培・体験・販売の全てで働く

事業（栽培）は、ドメインの対象を**使う** STN である。

## 4. 5-level ID

事業主体は事業より**上位**（1:N）なので、現行の 3-level ID
（`domain_id ⊃ entity_id ⊃ object_id`）に収まらなかった。**4-level**（subject 最上位）に
拡張した（v1.4.0）。さらに **2026-09-15**、真界を TrueWorld に改名し、**最上位概念を
world（閉じた系）に据える**ことで **5-level** に拡張する。

```
真界 (world)           world_id     = "stb"         ← 最上位・閉じた系（デプロイ/インスタンス）
 └─ 事業主体 (subject) subject_id   = "mikakura"    ← 行為者・接地の根（world をまたぐ）
     └─ 事業ドメイン (domain)  domain_id   = "iichigo"   ← 事業ドメイン
         └─ 対象 (entity)      entity_id   = "field"     ← 集約（aggregate）
             └─ 個体 (object)   object_id   = "1"         ← 部分（part）＝実在
```

| 層 | 語 | 意味 | ID | ID の値（例） |
|---|---|---|---|---|
| 1 | **真界（world）** | 閉じた系。デプロイ/インスタンス | `world_id` | `"stb"`（いちご世界）/ `"dc"`（発電機世界） |
| 2 | **事業主体** | 実働の主体。接地の根。world をまたぐ | `subject_id` | `"mikakura"`（三果倉） |
| 3 | **事業ドメイン** | 事業の種別。主体の活動 | `domain_id` | `"iichigo"`（いちご農園） |
| 4 | **対象（エンティティ）** | 集約。同一種の個体の全体 | `entity_id` | `"field"` / `"worker"` / `"organization"` |
| 5 | **個体（オブジェクト）** | 部分。実在（具体的な存在） | `object_id` | `"1"` / `"6"` |

> **事業（栽培）は ID に持たない。** 事業は STN のスコープであり、ドメインの対象を使う
> 「活動」である。
> **net_id = world_id**（STN のスコープを世界に揃える）。現行 net_id="mikakura"（=subject_id）は
> 移行で world_id="stb" へ（挙動不変・リファクタ）。

### 4.1 world と subject の同一性

**world（系）と subject（行為者）は型として分離する。**

- **world** = 真界（閉じた系）= デプロイ/インスタンス。`world_id` は世界（系）の識別。
  STB=`stb`、DC=`dc`。
- **subject** = 行為者・接地の根。**world をまたぐグローバルな正規識別**（canonical id）。
  同一の三果倉が stb と dc の両方の world を営む（§3.1）。
- 役割・委任構造（has_role/holds/delegation）の根は **subject（行為者）** であり、
  world（系）と混ざらない。

- `stb/mikakura/iichigo/field/1` = 三果倉のいちご世界（stb）のいちご農園の圃場・育苗圃
- `dc/mikakura/dc/generator/H1` = 三果倉の発電機世界（dc）の発電機H1（将来）

### 4.2 移行（humos_os v1.4.0 → v1.5.0）

| | v1.4.0（現行） | v1.5.0（本設計） |
|---|---|---|
| ID | 4-level `subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id` | 5-level `world_id ⊃ subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id` |
| entity テーブル | PK `(subject_id, domain_id, entity_id, object_id)` | PK `(world_id, subject_id, domain_id, entity_id, object_id)` |
| 最上位 | `subject_id`（行為者） | `world_id`（系）。subject は world をまたぐ |
| net_id | subject_id（"mikakura"） | world_id（"stb"） |

**影響**: humos_os は pip パッケージ（STB・DC が個別インストール）。
v1.5.0 で entity 層を 5-level に拡張し、両 venv に再インストールする。
STB・DC の server.py の同期呼び出し・net_id 定数も更新する。

> **漸増的移行**: world の導入は「最上位を系（world）に据える」が核心であり、5-level ID は
> それを表現する手段。実装は挙動不変リファクタとして行う（world_id 列の追加 → 移行
> → net_id = world_id）。subject（行為者）の役割・委任構造は不変。

## 5. 膜（IF）の再定義

### 5.1 入方向（要求）— 起点が主体へ

[真界_IF設計.md §0.1](真界_IF設計.md) の入方向がこう変わる：

```
既存:  圃場（ドメインオブジェクト）──スケジュール──▶ 要求──IF──▶ STN
新規:  事業主体 ──スケジュール──▶ 要求（文脈: 圃場・場所・期限）──IF──▶ STN
```

膜弧の**起点が圃場から事業主体へ**。圃場・場所は要求トークンの**文脈（context）**に
格降格する。圃場はエンティティのままで、役割が「主体→対象」に変わる。

### 5.2 要求トークンの形

要求トークンは、**主体＋文脈**を持つ：

```
事業主体（三果倉）の要求トークン:
  {
    subject: "mikakura",              # 誰が（主体）
    role: "事業主",                  # 役割（位置的角色・要求の発生源）
    role_holder: "松山浩士",         # 役割の保持者（紐付けで解決・世代交代で変わる）
    requirement: "防除",            # 何を（要求の種）
    target: "分化した苗",           # 対象
    location: "作業場",             # 場所（圃場でなくてよい）
    deadline: "2026-10-08",        # 期限
    volume: 50                      # 文脈（圃場属性から参照可）
  }
```

- **subject** = 主体（誰が要求）
- **role / role_holder** = 役割（位置的角色）とその保持者（§2.6.1）。要求の発生源は
  役割（人物でなく）。保持者は delegation の `holds` で解決され、世代交代で変わる。
- **requirement** = 要求の種（何を）
- **target / location / deadline** = 文脈（何を・どこで・いつ）
- **volume 等** = 圃場属性から参照可（[オブジェクト接地 §1.10](真界_オブジェクト接地設計.md)
  の「要求を最小にし、文脈はオブジェクトに寄せる」に従う）

### 5.3 作業場問題の解決

```
事業主体（三果倉）──膜弧──▶ P_treat_req（防除要求）
   文脈: 対象=分化した苗, 場所=作業場, 期限=2026-10-08
```

**圃場がなくても成立する。** これが「苗に持たせる」案を不要にした理由。

### 5.4 STN UI での表示 — 圃場を識別キーに（B案・2026-09-15）

§5.1 で膜弧の起点を圃場から事業主体へ移し、圃場を**文脈**に格降格した（§8）。
しかしこれは**モデル（接地）の変更**であり、**表示（射影）まで圃場を二等情報に
すべきではない**。subject 統一後、要求の主たるラベルが「三果倉・事業主：…」と
発生源先頭になると、運航担当が一目で知りたい**どの圃場・どの圃番の要求か**が
括弧内に沈み、トリアージが困難になる（圃場が増えるとノードが同顔になる）。

> **発生源（who）と対象（what / where）を分ける。**
> 発生源は**構造（膜弧の起点ノード）**が担い、対象は**文字（要求の主たるラベル）**が
> 担う。両者は別レイヤーで、圃場を主ラベルにしても発生源は三果倉のまま。

| 問い | 答え | 正の載せ方 |
|---|---|---|
| **誰が要求を発行したか**（発生源） | 三果倉・事業主 | **膜弧の起点ノード**（構造・不変） |
| **何の・どこへの要求か**（対象） | 本圃・A-3 ベッド | **要求の主たるラベル**（文字・B案） |

**B案（採用）— 対象先頭＋帰属**:
- 主ラベルを圃場先頭に：`本圃 / マルチ敷設（延べ510m・白黒・黒）`
- 帰属を小さな行に残す：`発行：三果倉・事業主（松山浩士）`
- **膜弧の起点ノードは三果倉のまま**（「圃場が発火する」旧モデルの誤解を防ぐ）
- 圃番まで出したい場合は主ラベルに圃場＋圃番を載せる：`本圃・4列 / マルチ敷設（…）`

**なぜ C（圃場ノード起点）に戻さないか**：圃場を膜弧の起点にすると識別性は最高だが、
**圃場が発火している**ように見え、§5.1・§8 の趣旨（圃場は文脈）と矛盾し、経験者が
旧モデルを再推測する。発生源は構造（弧）が保証し続ける。

**なぜ A（発生源先頭・旧）を捨てたか**：圃場が括弧内の二次情報になり、圃場を増やした
ときの識別キーが失われる。

**読者**：①実務者（Slack 手順書で場所・担当が分かる＝投射済み）②**運航担当**
（圃場でトリアージしたい＝B案の主たる読者）③設計・保守（発生源を検証したい＝弧の
起点が三果倉で満たされる）。

> **性質**：これは**射影（表示）の変更**であり、挙動不変。要求トークン（§5.2）・
> 膜弧の起点（§5.1）・STN の構造は不変。3 builder の表示ラベルと stn.html の
> 膜弧・ドメイン層カードの強調を切り替えるだけ。真界の「STN は構造、UI は射影の
> 1 つ」に整合（[真界哲学_HUMOS設計.md](真界哲学_HUMOS設計.md)）。

## 7. 帰還経路 — 新しい膜の種類

検鏡は外部判定があるため、膜が2種類になる。

```
入方向（要求）:  事業主体（三果倉）──▶ P_judge_req（検鏡要求）
帰還（判定）:    那賀いちご生産組合連合会 ──▶ P_judge{seq}（判定結果）
```

**帰還経路は、主体→プレースでなく、組織→プレース**。
これは既存設計にない**新しい膜の種類**（外部主体からの帰還）である。

- **入方向** = 主体の要求（「この苗は検鏡に回すべき状態だ」）
- **帰還** = 組織の判定結果（「分化あり/なし」）

検鏡ループがこれで真界として閉じる：
**主体が要求 → 従業員が苗を運ぶ → 組織が判定 → 結果が帰還**。

### 7.1 膜の3種類（整理）

| 膜の種類 | 起点 | 終点 | 意味 |
|---|---|---|---|
| **要求膜**（入方向） | 事業主体 | 要求プレース | 主体が要求を発射 |
| **帰還膜** | 外部主体（組織） | 判定プレース | 外部の判定結果が帰還 |
| **作動膜**（出方向） | STN（投射） | 実働（従業員等） | 主体が作動を実行 |

## 8. 圃場の役割変化

圃場はエンティティのままで（ドメインエンティティオブジェクトであることは不変）、
役割が「主体→対象」に変わる。

| | 既存 | 新規 |
|---|---|---|
| 圃場の役割 | 要求の主体・状態保持体 | **主体が所有する対象・文脈** |
| 圃場の状態 | 圃場が独立に持つ | **主体の状態の一部** |
| 膜弧の起点 | 圃場 | **事業主体** |
| 表示の強調（ラベル） | 圃場先頭 | **圃場先頭＋帰属（§5.4 B案）** |

[真界哲学_HUMOS設計.md §3.7](真界哲学_HUMOS設計.md)「圃場は状態保持の代表例」は、
**主体が状態保持の根、圃場はその所有する対象**に読み替える。

> **表示（射影）は別レイヤー**（§5.4）：膜弧の起点（構造）は事業主体のままでも、
> 要求の**主たるラベル（文字）**は圃場先頭に戻す。圃場を文脈に格降格したのは
> **接地（モデル）**の話であり、運航 UI で圃場を識別キーに使うことを妨げない。

## 9. 既存設計との関係 — §1.11 の分裂問題の解決

[オブジェクト接地 §1.11](真界_オブジェクト接地設計.md) はこう予告していた：

> **苗の防除** — 要求情報（薬剤の量）は**育苗圃**の面積から来る。
> **苗の定植** — 要求情報（プランタンの数）は**親苗**の本数から来る。
> **「物」の単位と、オブジェクトの単位は一致しない。** 物理的な「物」（苗）は、
> 要求情報として切られると、育苗圃（面積）と親苗（本数）の二つのオブジェクトに
> **分裂**する。

これが**作業場問題の予告**。苗の定植前防除は「作業場」で行うが、作業場は圃場でも
親苗でもない。§1.11 の「分裂」が、ここでは**分裂先が見つからない**状態。

事業主体は、**分裂しない**主体：

```
苗（分裂する）
  ├─ 育苗圃（面積）→ 防除
  ├─ 親苗（本数）→ 定植
  └─ 作業場（？）→ 定植前防除   ← 分裂先がない

事業主体（分裂しない）
  └─ 三果倉が、分化した苗を、作業場で、防除すべき   ← 圃場がなくても成立
```

**事業主体は、§1.11 の「分裂する物」の上位に座る、分裂しない主体。**
要求は主体が発し、圃場・場所は文脈（パラメータ）になる。

> **結論**: 事業主体は既存設計の矛盾ではなく、§1.11 が予告した分裂問題の解決。

## 12. 用語

| 語 | 定義 |
|---|---|
| **事業主体**（subject） | 実働（作動・要求）の発生源。実働に直接接続される主体。法形態を問わない（個人/屋号/NPO/法人/機械/ハイブリッド）。接地の根・OS のユーザー |
| **事業ドメイン**（domain） | 事業の種別。主体の活動。複数事業を束ねる（いちご農園） |
| **事業**（business） | STN がモデル化する対象（栽培）。ドメインの対象を使う「活動」 |
| **対象**（object） | 主体が所有・操作する物（圃場・従業員・組織・場所） |
| **内部組織**（group） | 内部組織ノード（事業部/部/課）。木・横断の単位。役割の担い手（内部）（§2.6.2） |
| **プロジェクト**（project） | 組織を横断するプロジェクト。役割の担い手（内部・横断）（§2.6.2） |
| **contains** | group→group。組織階層（木）（§2.6.2） |
| **member_of** | group/project→worker。所属。横断＝同一 worker に複数（§2.6.2） |
| **lead** | group→worker。組織長（代表者）（§2.6.2） |
| **responsible_role_id** | `schedule_def` の責務担当役割。要求→確認の責務（PLAN）の担い手（§2.10） |
| **役割**（role） | オブジェクトがドメインで担うもの。主体/実行者/判定者/被所有。オブジェクトは1種類、役割で差別化（§2.3） |
| **役割（位置的角色）**（role, entity_id='role'） | 人が担う「位置（ポスト）」。事業主/店長/課長…。第一級エンティティ。要求の発生源は役割（人物でなく）。世代交代 = holds 差し替えのみ（§2.6.1） |
| **担い手**（role_holder） | 役割の現在保持者（worker）。delegation の `holds` で解決。世代交代で変わる |
| **化身**（embodiment） | 接地の受動的側。オブジェクトは物理実在の記号。全オブジェクトが持つ（§2.4） |
| **委任**（mandate/delegation） | 接地の能動的側。物理実在の責任・権限がオブジェクトに渡される。実働オブジェクトだけ（§2.4） |
| **権限**（authority） | 「していいこと」。前向き。IF/作動のゲート。delegation グラフから導出（§2.5） |
| **責務**（duty） | 「すべきこと」。前向き。PLAN（期待状態＋期限）の実体。機械・アプリに置ける（§2.5・§2.7） |
| **責任**（accountability） | 「答えること」。後向き。record_return（帰還・監査）。人・組織のみ・問責の終点（§2.5・§2.7） |
| **業務**（activity） | 活動そのもの（防除）。STN マクロ。「どうやるか」の構造（§2.8） |
| **表示（射影）** | UI が STN をどう見せるか（射影の1つ）。接地（モデル）と別レイヤー。圃場を文脈に格降格しても、主ラベルは圃場先頭（識別キー）にできる（§5.4 B案） |
| **要求膜** | 入方向。主体→要求プレース。主体が要求を発射 |
| **帰還膜** | 外部主体（組織）→判定プレース。外部の判定結果が帰還 |
| **作動膜** | 出方向。STN（投射）→実働（従業員等）。主体が作動を実行 |
| **5-level ID** | world_id ⊃ subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id（2026-09-15）。旧 4-level の上位拡張 |
| **world**（世界） | 真界（TrueWorld）＝閉じた系＝デプロイ/インスタンス。ID の最上位（`world_id`）。ドメインは world に内包。STB=`stb`、DC=`dc`（§4） |
| **エージェント**（agent） | **廃止**（2026-09-14）。化身＝接地、実行者＝実働、で吸収。新語として不要（§2.1） |
