# Part 1 — OS 契約（ドメイン非依存）

> 本 Part はどのドメインでも不変である。STB・DC・未来の第 3 ドメイン、すべて
> 同じ契約に従う。

## 1.1 意図（核心）

**物理界は「入力ポートの集合」でなく、「状態（属性）を持つオブジェクトの集合」である。**

HUMOS が物理界に接地するとき、接地点は「イベントが飛んできたポート」ではなく、
**状態（属性）を持つオブジェクト**である。ポートは結果にすぎず、接地の単位は
オブジェクトだ。

そして、オブジェクトの**粒度**は、物理的な便宜（「圃場」「ハウス」のような
管理単位）で決まるのではなく、**その属性が要求ベクトルとして必要かどうか**で
決まる（§1.8）。これが本設計の核心である。

> **オブジェクトの粒度 ＝ 要求情報（要求ベクトル）として必要な属性を持つレベル。**

この一文が、HUMOS が物理界をどこで切るか（接地の単位と粒度）を決める原理であり、
ドメインに依存しない基本設計である。

## 1.2 接地の単位はオブジェクト（ポートではない）

[真界哲学_HUMOS設計.md §3.6](真界哲学_HUMOS設計.md) は「物理界は入力ポートでなく、
空間状態を変える**オペレータ**として SSS に認知される」と定めている。
本契約はその「オペレータ」を**オブジェクト**として具体化する。

- **接地の単位** — 物理界の物を**オブジェクト**として接地する。
  オブジェクトは**状態（属性）**を持つ。
- **ポートは結果** — IF ポート（感覚・運動）は、オブジェクトと HUMOS の間に
  生じる**接点**であり、接地の単位そのものではない。
  オブジェクトが状態を持つから、ポートが生まれる。

> 接地を「ポートの集合」として設計すると、物理界を**イベントの列**としてしか
> 見られなくなる（いつ何かが起きた、の列）。接地を「オブジェクトの集合」として
> 設計すると、物理界を**状態を持つ物**として見られる（何が、どんな状態か）。
> 後者でなければならない。なぜなら、要求は「いつ起きたか」でなく
> 「**どんな状態か**」から生成されるから（§1.7）。

## 1.3 3 層の概念と 3-level ID

> ⚠️ **2026-09-14**: 本節の 3-level は **4-level** に拡張された（事業主体が最上位に
> 追加）。4-level の正は [真界_事業主体設計.md §4](真界_事業主体設計.md) を参照：
> `subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id`（`mikakura / iichigo / field / 1`）。
> 以下は旧版の 3-level 記述（歴史的参照）。

物理界の実在は 3 層で整理し、各層に**管理対象と同じ名前の ID** を持つ。
ID の名前は管理対象、ID の値はその識別（**code**、日本語名ではない）。

```
ドメイン（domain）        domain_id   = "stb"          ← 一番大きな実働空間
 └─ エンティティ（entity）  entity_id   = "field"        ← 集約（aggregate）
     └─ オブジェクト（object）object_id = "1"            ← 部分（part）＝実在
```

| 層 | 語 | 意味 | ID | ID の値（例） |
|---|---|---|---|---|
| 1 | **ドメイン** | 一番大きな実働空間。接地したエンティティの集合 | `domain_id` | `"stb"` / `"dc"` |
| 2 | **エンティティ** | **集約**（aggregate）。同一種のオブジェクトの全体・コレクション | `entity_id` | `"field"` / `"pesticide"` / `"worker"` |
| 3 | **オブジェクト** | **部分**（part）。実在（具体的な存在）。同一性を持つ個体 | `object_id` | `"1"` / `"P01"` / `"6"` |

- **ドメイン** — 「ドメインと聞いて一番大きな空間と直感的にわかる」ように、
  一番大きな実働空間を指す（STB＝いちご栽培、DC＝発電機）。
- **エンティティ** — 集約。`entity_id` は **code**（`"field"`、`"圃場"`ではない）。
- **オブジェクト** — 部分。`object_id` はそのエンティティ内の識別子。

> **ID は管理対象と同じ名前を持つ。**
> ドメインを管理する ID は `domain_id`、エンティティを管理する ID は
> `entity_id`、オブジェクトを管理する ID は `object_id`。
> 識別の値は code（機械語）であり、表示名（`name`）は別に持つ。

### 1.3.1 オブジェクト＝実在（具体的な存在）

オブジェクトは「具体的な存在」を指す。その実在の形はエンティティによって異なる。

| エンティティ（集約） | オブジェクトの実在の形 | 例（STB） |
|---|---|---|
| 圃場 | 施設 | 本圃・育苗圃 |
| 薬剤商品 | 単品 | ベルクート水和剤 |
| 従業員 | 個人 | 松山浩士 |

> 単品・在庫・個人・施設は、いずれも「具体的な存在」を指す語である。
> 特定の管理（在庫管理など）と紐づけた設計ではない。

### 1.3.2 薬剤商品は「単品」として実在（コーパスの保持場所の解決）

**薬剤商品**はエンティティ（集約）であり、そのオブジェクト（部分）の実在の形は
**単品**（製品そのもの：容量・価格・希釈倍率）。
`pesticides` テーブルは、その単品を**記号界でエンコードした形**（制約コーパス）である。

したがって「コーパスの保持場所は DB なのか、ドメインオブジェクトなのか」の
問いは、**別レベルの混同**だった：

- **薬剤商品（エンティティ）のオブジェクト＝単品** — 物理界の実在
- **`pesticides` テーブル＝その単品の記号界エンコーディング** — 制約コーパス

「薬剤商品を認識する」＝ 薬剤単品（部分）を膜で圃場・病害虫・決定に**接地**すること。

## 1.4 エンティティとオブジェクトの関係＝集約（aggregation）

エンティティとオブジェクトの関係は**集約（aggregation）**である。
汎化（generalization）でも構成（composition）でもない。

| 関係 | 意味 | 当否 |
|---|---|---|
| 汎化（generalization） | is-a（本圃は圃場の**一種**） | ❌ |
| 構成（composition） | 強い全体-部分（部分は全体なしに**存在しない**） | ❌ |
| **集約（aggregation）** | 弱い全体-部分（部分は**独立して存在可能**） | ✅ |

- エンティティ（圃場）はオブジェクト（本圃・育苗圃）を**集約**する
  （全体が部分を保持）。
- オブジェクトは独立して存在可能（本圃 は圃場という集約から外れても
  「本圃」として存在する）。

## 1.5 構成品（component）— オブジェクトの部品

オブジェクト（部分）はさらに**構成品**を持つ。構成品は**オブジェクト（個体）に
所属**し、エンティティには昇格しない。

- **構成品はオブジェクトに所属する** — 圃場（エンティティ）に所属するのではなく、
  **本圃（オブジェクト）に所属する**。
- **昇格しない理由** — どのオブジェクトにもあるとは限るもの（例：ベッドはどの
  本圃にもあるとは限らない）は、エンティティ（集約）ではない。
  エンティティは「このドメインで普遍的に存在する実在の種」である。

| 所属オブジェクト | 構成品 | 管理の形 |
|---|---|---|
| 本圃 | ベッド | 属性（length_m 等） |
| 育苗圃 | プランタン | **個数**管理 |
| 育苗圃 | 育苗棚 | 属性（高さ・幅・奥行き・列数・列長） |

> **構成品 vs エンティティの判定** — 「このドメインの**全**オブジェクト（あるいは
> 普遍的に）に存在するか」。存在するならエンティティ候補（薬剤商品・従業員）、
> 存在しないなら構成品（ベッド・プランタン・育苗棚）。

## 1.6 2 系列の境界（ドメイン系列 vs STN 系列）

HUMOS の中に 2 つの系列があり、**混同しない**ことが契約である。

| | ドメイン系列（物理界） | STN 系列（記号界） |
|---|---|---|
| 中身 | エンティティ・オブジェクト・構成品 | ネット（P+T）・コホート・スケジュール鎖 |
| 実体 | 物理界の実在（接地する対象） | 状態遷移の**まとまり**（トランジションの集合） |
| ID | domain_id / entity_id / object_id | net_id（ネット識別） |
| 例 | 圃場・薬剤商品・従業員 | 防除ネット・コホート定植ネット |

> **コホート（cohort）は STN 系列である。**
> コホートは「育苗バッチ」の物理実在に見えるが、設計上は**状態遷移の
> トランジションのまとまり**（検鏡1→…→検鏡N→定植のペトリネット鎖）であり、
> ドメイン系列（エンティティ）には入れない。
> 混同すると、接地の単位（オブジェクト）と発火の単位（ネット）が混ざり、
> マーキング駆動の発火ループ（石2）の根拠が崩れる。

## 1.7 属性の二面性 — 状態 × 要求情報

オブジェクトの属性は、単なるメタデータ（説明書き）ではない。
属性には**二面**がある:

| 面 | 意味 | 誰が使う |
|---|---|---|
| **状態** | オブジェクトの空間状態（SSS が認知する） | SSS（認識・予測・通知） |
| **要求情報** | 認知が生成する**要求ベクトルの軸・値** | 認知（perception） |

- **状態** — 属性は SSS が認知する空間状態である
  （[真界哲学_HUMOS設計.md §3.1](真界哲学_HUMOS設計.md)）。
- **要求情報** — 属性は、認知（perception）が要求ベクトルを生成するときに
  **軸・値**として読まれる（[TS設計.md §12.7](TS設計.md)・認知の緒言）。

> **属性は、状態であると同時に要求情報である。**
> 「圃場の面積」は、単に圃場の状態（SSS が認知する）であると同時に、
> 認知が「薬剤の量」を計算するときの要求情報（要求ベクトルの値）でもある。

この二面性が、接地の粒度を決める（§1.8）。

## 1.8 オブジェクトの粒度原理（核心の原理）

**オブジェクトの粒度は、要求情報として必要な属性で決まる。**

- 属性が**要求情報になる**（要求ベクトルの軸・値になる）レベルで、
  オブジェクトを切る。
- 属性が要求情報にならないレベル（状態はあるが、要求を計算する材料にならない）は、
  独立したオブジェクトにしない。

> **粒度は物理的な便宜で決まらない。**
> 「圃場」「ハウス」「苗」のような管理単位でオブジェクトを切ると、
> 要求を計算するときに必要な属性がオブジェクトに無い、という破綻が起きる。
> 粒度は、**要求ベクトルが完成する単位**で決まる。

## 1.9 スケジュール（PLAN）はオブジェクトに属する

PLAN（第3の柱・期待状態）は、ドメインにフラットに属するのではなく、
**オブジェクトに属する**（[真界哲学_HUMOS設計.md §1.4](真界哲学_HUMOS設計.md)）。

- **スケジューラ** — オブジェクトが持つ PLAN。複数のスケジュール（時刻＋業務）を保持。
- **スケジュール発火** — スケジュールの期待時刻が来ると、**感覚（入力）**として
  STN に要求を生成する（[真界哲学_HUMOS設計.md §5](真界哲学_HUMOS設計.md)）。

**なぜスケジュールはオブジェクトに属するのか** — スケジュールが発火したとき、
要求ベクトルを生成する**属性**が、そのオブジェクトに揃っているから。
スケジュールと、その要求を計算する属性は、同じオブジェクトに属する。
これが §1.8 の粒度原理の帰結である。

### 1.9.1 要求は必ずプレースに接続される（トランジションには直接接続しない）

**ドメインオブジェクトが直接 STN のトランジションに要求を発生させることはなく、
必ずプレースに接続される。**

- **接地点はプレース** — スケジュール発火が生成する要求（感覚・入力）は、
  対象トランジションの**一つ前のプレース**（要求プレース）に
  **要求トークン**として置かれる。トランジションは要求トークンを**読む**側であり、
  要求の**着地点**ではない。
- **要求トークンにオブジェクト属性を付与する** — 置かれる要求トークンは、
  そのオブジェクトの属性（要求ベクトルの種・値）を**付与された**もの。
  トークンが「誰の・どんな要求か」を自己完結して持つ。
- **なぜトランジションに直接接続しないのか** — トランジションは「発火の
  セマンティクス」（認知→評価→決定→投射＋作動）であり、要求の**受け皿**ではない。
  要求をプレースに置くことで、要求は**状態**（マーキング）として存在し、
  マーキング駆動の発火ループ（石2）が「要求＋他条件が揃ったら発火」を
  自然に判定する。要求をトランジションに直接接続すると、要求が
  **状態として存在せず**、発火の根拠がマーキングから外れてしまう
  （不変条件 5「マーキング ≡ M0 からのリプレイ」に反する）。

> **膜（接地の点）= ドメインオブジェクト → 要求プレース へのトークン発行弧。**
> 膜弧の終点は必ず**プレース**であり、トランジションではない。
> 可視化（/stn）でも、折りたたみ（マクロ化）しても膜弧は要求プレースに
> 接続したまま保持する（要求プレースはマクロの内部構造ではなく接地の点）。

## 1.10 要求ナレッジ × 判断ナレッジの境界設計（稼働しながら充実させる）

情報には二種ある。

| | 判断ナレッジ | 要求ナレッジ（要求情報） |
|---|---|---|
| 正体 | **{認知・評価・決定・投射}** | 判断の**入力文脈**（圃場の散布量・薬剤の容量・希釈倍率…） |
| 形成 | **自動導出で形成される**（緒言→RBP 導出 §12.7） | 形成されない。**与えられる／参照される** |
| 例 | 炭疽病→どの薬剤（RBP マッチング） | 本圃 は 500L、ベルクートは 500g 入 |

> **「何リットル溶液が必要か」は判断ナレッジではない。要求情報だ。**
> 判断ナレッジは「何を・どう判断するか」を導出する。要求情報は「判断が走る
> 文脈」を与える。両者は混同してはならない。

### 1.10.1 境界の位置（核心の設計問題）

```
要求がすべてを知る  ◄───────────────────►  要求が何も知らない
（STN は何も知らない）                       （STN がすべて知っている）
```

> **原則: 要求を最小にし、文脈はドメインオブジェクトに寄せる。**
> 要求が何も知らなくてよければ、STN 側がすべて知っている必要がある。
> HUMOS が**ドメインオブジェクトを持てる**特徴が、この境界を STN 側に寄せる
> 武器である（§1.1・§1.8）。

### 1.10.2 方針 — すべて HUMOS にデジタル化し、稼働させながら充実させる

境界は一度に引かない。**その時々で実現可能な境界線を探りながら設計実装する。**

- **方向** — すべて HUMOS（ドメインオブジェクト）にデジタル化していく。
  要求は最小識別子に、文脈はオブジェクト属性に寄せていく。
- **方法** — **稼働させながら充実させる**。境界は一度で完成させず、
  稼働中に「この属性を要求からオブジェクトへ移せるか」を逐次探る。
- **漸増** — [TS設計.md §12.3](TS設計.md)「写生しながら全体に近づく」と同型。

### 1.10.3 境界線の探り方（各情報の配置を明示する）

各情報を「どこに置くか」を、その時々で決定する。配置は**要求／
ドメインオブジェクト／判断ナレッジ**の3択。

| 情報の種 | 置く場所 | 性質 | 境界の位置 |
|---|---|---|---|
| 対象参照・要求の種・時期 | **要求** | 最小識別子 | 要求に残す |
| 対象の量・仕様（散布量・容量・希釈倍率…） | ドメインオブジェクト | 要求文脈 | STN 側へ寄せる |
| 判断（選定・マッチング） | 判断ナレッジ | **導出** | — |
| 数量・価格 | 計算 | 導出でも文脈でもなく計算 | — |

> 境界の位置は**固定の答え**ではなく、**その時々で実現可能な線**である。
> 境界設計は**一度きりの設計**ではなく、**稼働と一体の漸増作業**である
> （[TS設計.md §12.5](TS設計.md)「稼働後の漸増的保守運用」）。
> 稼働中に「この要求が重い」「この属性が要求に載っている」と感じたら、
> 境界を一段 STN 側に寄せる。

### 1.10.4 境界設計の検証（稼働中に確認する問い）

- **要求の最小性** — この要求は、本当にこの情報を運ぶ必要があるか。
  オブジェクトが知っているなら、要求から抜けるか。
- **STN の自己完結性** — 要求が最小識別子だけ渡しても、判断は完結するか。
  完結しないなら、不足する文脈をどのオブジェクトに置くか。
- **導出の整合** — 判断ナレッジ（導出）と要求ナレッジ（文脈）が混ざっていないか。

## 1.11 一つの「物」が複数のスケジュールに関わる場合

物理的な一つの「物」（苗）が、複数のスケジュールに関わることはある。
そのとき、**要求情報は別オブジェクトから来る**。

- 苗の**防除** — 要求情報（薬剤の量）は**育苗圃**の面積から来る。
- 苗の**定植** — 要求情報（プランタンの数）は**親苗**の本数から来る。

> **「物」の単位と、オブジェクトの単位は一致しない。**
> 物理的な「物」（苗）は、要求情報として切られると、
> 育苗圃（面積）と親苗（本数）の二つのオブジェクトに分裂する。
> オブジェクトは「物」でなく「**要求情報として必要な属性を持つ単位**」である。

## 1.12 ドメインは接地したエンティティの集合

ドメイン（STN＋HUMOS）は、**複数エンティティ**を接地する
（[真界哲学_HUMOS設計.md §2](真界哲学_HUMOS設計.md) の二分解）。

- **ドメイン** — 記号界の系。複数エンティティを接地する。
- **全オブジェクトはスケジューラを持つ** — 接地したオブジェクトは、
  すべて PLAN（スケジューラ）を持つ。
- **カレンダーUI** — ドメインの全オブジェクトのスケジューラを**レイヤー**として
  集約表示する。レイヤーはオブジェクトのスケジューラに対応し、
  表示/非表示に切り替え可能（スコープの可視化・[TS概念.md §4](TS概念.md)）。

> ドメインは「ネット＋状態空間」でなく、「**接地したエンティティの集合**」でもある。
> エンティティを接地し、そのオブジェクトのスケジューラを PLAN として保持し、
> スケジュール発火で感覚を生成する。これがドメインの姿。

## 1.13 不変条件との整合

オブジェクト接地は不変条件（[真界哲学_HUMOS設計.md §6](真界哲学_HUMOS設計.md)）を満たす。

| 不変条件 | オブジェクト接地での具体 |
|---|---|
| **1. 未接地の系は真界（TrueWorld）ではない** | オブジェクト（状態を持つ物）を接地する単位とする |
| **2. STN は IF・SOS を直接 import しない** | スケジュール発火は HUMOS（IF ポート）を介して STN に要求を生成 |
| **3. 物理界との接触点は HUMOS に一点に集約** | オブジェクトのスケジュールは HUMOS を経由 |
| **4. 物理界の全状態変化に IF ポート** | オブジェクトの属性変化・スケジュール発火は IF ポートとして列挙 |
| **5. マーキング ≡ M0 からのリプレイ** | スケジュール発火は `place_external_token` で firing 行を記録 |

# Part 2 — 事例化方法（新ドメインを HUMOS に載せる 9 手順）

> 本 Part はドメイン非依存の**手順**である。STB（Part 4）はこれの完成形、
> DC（Part 5）は別の完成形。新ドメインではこの 9 手順を順に踏む。

## 2.1 手順の全体像

```
① 物理界の実在を棚卸し
② 2 系列に分類（ドメイン系列 / STN 系列）
③ エンティティを定義（entity_id = code）
④ オブジェクトを定義（object_id + name）
⑤ 構成品を定義（object_component）
⑥ 属性の二面性で粒度を決める
⑦ PLAN を定義（schedule_def）
⑧ STN を定義（run_net）
⑨ 接地する（ground）
```

## 2.2 ① 物理界の実在を棚卸し

ドメインの物理界に「何が実在するか」を列挙する。管理単位・製品・人・設備・
材料・部品…すべて候補になる。

> 目的: 「接地の単位はオブジェクト」（§1.1・§1.2）なので、まず接地対象を
> 洗い出す。ここはドメイン固有の事実発見であり、OS が代わってやれない。

## 2.3 ② 2 系列に分類（ドメイン系列 / STN 系列）

棚卸しした実在を、**ドメイン系列**（物理界の実在）と **STN 系列**
（状態遷移のまとまり）に分類する（§1.6）。

- **ドメイン系列** — 接地する対象（エンティティ・オブジェクト・構成品）。
- **STN 系列** — ネット・コホート・スケジュール鎖。接地の**対象**ではなく、
  接地の**受け皿**（要求プレース）を持つ側。

> よくある誤り: 「コホート」のような、物理実在に見えるが実態は
> トランジションのまとまりなものを、ドメイン系列に分類してしまう。
> 分類の判定は「これは**実在の個体**か、それとも**発火のまとまり**か」。

## 2.4 ③ エンティティを定義（entity_id = code）

ドメイン系列の実在を、**集約**（エンティティ）にまとめる。
各エンティティに **code** の `entity_id` を付ける（§1.3）。

判定（§1.5）:
- **エンティティにする** — このドメインで**普遍的に**存在する実在の種。
  （圃場・薬剤商品・従業員・発電機）
- **構成品にする** — 全オブジェクトにあるとは限らないもの（ベッド・プランタン）。

> `entity_id` は code（`"field"`、`"pesticide"`、`"worker"`、`"generator"`）。
> 日本語名（`"圃場"`）は `name` として別に持つ。

## 2.5 ④ オブジェクトを定義（object_id + name）

各エンティティの**部分**（個体）をオブジェクトとして定義する。
`object_id`（エンティティ内の識別）と `name`（表示名）を持つ（§1.3）。

> オブジェクトは**実在**（§1.3.1）。圃場なら施設、薬剤商品なら単品、
> 従業員なら個人。

## 2.6 ⑤ 構成品を定義（object_component）

オブジェクトに所属する部品を構成品として定義する（§1.5）。
構成品は**オブジェクト（個体）に所属**し、エンティティには昇格しない。

- **個数管理**の構成品（プランタン）— 数値属性を持つ。
- **属性管理**の構成品（育苗棚・ベッド）— 複数属性を持つ。

## 2.7 ⑥ 属性の二面性で粒度を決める

各オブジェクトの属性を、**状態 × 要求情報**の二面性（§1.7）で検証し、
粒度を確定する（§1.8）。

- 属性が**要求情報になる**（要求ベクトルの軸・値）なら、そのレベルで
  オブジェクトを切る。
- 要求情報にならないレベルは独立オブジェクトにしない（構成品・属性に留める）。

> これが「なぜ本圃 なのか苗ではないのか」を決定する手順（§1.11）。

## 2.8 ⑦ PLAN を定義（schedule_def）

各オブジェクトに PLAN（スケジューラ）を付ける（§1.9）。
`schedule_def`（target_value = オブジェクト ID・複数）で定義する。

- スケジュール発火は**感覚（入力）**として STN に要求を生成する。
- 発火時に読む属性が、そのオブジェクトに揃っていることを確認する
  （§1.9 の帰結）。

## 2.9 ⑧ STN を定義（run_net）

要求を受ける STN（ペトリネット）を定義する（§1.9.1）。

- **要求プレース** — 対象トランジションの一つ前のプレース。
  膜弧の終点は必ず**プレース**（トランジションではない）。
- **要求トークン** — オブジェクト属性を付与されたもの（要求ベクトルの種・値）。
- **発火ループ** — マーキング駆動（石2）。要求＋他条件が揃ったら発火。

## 2.10 ⑨ 接地する（ground）

ドメインオブジェクト → 要求プレース の膜弧を張り、接地を完了する（§1.9.1）。

- `ground`（humos_os.entity）で発火行 `E:<token_key>` を記録し
  `grounded=1` を設定する。
- 接地が済んだエンティティだけが、そのドメインの真界（TrueWorld）を構成する
  （不変条件 1・§1.13）。

> 9 手順の出口は「接地」。接地していない系は真界（TrueWorld）ではない
> （§1.13・不変条件 1）。

# Part 3 — 実装パターン（humos_os の API）

> 本 Part はドメイン非依存の**実装パターン**である。どのドメインでも同じ
> API を使う。具体的テーブル名・属性名は Part 4・5 で示す。

## 3.1 スキーマ（entity 層）

```sql
-- 3-level ID: domain_id ⊃ entity_id ⊃ object_id
CREATE TABLE IF NOT EXISTS entity (
    domain_id   TEXT NOT NULL,      -- ① ドメイン識別（code: "stb" / "dc"）
    entity_id   TEXT NOT NULL,      -- ② エンティティ識別（code: "field" / "pesticide"）
    object_id   TEXT NOT NULL,      -- ③ オブジェクト識別（"1" / "P01" / "6"）
    name        TEXT NOT NULL,      -- 表示名（日本語可: "本圃"）
    attrs       TEXT DEFAULT '{}',  -- 属性（状態×要求情報）JSON
    grounded    INTEGER DEFAULT 0,  -- 接地済みフラグ
    created_at  TEXT DEFAULT (datetime('now')),
    updated_at  TEXT DEFAULT (datetime('now')),
    PRIMARY KEY(domain_id, entity_id, object_id)
);

CREATE TABLE IF NOT EXISTS entity_attribute (
    domain_id   TEXT NOT NULL,
    entity_id   TEXT NOT NULL,
    object_id   TEXT NOT NULL,
    attr_key    TEXT NOT NULL,
    attr_value  TEXT,
    attr_kind   TEXT DEFAULT 'requirement',   -- requirement / state（§1.7 二面性）
    source      TEXT,
    updated_at  TEXT DEFAULT (datetime('now')),
    PRIMARY KEY(domain_id, entity_id, object_id, attr_key)
);

-- 構成品（§1.5）— オブジェクトに所属
CREATE TABLE IF NOT EXISTS object_component (
    domain_id   TEXT NOT NULL,
    entity_id   TEXT NOT NULL,
    object_id   TEXT NOT NULL,      -- 所属オブジェクト
    comp_type   TEXT NOT NULL,      -- 構成品の種（code: "bed" / "planter" / "rack"）
    comp_id     TEXT NOT NULL,      -- 構成品の識別
    name        TEXT,
    attrs       TEXT DEFAULT '{}',  -- 構成品の属性 JSON
    PRIMARY KEY(domain_id, entity_id, object_id, comp_type, comp_id)
);
```

> **v1.2.0 注記**: 現行 v1.1.0 の `entity.py` は
> `net_id`/`domain`/`entity_id` の 3 列で、本設計の
> `domain_id`/`entity_id`/`object_id` と**1 レベルずれている**。
> v1.2.0 で本スキーマにリネームする（§3.6 移行）。

## 3.2 パターン A — ドメイン DB から同期（sync_from_domain）

ドメイン側に既存の DB（`fields`・`pesticides` 等）がある場合、
その行を HUMOS の entity 層に同期する。**属性の正はドメイン DB に残る**。

```python
from humos_os import entity

entity.ensure_entity_schema(conn)

def _rows_to_dicts(sql):
    cur = conn.execute(sql)
    cols = [d[0] for d in cur.description]
    return [dict(zip(cols, row)) for row in cur.fetchall()]

rows = _rows_to_dicts("SELECT id, name, area_value, spray_volume FROM fields")
entity.sync_from_domain(conn,
                        domain_id="stb",
                        entity_id="field",          # code（日本語名ではない）
                        rows=rows,
                        id_key="id",                # → object_id
                        name_key="name",
                        attr_map={"area_value": "area_value",
                                  "spray_volume": "spray_volume"})
```

> 同期は**属性の正をドメイン DB に置く**（pest-disease-db-authority と同型）。
> HUMOS 側は接地・認知のためのコピー。

# Part 4 — 事例 1: STB（いちご栽培）

> **STB 固有**の事例。Part 1〜3 の OS 契約を、いちご栽培ドメインでどう適用したか
> の**模範解答**である。テーブル名・属性名・業務名はすべて STB 固有。

## 4.1 3-level ID の適用

```
domain_id = "stb"
 ├─ entity_id = "field"           （圃場）
 │    ├─ object_id = "1"  name="育苗圃"  （施設）
 │    └─ object_id = "2"  name="本圃"        （施設）
 ├─ entity_id = "pesticide"       （薬剤商品）
 │    ├─ object_id = "P01"  name="ベルクート水和剤"  （単品）
 │    └─ …（64 単品）
 ├─ entity_id = "worker"          （従業員）
 │    ├─ object_id = "6"  name="松山浩士"  （個人）
 │    └─ …
 └─ entity_id = "mulch_material"  （マルチ資材）
      ├─ object_id = "2"  name="白黒マルチ"  （単品）
      └─ object_id = "3"  name="黒マルチ"    （単品）
```

## 4.2 構成品の適用（§1.5）

| 所属オブジェクト | 構成品 | 管理の形 |
|---|---|---|
| 本圃（field/2） | ベッド | 属性（length_m 等）。6 本 |
| 育苗圃（field/1） | プランタン | **個数**管理 |
| 育苗圃（field/1） | 育苗棚 | 属性（高さ・幅・奥行き・列数・列長） |

> ベッドはどの本圃にもあるとは限らないため、エンティティに昇格せず
> **本圃 の構成品**にした（§1.5 の判定）。

## 4.3 属性と粒度（§1.8）

| オブジェクト | 属性（要求情報） | 決定するスケジュール |
|---|---|---|
| **本圃** | 面積（10 tan）・散布量（500L） | **防除**（面積・散布量→薬剤量） |
| **育苗圃** | 面積・散布量（50L） | **苗の防除**（面積→薬剤量） |
| **本圃**（構成品: ベッド） | ベッドの**延べ長さ** | **マルチ敷設**（延べ長さ→マルチ本数） |

- **苗**は独立オブジェクトにしない — 苗自体は要求情報を持たない。
  苗の防除は育苗圃 に、苗の定植は親苗に属する（§1.11）。

## 4.4 2 系列の分類（§1.6）

| 系列 | STB の中身 |
|---|---|
| **ドメイン系列** | 圃場・薬剤商品・従業員・マルチ資材（エンティティ） |
| **STN 系列** | 防除ネット・コホート定植ネット・散布鎖 |

> **コホート（第5期 等）は STN 系列** — 育苗バッチの物理実在に見えるが、
> 検鏡1→…→検鏡N→定植のペトリネット鎖（トランジションのまとまり）であり、
> ドメイン系列には入れない（§1.6）。

## 4.5 PLAN と STN（§1.9・§2.8・§2.9）

- **PLAN** — `schedule_def`（target_value = オブジェクト ID）。
  本圃 の防除・マルチ敷設、育苗圃 の検鏡・定植。
- **STN** — 要求プレース（`P_spray_req` 等）に要求トークンを置き、
  マーキング駆動で発火（`jobnet.run_net`）。

## 4.6 既存テーブルとの対応（実装メモ）

| OS 契約の概念 | STB の既存テーブル |
|---|---|
| エンティティ・オブジェクト（レジストリ） | `fields`（圃場）/ `pesticides`（薬剤）/ `workers`（従業員）/ `mulch_materials` |
| 属性（状態×要求情報） | `fields.area_value` / `fields.spray_volume` / `beds`（延べ長さ） |
| 構成品 | `beds`（本圃 の構成品） |
| スケジューラ（PLAN） | `schedule_def`（target_value = オブジェクト ID・複数） |
| 要求発生（スケジュール→STN） | `place_external_token`（未配線・石5 IF） |
| カレンダーUI | 運航管理センターUI（運行図表・レイヤー集約） |

# Part 5 — 事例 2: DC（発電機）

> **DC 固有**の事例。Part 1〜3 の OS 契約が**ドメイン非依存**であることを
> 証明するための第二の完成形。STB（いちご栽培）と全く異なるドメインで、
> 同じ 9 手順（Part 2）を踏む。

## 5.1 3-level ID の適用

```
domain_id = "dc"
 └─ entity_id = "generator"       （発電機）
      ├─ object_id = "H1"  name="発電機H1"  （施設・単機）
      ├─ object_id = "H2"  name="発電機H2"  （施設・単機）
      └─ object_id = "K3"  name="発電機K3"  （施設・単機）
```

> STB が「圃場・薬剤・従業員」の複数エンティティを持つのに対し、
> DC は**単一エンティティ（発電機）**でよい。エンティティの数は
> ドメイン固有（§2.4）。

## 5.2 構成品の適用（§1.5）

発電機は単機（オブジェクト）であり、構成品は例：

| 所属オブジェクト | 構成品 | 管理の形 |
|---|---|---|
| 発電機H1（generator/H1） | 油（エンジンオイル） | 属性（前回交換日・交換周期） |

> 油はどの発電機にもあるが、**発電機（オブジェクト）に所属**する構成品であり、
> 独立エンティティにはしない（個体の部品）。

## 5.3 属性と粒度（§1.8）

| オブジェクト | 属性（要求情報） | 決定するスケジュール |
|---|---|---|
| **発電機H1** | 前回交換日・交換周期（年） | **油交換**（周期→次回交換日） |

- 油交換の要求情報（前回交換日・周期）は**発電機オブジェクト**に属する。
- 要求は「発電機H1＋油交換」の最小識別子だけでよい（§1.10）。

## 5.4 2 系列の分類（§1.6）

| 系列 | DC の中身 |
|---|---|
| **ドメイン系列** | 発電機（エンティティ） |
| **STN 系列** | 油交換ネット（定常業務） |

## 5.5 PLAN と STN（§1.9・§2.8・§2.9）

- **PLAN** — `schedule_def`（net_id = `genki_key`、reference = 前回交換日、
  offset = 交換周期 `round(years*365.25)` 日、expected_state = `P_completed`）。
  定常業務なので **interval**（周期型）。
- **STN** — 油交換ネット。要求プレースに要求トークンを置き、
  交換完了で `P_completed` に到達。

## 5.6 既存テーブルとの対応（実装メモ）

| OS 契約の概念 | DC の既存テーブル |
|---|---|
| エンティティ・オブジェクト（レジストリ） | 発電機台帳（generator） |
| 属性（状態×要求情報） | 前回交換日・交換周期 |
| スケジューラ（PLAN） | `schedule_def`（interval・net_id=genki_key） |
| 要求発生（スケジュール→STN） | `place_external_token` |

> DC は STB と**全く異なるドメイン**（発電機 vs いちご栽培）でありながら、
> 同じ 9 手順（Part 2）・同じ API（Part 3）・同じ OS 契約（Part 1）で
> 実装できる。これが本ガイドの**ドメイン非依存性**の証明である。

# 付録 — 用語

| 語 | 意味 |
|---|---|
| **world**（世界） | 真界（TrueWorld）＝閉じた系（デプロイ/インスタンス）。5-level ID の最上位。STB=`stb`、DC=`dc`。net_id = world_id |
| **事業主体**（subject） | 接地の根・実働の発生源。5-level ID の2段目（world をまたぐ行為者）。STB＝三果倉（`subject_id="mikakura"`）。[真界_事業主体設計.md](真界_事業主体設計.md) を参照 |
| **5-level ID** | `world_id ⊃ subject_id ⊃ domain_id ⊃ entity_id ⊃ object_id`（`stb / mikakura / iichigo / field / 1`）。旧 4-level（`subject ⊃ domain ⊃ entity ⊃ object`）の上位拡張 |
| **役割**（role） | オブジェクトが担うもの。主体/実行者/判定者/被所有。オブジェクトは1種類で役割で差別化 |
| **化身**（embodiment） | 接地の受動的側。オブジェクトは物理実在の記号。全オブジェクトが持つ |
| **委任**（mandate） | 接地の能動的側。実働オブジェクトだけ。権限・責務・責任の3射影を生成 |
| **ドメイン** | 事業の種別。主体の活動（STB＝いちご栽培、DC＝発電機）。`domain_id` で識別 |
| **エンティティ** | **集約**（aggregate）。同一種のオブジェクトの全体・コレクション（圃場・薬剤商品・従業員・発電機）。`entity_id`（code）で識別 |
| **オブジェクト** | **部分**（part）。実在（具体的な存在）。同一性を持つ個体。`object_id` で識別。属性（状態×要求情報）＋スケジューラを持つ |
| **構成品** | オブジェクト（個体）に所属する部品（ベッド・プランタン・育苗棚・油）。エンティティには昇格しない |
| **集約** | エンティティとオブジェクトの関係（弱い全体-部分）。部分は独立して存在可能（汎化でも構成でもない） |
| **2 系列** | ドメイン系列（物理界の実在）と STN 系列（状態遷移のまとまり）。混同しない |
| **単品** | 薬剤商品・マルチ資材のオブジェクトの実在の形（製品そのもの） |
| **属性** | オブジェクトの状態。SSS が認知する空間状態であり、認知が生成する要求ベクトルの軸・値（要求情報）。この二面性がオブジェクトの粒度を決める |
| **粒度原理** | オブジェクトの粒度は、要求情報として必要な属性で決まる（物理的な便宜で決まらない） |
| **判断ナレッジ** | {認知・評価・決定・投射}。自動導出で形成される |
| **要求ナレッジ** | 判断の入力文脈（散布量・容量・希釈倍率…）。形成されない、与えられる |
| **スケジューラ** | オブジェクトの PLAN（期待イベントの集合）。複数のスケジュールを保持 |
| **スケジュール** | スケジューラの 1 件（業務＋期待時刻）。発火すると感覚（入力）として要求を生成 |
| **膜** | 接地の点。ドメインオブジェクト → 要求プレース へのトークン発行弧。終点は必ずプレース |
| **事例化方法** | 新ドメインを HUMOS に載せる 9 手順（Part 2） |
