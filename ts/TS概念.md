# TS（真界システム）

**TS ＝ 真界システム ＝ 人と機械の協働系（システム）**

物理界と記号界を包括した**一つの閉じた世界**。これはラベルでなく構造。
知能があるわけではなく、関係と構造だけが問題である（[業務無人思想](../業務無人思想.md) 参照）。

> **2026-09-15 改名**: 真界 TrueNet（TN）→ **TrueWorld（TW）**。真界は「ネット」でなく
> **世界**（記号界＋物理界の閉じた系）。ネットと呼ぶのは STN だけ。TS（真界システム）と
> TW（TrueWorld）は同一の閉じた系。哲学層（もたれかかり・交互・トラスト元素・自動無限運動・
> 重力の発生=M0・未来永劫のドミノ・生命の現象論）は [真界.md「本質（哲学）」](真界.md) を参照。

## 0. 前提 — 瓶の中の脳から身体へ

記号世界だけが走っているネットは、瓶の中の脳（brain in a vat）だ。
計算はする。世界を触っていない。手足がないから、世界からの帰還も要らない。
だから「Slack送信した**のち**」が語れなかった。

TS は身体である。世界の中で動き、世界に動かれる。
脳が物理の基盤の上に載っている。手足（IF）が膜として世界と接する。
この言い換えが、さきほどの全難しさ（ループを閉じるか否か）を溶かした。

> **身体とは、物理の上に載った記号ネットワークそのものだ。**

## 1. 三つの世界と、その接合

| 層 | 名 | 内容 |
|---|---|---|
| **全体（閉じた系）** | **TS**（TrueWorld） | 脳＋膜＋身体を包括した世界 |
| 脳 | **SymbolNet** | 状態遷移ネット（ペトリ構造）＋ HUMOS（状態空間基盤） |
| 膜 | **IF** | 感覚・運動。境界（membrane）。ポートの集合 |
| 身体 | スコープを決めた実働世界 | 人・機械。実働系 |

- **記号世界** ＝ 状態遷移ネット（構造）＋ 状態空間基盤（マーキング・ログの土壌）＋ SOS（作動）
- **物理世界** ＝ 人・機械（実働）
- **境（IF）** ＝ 入力（認知）／出力（作動）＝ 感覚・運動

「境」はポート（入出力）ではない。**アフォーダンス**だ。
目はデータを「取り込む」のではなく、見られる範囲に**既にフィルタされた知覚**を脳に渡す。
手はデータを「出す」のではなく、能力と制約を持つ（同時に二か所に在れない、これ以上は持てない）。

## 2. TS（TrueWorld）の定義

**物理界に存在する記号ネットワーク。記号界に閉じておらず、物理界に開かれている。**

しかしさらに、
**その物理界は「スコープを決めた実働世界」を範囲にもつ**ので、
**物理―記号、両界を包括した閉じたシステム**でもある。

この三つの主張は矛盾ではなく、一つの構造の三方向からの言い方:

> **膜（membrane）で開き、スコープ（境界）で閉じる。**

熱力学の開放系・閉鎖系に等しい。部屋とサーモスタットの複合体は、
外界に対して閉じていて、部屋と装置のあいだ（膜）に対して開いている。

### 命名の由来 — シミュレーションの網 vs 接地された網

- **SimNet** ＝ 記号界に閉じたシミュレーションの網。住人はそれが現実だと思っている
- **TrueWorld** ＝ 物理界に接地された閉じた系（世界）

> **未接地の系は TrueWorld（真界）ではない。** ネットと呼ぶのは STN だけ。

**状態遷移ネット（State Transition Net / STN）** — ペトリ網構造の脳本体。
命名の経緯: **JOBNET → NAVNET（ナビネット）→ STN（状態遷移ネット）**。
「状態機械との違い＝並行性、状態がマーキング＝分布」というペトリネットの本質を名前に反映した命名（[TS設計.md §11.10〜§11.14](TS設計.md)）。
ファイル名 `jobnet.py` は命名と分離して旧称のまま（概念名とファイル名を分離する決定）。

マトリックス（1999）がその反例を描く。
住人は自分の世界を「the System」と呼んで、それが真だと信じている。
完全で一貫しているのに、真ではない。
**スコープ境界（膜）を失ったネットはマトリックスになる** — これが TS の「マトリックス化」だ。

## 3. 不変条件（検証可能なもの）

不変条件は設計者の意気込みでなく、**検査できる違反**として置く。

### 3.1 接地

IF 契約が切れたら、記号ネットワークの真理は中断される。エラーではなく、単に接地されていない。

### 3.2 閉包（closure）

> **境界を跨ぐ可能性のあるすべてのイベントに、ポートがなければならない。**

これが壊れた瞬間、系は閉じていない。解釈ではなく検知できる違反。
在庫待ちの状態がないのに「在庫なし」トークンが来たら、バグではなく**閉包違反**として名指しできる。

**注意** — 閉包の本当に難しい所は制御不能入力だ。
- 誰もチェックしなかったのに「あの薬剤、実は切れてた」
- 機械が勝手に壊れた
- 突然の病害発生

これらは制御しなかったのに跨ぐ入力。**ポートを持たないと閉包違反**になる。
ポートの棚卸しは「制御できる出」だけでなく「制御できない入」を列挙する。
後者が漏れると閉包は嘘になる。

### 3.3 有界性（boundedness）

Petri 網の語で言うと、TS は「有界な閉網に制御入力＋非制御入力を付けた系」:

- **閉じている** ＝ 有界性。全プレースのトークンが有限に保たれ、系全体としてトークンが漏れない
- **膜で開いている** ＝ 外部入力トランジション（制御入力＋非制御入力）
- **スコープ** ＝ どの P・T を「系の中」に置くか、外の事象を外部入力ポートとして扱うかの選択

有界性は Petri 網理論で**機械的に判定できる性質**。
したがって「閉じた系」は願望ではなく、**機械的に検証できる不変条件**として置ける。

### 3.4 内部の整合（マーキング≡リプレイ）

> **ライブマーキング ≡ M0 からトレースをリプレイした結果**

これは 3.3 の内部版。全体版は「有界性 ＋ ポート完備」だ。

## 4. スコープとは、ポートの集合である

境界は物理的な線ではない。
**境界 ＝「ポートとして扱う」ことを決めたイベントの集合。**

「どこをスコープに入れるか」の決定はポートの棚卸しであり、
**第一に、かつ最も高価な設計決定**だ。
なぜならポートが決まると IF 契約が決まり、IF 契約が決まると状態空間が決まるから。
スコープを後からずらすと、そのすべてが追従する手術になる。

## 5. 身体 — 反射と審議

身体には二種類の動きがある。

- **審議（遅い脳）** ＝ 認知→評価→決定→投射→作動。
  LLM・Haskell・DB単一化が乗る、高価な中央経路。
- **反射（速い・局部）** ＝ 火傷した手を引くのに脳は考えない。脊髄がやる。
  `enabled_when` の宣言的発火・cron・在庫結果での再開。

在庫の結果で引き分けが決まる:

- **在手** → 反射。ネットは次トランジションを発火して再開。LLM も決定も要らない。速く・局部・安い。
- **欠品** → 身体が自分で決められない（代替剤はどれ？どこから発注？）。**審議にエスカレート。**

> **常態の帰還（在手・天気OK・散布完了）は反射で再開し、例外の帰還（欠品・天不良）だけ審議にエスカレートする。**

この線を引いておかないと、在庫の結果を全部審議（LLM）に回して、
高価な脳を常態で回し続ける設計になる。
**高価な脳は「本当に判断が要る少数の分岐」だけで回し、常態は反射が背負う。**

### 体性状態・恒常性

身体は脳が考えていなくても姿勢を保ち、状態（マーキング）を保つ。
- 状態空間基盤は「ログ」でなく、**身体の standing condition**
- 在庫はイベントでなく「腹が減っている／満腹」という**持続状態**
- 停止中（在庫待ち）の「停止」自体が、体性状態として保持され続ける

## 6. HUMOS — 状態空間管理基盤（設計）

脳が住む土壌（humus）。各トランジションごとの状態（ログ）、
各プレースの登録、マーキングの書き込み DB がここにある。

**HUMOS は受動レコードではなく能動ゲート。**

発火判定（`enabled_when`）が「上流が発火したか」ではなく、
「**今、このプレースにこういうトークンがあるか**」をライブマーキングから読む。
だからマーキングは単なるログでなく、**発火判定そのものの根拠**。
在庫待ちのプレースにトークンを載せて停止し、結果トークンが落ちたら再開 —
これには能動ゲートが要る。

### 6.1 書き込むもの（書き込みスコープ）

HUMOS に書き込む場所は、状態遷移ネット のマーキング・トランジションに留まらない。

| 書き込み | 誰が書くか |
|---|---|
| プレースのマーキング（ライブ M） | `fire()` |
| トランジション発火（消費・生成・トリガー） | `fire()` |
| 認知モジュールのログ | perception.py |
| 評価モジュールのログ | evaluation.py |
| 決定モジュールのログ | decision.py |
| 投射モジュールのログ | projection.py |
| SOS ライブラリのログ（Slack 送信など） | sos/ |

認知・評価・決定・投射のモジュールが 状態遷移ネット のプレースのマーキングやトランジションを形成する。
そのログと、SOS ライブラリのログもまた、HUMOS に書き込む場所が必要である。

### 6.2 なぜ書き込むのか — 空間状態としての認識

書き込む理由は、**HUMOS がこれらの書き込みを空間状態として認識するため**である。

- **状態認識** — 書き込みの集合を、今の空間状態 M として認識する
- **状態予測** — 一般システム理論で、状態の遷移を予測する
- **通知** — 状態変化をリアルタイムに通知する

一般システム理論とは、部分の和としてではなく**系全体の振る舞い**として状態を捉える理論である。
HUMOS は書き込みの集合を「系」として扱い、その全体の振る舞いを認識・予測・通知する。

### 6.3 認知スコープ — 物理界の実働（オペレータ）

この空間状態システムの認知スコープは、状態遷移ネット に留まらない。

- 状態遷移ネット（記号界）
- 物理界の**人**・**機械**・**ロボット**・**業務アプリ**・**物**

これらはすべて、**物理界の実働（オペレータ）** として認知できる。
HUMOS は「誰が空間状態を変えたか」を、状態遷移ネット のトランジションだけでなく、
物理界の実働（オペレータ）として認識する。

これが接地の具体である。物理界は「入力ポート」ではなく、**オペレータ**である。
HUMOS は、記号界と物理界の両方のオペレータによる空間状態の変化を、一つの系として認識する。

### 6.4 彩色 Petri 網

個数カウントでなく、トークンにペイロードを持たせる（彩色）。
「在庫チェック待ち」のトークンが「どの薬剤か」を運ばなければ、
チェックが何を調べるか分からない。

### 6.5 スキーマ

```sql
-- ① プレース登録（ネットのスキーマ。jobnet.py と一致）
place(id PK, name, kind, capacity NULL)
--   kind: state / gate / external_wait / terminal

-- ② トークン（彩色 — 識別子＋ペイロード。個数でなく"トークンを記録"）
token(id PK, kind, payload JSON, created_at)
--   payload 例: {pesticide_id, plot, qty}

-- ③ ライブマーキング ＝ 今の M（place → tokens の多集合）
marking(place_id, token_id, entered_at, PK(place_id, token_id))

-- ④ トレース ＝ 追記専用の発火ログ
firing(id PK, transition_id, fired_at,
       consumed JSON, produced JSON,
       triggering_event JSON)  -- internal / cron / slack_cb / inventory_result

-- ⑤ 書き込みログ ＝ 空間状態の生データ（モジュール・SOS・物理界の全書き込み）
writing(id PK,
        operator_id,        -- 誰が書いたか（トランジション or 物理界のオペレータ）
        operator_kind,      -- transition / perception / evaluation / decision / projection / sos / physical_operator
        action,             -- 何をしたか（log / slack_send / ...）
        payload JSON,       -- 内容
        related_place_id,   -- どのプレースに関係するか（nullable）
        created_at)
```

### 6.6 関数

- `enabled(t)` — ライブマーキングを読んで「今 t は発火できるか」
- `fire(t)` — 原子的に 入力トークン消費 → 出力トークン生成 → ③更新 → ④追記

### 6.7 メタ認知 — 自資源状態の認識

在庫（倉庫）は「外部の物」ではない。
系の実働（発火）が依存し、消費する**物理的基盤**＝身体の状態である。

系が自分の発火の物理的帰結（在庫逓減）を空間状態の一部として認識すること —
それが**メタ認知**である。体性感覚（proprioception）に相当する。

- **別モジュールではない。** 空間状態システム（HUMOS）が、系の自基盤を認識しているだけ。
  「meta」は別機構でなく、**自分の状態を認識することから生じる**。
- **不変条件と直結する。** 在庫を外に置くと、系の発火が物理的に在庫を逓減させても
  マーキングに乗らず、クエリ間のモデルのずれ（隠れリーク）が生まれる。
  接地・有界性・閉包を同時に破る。
- **だから閉じた接地系では必須。** メタ認知はオプションでなく、不変条件の要求。
  代償は閉包の重さ（在庫の全変化をトランジションで捕らえる）。

これが §10 の倉庫内/外の決定を**内（メタ認知）**へ決着させる根拠である。

## 7. IF — 感覚・運動（境界）

IF 層はポートでなく**感覚・運動の対**（アフォーダンス）。

**IF 契約（IF contract）:**

> 物理世界が、**種別 K** のトークンを、**プレース P** へ、
> **制約 C** 以内で返すこと — を**宣言**するもの。

Slack送信（出力）を投じた瞬間に「在庫結果というトークンが落ちるべき」が宣言され、
ネットはそのプレースに載せて停止、トークンが落ちたら再開。
**宣言しなければ** Slack送信は**漏れ**（出はするが戻らない）で、TS は閉じない。

## 8. SOS — System Operation System

**記号界で実働（作動）できるシステムを操作するシステムのライブラリ。**

作動（action）は実働系を記号化する。
SOS はその作動を、記号界から物理界に届ける運動器の集まり（Slack 送信・機械制御・…）。

## 10. 最初の石 — 在庫リフレックス

**物理基盤 ＝ Slack チャンネル ＋ 人間による在庫照合行為。**

```
Slack送信（運動器）→ 人が倉庫を覗く（物理）→ 在庫結果（感覚器）→ トークン再入
```

この一行が「on Physical」の最初の地面。
IF 契約 #1 は「人手・倉庫」に差し替え可能なアダプタとして書く。

### 決定 — 倉庫はスコープ内（メタ認知）

| 案 | 在庫の扱い | 閉包の重さ |
|---|---|---|
| **倉庫が内** ✅ | 在庫は「身体の状態」。マーキングに載る持続状態。逓減・補充もトランジションとしてモデル化 | **重い**（在庫の全変化をポートで捕らえる） |
| 倉庫が外 | 在庫は「非制御入力ポート」。ネットは「在庫チェックを投じた」まで、結果は外から落ちてくる | **軽い**（在庫状態は信用できない） |

**内を選ぶ。** 理由はコストのトレードオフ（重い閉包 vs 軽い閉包）ではなく、
**系が自資源状態を認識するか否か＝メタ認知するか否か**である（§6.7）。

在庫は外部の物でなく、系の実働が依存し消費する物理的基盤＝身体の状態。
閉じた接地系（TS）を欲する限り、発火の物理的帰結（在庫逓減）を空間状態に乗せねば、
クエリ間のモデルのずれ（隠れリーク）が生まれ、接地・有界性・閉包を同時に破る。
だからメタ認知はオプションでなく不変条件の要求。

代償は閉包の重さ — 在庫の全変化（逓減・補充・破損・棚卸し）をトランジションで捕らえる。
第一のリフレックスは「在庫チェック」から「**在庫の全状態管理**」に育つ。

> **倉庫＝内が定まった。** 第一の不変条件（接地）の具体 ＝ 在庫の全変化をポートで捕らえる。
> 次の石は、**ポートの棚卸し**（境界を跨ぐ全イベントを列挙）である。

| **メタ認知** | 系が自資源状態（在庫など）を空間状態の一部として認識すること。別モジュールでなく空間状態システムから生じる。閉じた接地系では必須（§6.7） |
| **IF** | 境界（膜）。感覚・運動。ポートの集合 |
| **IF 契約** | 物理世界が種別 K のトークンをプレース P に制約 C 内で返すことの宣言 |
| **SOS**（System Operation System） | 記号界で実働できるシステムを操作するシステムのライブラリ（作動の運動器） |
| **スコープ** | 実働世界の範囲 ＝ ポートの集合。最も高価な設計決定 |
| **閉包** | 境界を跨ぐすべてのイベントにポートがあること |
| **有界性** | 全プレースのトークンが有限に保たれること（機械的に判定可能） |
| **反射／審議** | 速い・局部／遅い・中央経路。常態は反射、例外のみ審議 |
| **マトリックス化** | スコープ境界（膜）の破断。完全で一貫しているのに真ではない状態 |
