【追記・訂正】呼び出し元調査結果（schedule_app.html を確認）
====================================

- buildSpecBox（spec_matching.js）は schedule_app.html:397 の renderSpecBox からのみ
  呼ばれているが、その renderSpecBox 自体がどこからも呼ばれていない完全なデッドコード。
  schedule_app.html:306 のコメントにも「旧・候補選択UIの renderSpecBox は下に残置。
  呼び出し元は本関数（renderPrescriptionCard）に切り替え済み」と明記されている。
  → matchCandidates, scoreCandidate, rankPrescriptions, buildSpecBox は
    いずれも本番では実行されないデッドコード。

- buildPrescriptionSet（prescription.js）は schedule_app.html:309 の
  renderPrescriptionCard から呼ばれ、renderPrescriptionCard 自体は line 276 で
  メインの描画フローから呼ばれている。→ こちらが実際に使われている経路（ライブコード）。

- ただし hasMixingConflict（spec_matching.js:16-27）だけは例外で、デッドパス
  （scoreCandidate）とライブパス（prescription.js の setHasInternalMixingConflict、
  spec_bridges.js の SPEC-BRIDGE-MIXING）の両方から共有されている。
  したがって「二重実装の統合」という指摘は、hasMixingConflict という共有部品を介した
  部分的な二重評価として残る（scoreCandidate 自体を直接統合する必要はない）。

この事実を踏まえ、以下の「まとめ」の項目1は次の通り補正する：


診断結果のまとめ（重要な指摘・補正版）
====================================

1. ロジックの二重実装（補正）
   spec_matching.js の scoreCandidate（if-elseチェーン）は デッドコードであり、
   本番では実行されない。統合が必要なのは scoreCandidate 自体ではなく、
   scoreCandidate と SPEC_BRIDGES の両方が依存している hasMixingConflict という
   共有関数の実装方式（文字列包含判定 → 行列参照）。
   Phase 3 では、まず buildSpecBox / matchCandidates / scoreCandidate / rankPrescriptions
   の削除（または明示的な "legacy, unused" 化）を検討し、hasMixingConflict のみを
   行列ベースに置き換えてライブパス（prescription.js, spec_bridges.js）に反映する。

2. 循環的な責任分散
   spec_bridges.js の SPEC_BRIDGE_MIXING_SET が prescription.js の
   setHasInternalMixingConflict/buildMixingReason を実行時参照しており、
   ファイル間の責任境界が循環している。

3. 暗黙の前提
   rbp_core.js:55 の w = weight[0] が「BRIDGEは常に一様重みベクトルを返す」という前提を
   検証なしに置いている。

4. 手続き的複雑度が最も高い箇所
   prescription.js の scorePrescriptionSet（40-122行）と buildPrescriptionSet（124-188行）。
   ここがPhase 3で最も慎重な設計が必要。

この段階では以上が洗い出し結果です。Phase 2（責任分離の設計）に進めてよいか、指示をお願いします。
